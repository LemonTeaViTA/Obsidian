## ⚡ 开场 30 秒

> SageCLI 是对标 Claude Code 的本地 Java Agent CLI，用自然语言驱动代码开发、调试和自动化。核心是三条执行路径——简单任务走 ReAct，多步依赖走 Plan-and-Execute（DAG 并行），需要质量审查走 Multi-Agent，三条共享同一套工具和记忆。底下支撑有 Provider 子类多模型适配、长上下文动态压缩、MCP 工具生态和安全纵深防御。具体实现与个人贡献边界以 [[SageCLI-03-证据与事实边界]] 为准。

## 🔴 最高频问题（必须流利）

### Q1：三条路径的区别是什么？各适合什么场景？

| 路径 | 适合场景 | 核心机制 |
|------|----------|----------|
| ReAct | 简单探索，灵活 | while循环，LLM停止调工具即结束 |
| Plan-Execute | 多步骤有依赖，可并行 | LLM生成DAG → 拓扑排序 → 分批并行 |
| Multi-Agent | 需要质量门控，有审查 | Planner/Worker/Reviewer三角色 |

**一句话收口：这是"规划-执行耦合度 vs 可控性/可并行"的谱系，不是越复杂越好。**

---

### Q2：ReAct 怎么防止死循环？

三道保险阀（优先级从高到低）：
1. **停滞检测**：对每轮工具调用集合取签名，连续3轮相同 → 判停滞
2. Token 上限（默认不限，可配）
3. 硬轮数上限（50轮）

**追问：停滞检测的局限？**
只能抓"完全相同的重复动作"。A/B 两工具交替横跳、参数含时间戳——这些只靠硬轮数兜底。这是有意的工程近似，简单够用。

---

### Q3：Plan-and-Execute 怎么处理循环依赖？并行怎么实现？

- **环检**：DFS 拓扑排序 + visiting/visited 双集合，visiting 中再次命中 = 有环 → 抛异常
- **并行**：拓扑排序后分层，同层节点无依赖关系 → 固定线程池（最多4）并行执行
- **计划解析两遍扫描**：第一遍建节点，第二遍连依赖边（解决前向引用 + 统一重编号）
- **重规划**：任务失败且进度 < 50% 时重新规划，最多2次

---

### Q4：Multi-Agent 并发时怎么保证线程安全？

- **Worker 池化**（BlockingQueue take/offer）：防同一实例被并发复用，Worker 有可变对话历史
- **Reviewer 按步 new 独立实例**：无状态，无竞争
- 状态更新加 synchronized，per-step 独立缓冲区，按顺序 flush 输出

**追问：Reviewer 审查失败默认不通过，但 Reviewer LLM 调用失败反而放行，矛盾吗？**
不矛盾。前者是"内容不可信"（fail-closed 拒绝）；后者是"服务不可用"（审查器故障不应阻塞已产出的 Worker 结果，fail-open 放行）。两种情况，方向相反都合理。

---

### Q5：多模型适配怎么做的？为什么不用类继承？

- `LlmClient` 接口 → `AbstractOpenAiCompatibleClient` 通用基类 → 各 Provider 子类
- 各 Provider 子类负责 endpoint、窗口、reasoning 字段名、图片格式等平台差异
- **加一个新平台：新增或调整对应 Provider 实现，并补充验证**

类继承 = 差异是代码，加平台必须写子类；数据驱动 = 差异是配置，加平台只改注册表。这是 LiteLLM 的核心思路。

---

### Q6：长上下文压缩策略？为什么用绝对值不用比率？

**触发线 = 窗口大小 - summaryReserve - buffer**（绝对值）

- 比率（如80%）：128k窗口触发点102k，8k窗口触发点6.4k → 相差悬殊，行为不稳定
- 绝对值：固定"留多少余量"的语义，跨模型行为一致

**分割点必须落在 user turn 边界**：assistant 的 tool_call 和 tool result 是强配对，切断会破坏格式。

---

### Q7：安全机制有哪些？

**四层**：
1. **命令黑名单**：HITL 之前先拦截（sudo/rm -rf/mkfs/curl|sh 等）
2. **HITL 三级审批**：只读自动允许；写文件/执行命令展示确认；危险命令阻断
3. **路径围栏**：文件操作必须在项目目录内，防 `../../` 逃逸
4. **审计日志**：危险操作按天写 JSONL，脱敏凭证

## 🟡 次高频问题（说清楚要点）

### Q：工具并行执行怎么保证结果顺序？

固定线程池并行执行，按**提交下标有序 Future.get()**（不是按完成顺序）。LLM 上下文里 tool_call 和 tool result 是按 id 配对的，乱序会导致 LLM 混淆。

### Q：记忆系统三层是什么？

- 短期：会话内，O(1)查找
- 长期：跨会话持久化，write-behind 异步（不阻塞响应）
- 项目级：PAI.md 随代码库，`@path` 行内导入（三重防护：深度/环检/子树）

### Q：MCP 怎么集成？SchemaSanitizer 做什么？

两种 transport：stdio（本地子进程）和 HTTP SSE（远端）。SchemaSanitizer 清洗第三方 MCP server 返回的不规范 JSON Schema，防止目标模型拒绝工具注册。

### Q：代码库检索怎么实现？

- 通路A：ripgrep 优先（快），不可用降级 Java 遍历；三态可用性缓存（启动时探测一次）
- 通路B：`/index` 触发，JavaParser AST 分块 → embedding → SQLite 向量索引
- 混合评分：语义分 + 关键词基础分(0.3) + 分级加分 + 类型加分

## 🆕 第11-23期新特性（次高频）

### Q：Skill 系统是什么？为什么不直接往 system prompt 里加规则？

**Skill = 决策手册 + 按需加载**

- 结构：`SKILL.md`（frontmatter + 正文）+ `references/`（按需读取）
- 三层加载：jar 内置 < 用户级 `~/.paicli/skills/` < 项目级 `.paicli/skills/`
- 加载时机：启动期注入 `name` + `description` 索引（≤ 4KB），运行期 LLM 调用 `load_skill(name)` 后注入正文

**为什么不直接加规则**：工具堆成山（内置 9 个 + MCP 60+ 工具），system prompt 塞规则不可扩展。Skill 是"打包专家手册"，按场景展开。

**内置 web-access skill**：浏览哲学四步法 + 工具选择表 + 6 个站点经验文件（微信公众号/知乎/小红书等）

**追问：Skill 内调用危险工具怎么审批？**
沿用既有 HITL 审批，不给 Skill 单独审批维度。Skill 是"告诉 Agent 怎么思考"，不是"绕过安全门控"。

---

### Q：三种终端形态的区别？为什么需要三种？

| 形态 | 启用方式 | 适用场景 |
|------|---------|---------|
| inline 流式 TUI（默认） | `PAICLI_RENDERER=inline` | Claude Code 风格，流式体验 + 底部 dock 状态栏 |
| lanterna 全屏 TUI | `PAICLI_RENDERER=lanterna` | 大屏操作，三栏布局（文件树 + 对话流 + 状态栏） |
| plain 兜底 | `PAICLI_RENDERER=plain` | 纯文本，兼容不支持 ANSI 的终端 |

**为什么需要三种**：不同用户偏好不同，硬编码单一形态不够灵活。三种形态共享同一套 Agent / ToolRegistry / MemoryManager，不创建孤立空会话。

---

### Q：Git 快照为什么不写用户项目 .git？

**Side-git 设计**：快照仓库独立于用户项目，默认位于 `~/.paicli/snapshots/<project_hash>/<worktree_hash>/.git`

**原因**：
1. 不污染用户项目 `.git` 历史
2. 支持多 worktree（每个 worktree 独立快照）
3. 异步创建 post-turn 快照，不阻塞响应
4. 快照清理不影响用户项目

**快照时机**：`pre-turn`（开始前）+ `post-turn`（结束后异步）+ `pre-restore`（恢复前）

---

### Q：Runtime API 的应用场景是什么？

**场景**：外部系统接入 Agent 能力
- CI / CD 管道中自动生成测试
- 定时任务触发代码审查
- 团队协作平台集成（如钉钉/飞书）

**架构**：
- SQLite 持久化任务队列（单机够用，避免 Redis / Kafka 依赖）
- Worker Pool 默认 2 个（可配置）
- HTTP API：`POST /v1/threads`、`POST /v1/threads/{id}/turns`、`GET /v1/threads/{id}/events`
- 强制要求 `PAICLI_RUNTIME_API_KEY`（避免未授权访问）

---

### Q：图片输入怎么适配不支持多模态的模型？

**ContentPart 抽象**：`text` / `image_base64` / `image_url`

**模型适配**：
- `LlmClient.supportsImageInput()` 声明图片能力
- DeepSeek 等文本 provider 会把图片块替换成文本提示（"[Image: 尺寸 1920x1080, 来源 ...]"）
- GLM 用户可通过 `/model glm-5v-turbo` 切换到多模态模型

**上下文管理**：新一轮任务开始前省略历史 image payload，仅保留文本元信息，避免旧截图反复进入上下文。

---

### Q：微信通道为什么用更严格的安全策略？

**非交互式默认拒绝策略**：
- 只读工具：默认允许
- `write_file` / `create_project`：受 workspace PathGuard 限制
- `execute_command`：必须精确命中命令白名单
- `mcp__*`：必须命中 MCP 白名单
- `revert_turn` 和浏览器会话切换：默认拒绝

**原因**：
1. 非交互式场景下用户无法看到完整上下文，误操作风险更高
2. 移动端用户更可能在碎片时间使用，注意力分散
3. 微信侧只接收 assistant 正文，用户看不到 thinking / 工具调用过程

---

### Q：长上下文工程的三种模式有什么区别？

| 模式 | 预算策略 | RAG topK | 摘要压缩 | 适用场景 |
|------|---------|----------|----------|----------|
| short | 80% * window | 默认（3-5） | 启用 | 短窗口模型（GLM-5.1 200k） |
| balanced | 80% * window | 默认 | 启用 | 平衡模式 |
| long | 跳过压缩 | 提升到 20 | 禁用 | 长窗口模型（DeepSeek V4 1M） |

**动态适配**：`AgentBudget` 按当前模型动态计算预算，`search_code` 未显式传 `top_k` 时按上下文模式自适应。

**追问：为什么长模式跳过压缩？**
长窗口模型可以承担更多上下文，摘要压缩虽然省 token 但丢信息。短窗口模型必须压缩，长窗口模型可以选择保留完整信息。

---

### Q：LSP 诊断注入的作用是什么？

**场景**：Agent 写代码后可能有语法错误，但没有反馈机制。

**实现**：
- `write_file` 成功后触发 post-edit 诊断
- 当前 MVP 对 Java 文件使用 JavaParser 做轻量语法诊断
- 诊断结果注入下一轮 LLM 请求（按 error / warning / info、文件、行列号、message 格式化）
- 默认最多注入 20 条

**关键权衡**：诊断结果不阻塞工具主流程。诊断失败（JavaParser 解析异常、LSP server 不可用）不应让 `write_file` 失败。

---

### Q：Chrome DevTools MCP 的两种模式有什么区别？

| 模式 | 适用场景 | 启动参数 | 风险 |
|------|---------|---------|------|
| isolated | 公开页面、测试 | `--isolated=true`（临时 profile） | 低 |
| shared | 需要登录态 | `--autoConnect` + `--browser-url` | 高 |

**模式切换**：
- `/browser connect [port]`：切到 shared 模式
- Agent 遇到登录页时会自动调用 `browser_connect`

**安全门控**：
- shared 模式下 `close_page` 只能关闭 PaiCLI 自己创建的 tab
- 敏感页面命中规则后，`click` / `fill_form` / `evaluate_script` 必须单步 HITL
- 切换模式时清空 server 维度全部放行

### Q：Prompt 分层架构的组装流水线是什么？

```
base -> personality -> mode -> approval -> runtime_context
     -> project_context -> skills -> context_mgmt -> handoff
```

**加载优先级**：内置 < 用户级 `~/.paicli/prompts/` < 项目级 `.paicli/prompts/`（最高）

**动态注入**：
- `runtime_context`：当前日期/时区
- `project_context`：先注入 `PAI.md` 项目记忆，再注入 `/save` 检索到的相关长期记忆和 MCP resource 索引

**为什么抽离**：硬编码 prompt 修改需要重新编译；用户无法自定义 Agent 行为。项目级覆盖优先级最高，团队可以在代码库里定义项目特定行为。
