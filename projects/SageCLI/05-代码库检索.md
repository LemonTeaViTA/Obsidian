# 代码库检索

**是什么**：让 Agent 在不读全部代码的情况下找到相关上下文的两条检索通路。

**为什么**：代码库往往超出上下文窗口，必须主动检索而不是全量输入。

**怎么做**：
- 通路 A（关键词）：优先用 ripgrep（速度快），不可用时降级为 Java 遍历；可用性三态缓存（启动时探测一次，运行时不重复探测）
- 通路 B（语义）：`/index` 命令触发，JavaParser 解析 AST 分块 → embedding → 存 SQLite 向量索引
- 混合评分：语义相似度（0~1）+ 关键词基础分（0.3）+ 分级加分 + 双重命中奖励 + 文件类型加分
- 两条通路结果合并、去重、按分数排序后返回给 LLM

**关键权衡**：向量检索目前是暴力 KNN（O(n)），中小型代码库够用，大型代码库需要升级 FAISS/pgvector——这是已知的性能债，有意推迟。

## 面试 Q&A

**Q：为什么 ripgrep 可用性要缓存而不是每次检测？**
每次检索都探测 ripgrep 是否存在会增加延迟。三态缓存（AVAILABLE/UNAVAILABLE/UNKNOWN）把探测结果记下来，运行中不重复系统调用。

**Q：混合评分里关键词基础分 0.3 是什么意思？**
关键词匹配命中就给 0.3 的基础加分，再叠加语义分。这样关键词精确匹配的结果不会因为 embedding 相似度略低而被排到后面——精确命中本身就是强信号。

**Q：为什么用 AST 分块而不是按行数分块？**
按行数切可能切断一个类或方法，embedding 的语义不完整。AST 分块保证每个块是语义完整的单元（类/方法/函数），embedding 质量更高，检索更准确。
