## 第12期：长上下文工程

**是什么**：根据模型能力动态调整上下文预算和检索策略，支持三种上下文模式。

**为什么**：不同模型窗口大小差异巨大（GLM-5.1 200k vs DeepSeek V4 1M），固定预算和检索策略不合理。

**怎么做**：

*模型能力声明*
- `LlmClient` 接口新增 `maxContextWindow()`、`supportsPromptCaching()`、`promptCacheMode()`
- GLM-5.1 默认 200k、DeepSeek V4 默认 1M、StepFun 默认 256k

*三种上下文模式*
| 模式 | 预算策略 | RAG topK | 摘要压缩 |
|------|---------|----------|----------|
| short | 80% * window | 默认（3-5） | 启用 |
| balanced | 80% * window | 默认 | 启用 |
| long | 跳过压缩 | 提升到 20 | 禁用 |

*动态适配*
- `AgentBudget` 按当前模型动态计算预算
- `search_code` 未显式传 `top_k` 时按上下文模式自适应
- 长上下文模式下自动把 MCP resources 的 URI / 描述索引注入 system prompt

*状态可见化*
- inline 模式下 Token / cached input tokens / 估算成本 / 耗时进入底部状态栏
- `/context` 显示当前上下文模式、prompt cache 模式、RAG topK、resources 自动索引状态

**关键权衡**：长上下文不是银弹。摘要压缩虽然丢信息，但对短窗口模型必要；长窗口模型可以跳过压缩，但要承担成本和延迟。

## 第13期：Chrome DevTools MCP

**是什么**：接入 Google 官方 `chrome-devtools-mcp`，让 Agent 能操作真实浏览器。

**为什么**：`web_fetch` 只能处理静态 HTML，遇到 SPA / JS 渲染 / 防爬墙站点（微信公众号、知乎专栏、小红书）会失败。

**怎么做**：

*默认配置*
- `~/.paicli/mcp.json` 不存在时启动自动创建模板
- 默认使用 `--isolated=true` 临时浏览器 profile（无登录态）
- 注册为 `mcp__chrome-devtools__navigate_page`、`take_snapshot`、`click`、`fill_form` 等工具

*与 web_fetch 的协同*
- `web_fetch` 失败的站点会引导走浏览器 MCP
- 公开页面如微信公众号文章不需要登录态

*HITL 优化*
- "全部放行"支持 MCP server 维度
- 连续浏览器操作可对 `chrome-devtools` 一次确认

*图片处理*
- `image` 类型结果作为图片输入附加到下一轮
- 文本 fallback 保留，用于 DeepSeek 等不接受图片的 provider 自动降级

*超时处理*
- MCP initialize 默认超时 60 秒
- CLI 首屏默认最多等待 8 秒，超时后先进入交互，未完成的 server 保持 `starting` 并后台继续启动

**关键权衡**：临时 profile 安全但无登录态；shared profile（第14期）有登录态但需要敏感页面门控。

## 第14期：CDP 会话复用 + 登录态访问

**是什么**：支持切换到用户已登录的 Chrome，访问需要登录态的页面。

**为什么**：临时 profile 无法访问需要登录的内容（企业内网、个人账号页面）。

**怎么做**：

*两种模式*
| 模式 | 适用场景 | 启动参数 |
|------|---------|---------|
| isolated | 公开页面、测试 | `--isolated=true` |
| shared | 需要登录态 | `--autoConnect` + `--browser-url` |

*模式切换*
- `/browser connect [port]`：切到 shared 模式
- `/browser disconnect`：切回 isolated 模式
- Agent 遇到登录页时会自动调用 `browser_connect`

*安全门控*
- shared 模式下 `close_page` 只能关闭 PaiCLI 自己创建的 tab
- 敏感页面命中规则后，`click` / `fill_form` / `evaluate_script` 必须单步 HITL
- 切换模式时清空 server 维度全部放行

*审计增强*
- chrome-devtools 工具追加可选浏览器 metadata：`browser_mode`、`sensitive`、`target_url`

**关键权衡**：shared 模式能力更强但风险更高，必须有敏感页面门控 + 单步审批。

## 第15期：Skill 系统

**是什么**：把"Agent 该怎么思考"从硬编码 system prompt 抽出，沉淀成可复用单元。

**为什么**：工具堆成山（内置 9 个 + MCP 60+ 工具），往 system prompt 里塞更多规则不可扩展。

**怎么做**：

*Skill 结构*
```
<name>/
├── SKILL.md          # 决策手册（frontmatter + 正文）
├── references/       # 按需读取的引用文档
└── scripts/          # 可选的可执行依赖
```

*三层加载位置*（按优先级，后者整体覆盖同名 skill）
1. jar 内置
2. 用户级 `~/.paicli/skills/<name>/`
3. 项目级 `<project>/.paicli/skills/<name>/`

*加载时机*
- 启动期：把启用 skill 的 `name` + `description` 注入系统提示词索引段（启用上限 20 个，索引段 ≤ 4KB）
- 运行期：LLM 调用 `load_skill(name)` 后，把 SKILL.md 正文（5KB 截断）写入 `SkillContextBuffer`，下一轮 user message 自动前置注入

*内置 web-access skill*
- 决策手册：浏览哲学四步法 + 工具选择表 + 浏览器优先级 + Jina 兜底说明
- 6 个站点经验文件：mp.weixin / zhuanlan.zhihu / x.com / xiaohongshu / github / juejin
- cdp-cheatsheet

*CLI 命令*
- `/skill list` / `/skill show <name>` / `/skill on <name>` / `/skill off <name>` / `/skill reload`
- 启用状态持久化到 `~/.paicli/skills.json` 的 `disabled` 列表

**设计意图**：从「写工具」演进到「打包专家手册」。Skill 给 LLM 一份按场景展开的"专家手册"。

**关键权衡**：Skill 内调用危险工具仍走既有 HITL 审批，不给 Skill 单独审批维度。

## 第16期：TUI 产品化（v16.1 三种形态）

**是什么**：抽出 `Renderer` 接口，支持三种可切换的终端形态。

**为什么**：不同用户偏好不同（Claude Code 风格 vs 全屏 TUI vs 纯文本），硬编码单一形态不够灵活。

**怎么做**：

*三种形态*
| 形态 | 启用方式 | 视觉风格 |
|------|---------|---------|
| **inline 流式 TUI**（默认） | 直接运行 / `PAICLI_RENDERER=inline` | Claude Code / Qoder 风格：π 主题彩色开屏、主屏直出、底部 dock（YOLO/HITL、MCP、Skill、model、ctx、token、cwd）、行内可折叠工具块、行内 git diff |
| **lanterna 全屏 TUI** | `PAICLI_RENDERER=lanterna` | v16 三栏全屏：文件树 + 对话流 + 状态栏 + 底部输入栏，HITL 模态弹窗 |
| **plain 兜底** | `PAICLI_RENDERER=plain` | 纯 println，无折叠 / 状态栏，等价 v15 行为 |

*共享底层*
- 三种形态共享同一套 `Agent` / `ToolRegistry` / `MemoryManager` / MCP server / SkillRegistry / HITL handler
- 不创建孤立空会话

*通用命令*
- `/clear`、`/context`、`/memory`、`/save <事实>`、`/export`、`/hitl`、`/config`、`/exit`
- `/plan <任务>` 走 Plan-and-Execute，`/team <任务>` 走 Multi-Agent，`/cancel` 取消运行中任务

*兼容性开关*
- `PAICLI_NO_STATUSBAR=true` 在 inline 模式下禁用 JLine 底部 dock
- `NO_COLOR=1` 禁用所有 ANSI 颜色，保留布局

**关键权衡**：inline 形态是默认，兼顾流式体验和状态可见性；lanterna 全屏适合大屏操作；plain 是兜底。

## 第17期：LSP 诊断注入（MVP）

**是什么**：`write_file` 成功后触发 post-edit 诊断，诊断结果注入下一轮 LLM 请求。

**为什么**：Agent 写代码后可能有语法错误，但没有反馈机制；人工验证成本高。

**怎么做**：

*当前 MVP*
- 对 Java 文件使用 JavaParser 做轻量语法诊断
- 不依赖本机安装 JDT LS

*诊断注入*
- ReAct、Plan-and-Execute、Multi-Agent 三条路径都会在下一轮 LLM 请求前注入 pending 诊断
- 诊断按 error / warning / info、文件、行列号、message 格式化
- 默认最多注入 20 条

*配置*
- `PAICLI_LSP_ENABLED=false` 可关闭
- `PAICLI_LSP_MAX_DIAGNOSTICS=20` 可调整注入上限

*后续增强*
- 接入 JDT LS / rust-analyzer / pyright / gopls 的 stdio JSON-RPC transport

**关键权衡**：诊断结果不阻塞工具主流程，避免诊断失败影响 Agent 执行。

## 第18期：Git Side-History 快照与回滚（MVP）

**是什么**：每个 turn 开始前创建快照，结束后异步创建快照；支持回滚。

**为什么**：Agent 写错代码或执行错误操作后，用户需要快速恢复到之前状态。

**怎么做**：

*快照时机*
- `pre-turn`：每个 ReAct / Plan / Team turn 开始前创建
- `post-turn`：结束后异步创建
- `pre-restore`：恢复前先创建（防止误操作）

*快照仓库*
- 使用 JGit 纯 Java 实现
- 默认位于 `~/.paicli/snapshots/<project_hash>/<worktree_hash>/.git`
- 不写用户项目 `.git`

*CLI 命令*
- `/snapshot`：查看最近快照
- `/snapshot status`：查看配置与 side-git 目录
- `/snapshot clean`：清理当前项目快照目录
- `/restore <N>`：恢复到最近第 N 个 `pre-turn` 快照

*Agent 工具*
- 内置 `revert_turn` 工具，纳入 HITL 与 AuditLog 危险工具链

*配置*
- `PAICLI_SNAPSHOT_ENABLED=false` 可关闭
- `PAICLI_SNAPSHOT_MAX=50` / `PAICLI_SNAPSHOT_EXCLUDES=...` / `PAICLI_SNAPSHOT_DIR=...` 可调整策略

**关键权衡**：快照存在独立 side-git 仓库，不污染用户项目 `.git`；异步创建 post-turn 快照，不阻塞响应。

## 第19期：Prompt 分层架构（MVP）

**是什么**：把 system prompt 从 Java 硬编码抽离到 `src/main/resources/prompts/`，支持用户级和项目级覆盖。

**为什么**：硬编码 prompt 修改需要重新编译；用户无法自定义 Agent 行为。

**怎么做**：

*Prompt 组装流水线*
```
base -> personality -> mode -> approval -> runtime_context 
     -> project_context -> skills -> context_mgmt -> handoff
```

*加载优先级*
1. 内置：`src/main/resources/prompts/`
2. 用户级：`~/.paicli/prompts/...`
3. 项目级：`.paicli/prompts/...`（最高优先级）

*覆盖规则*
- 覆盖是整文件替换
- `base.md` 和最终 prompt 必须包含 `## Language`

*动态注入*
- `runtime_context` 注入当前日期/时区
- `project_context` 先注入 `PAI.md` 项目记忆，再注入 `/save` 检索到的相关长期记忆和 MCP resource 索引

*审计模板*
- Prompt 改动审计模板见 `docs/prompt-analysis-template.md`

**关键权衡**：项目级覆盖优先级最高，团队可以在代码库里定义项目特定行为。

## 第20期：异步后台任务 + Runtime API（MVP）

**是什么**：支持后台任务队列和 HTTP Runtime API，让外部系统接入 PaiCLI。

**为什么**：长时间任务阻塞交互式会话；外部系统（如 CI / CD）需要调用 Agent 能力。

**怎么做**：

*后台任务*
- `DurableTaskManager` 使用 SQLite 持久化任务队列
- 默认位置 `~/.paicli/tasks/tasks.db`
- 任务生命周期：`enqueued -> running -> completed / failed / canceled`

*Worker Pool*
- 默认 2 个后台 worker
- 可通过 `PAICLI_TASK_WORKERS` 调整

*CLI 命令*
- `/task`：查看任务列表
- `/task add <任务内容>`：添加后台任务
- `/task cancel <task_id>`：取消任务
- `/task log <task_id>`：查看任务日志

*Runtime API*
- 启动：`java -jar target/paicli-1.0-SNAPSHOT.jar serve --http --port 8080`
- 端点：
  - `POST /v1/threads`：创建线程
  - `POST /v1/threads/{id}/turns`：发送 turn
  - `GET /v1/threads/{id}/events`：获取事件
- 强制要求 `PAICLI_RUNTIME_API_KEY` 或 `-Dpaicli.runtime.api.key`

**关键权衡**：SQLite 单机够用，避免引入 Redis / Kafka 依赖；API Key 强制要求，避免未授权访问。

## 第21期：图片复制粘贴输入（MVP）

**是什么**：支持在 prompt 里引用图片，多模态模型可以处理图片输入。

**为什么**：用户想让 Agent 分析截图、UI 设计稿、错误截图等视觉内容。

**怎么做**：

*ContentPart 抽象*
- `LlmClient.Message` 支持 `ContentPart`，包括 `text`、`image_base64`、`image_url`

*引用方式*
- `@image:file:///abs/path.png`：绝对路径
- `@image:/abs/path.png`：绝对路径（简写）
- `@image:relative/path.png`：相对路径
- Ctrl+V：粘贴剪贴板图片

*模型适配*
- `LlmClient` 公共接口用 `supportsImageInput()` 声明图片能力
- DeepSeek 等文本 provider 会把图片块替换成文本提示
- GLM 套餐用户可通过 `/model glm-5v-turbo` 切换到多模态模型

*图片预处理*
- 压缩 / 缩放后作为图片块发送（不是 OCR 成文本）
- 带 alpha 的 PNG 会铺白底重编码
- 额外注入来源、尺寸和坐标映射元信息

*MCP 图片*
- MCP `image` content 会保留 base64 与 `mimeType`
- 在 ReAct / Plan / SubAgent 工具结果后作为图片 user message 回灌

*上下文管理*
- 新一轮任务开始前会省略历史 image payload，仅保留文本元信息
- 避免旧截图反复进入上下文

*兼容性*
- DeepSeek 流式调用默认使用 HTTP/1.1，规避部分 HTTP/2 网关长 SSE 响应被重置

**当前边界**：不做视频 / 音频、图像生成、TUI sixel 图片预览。

**关键权衡**：图片预处理策略参考 Claude Code，压缩后发送而不是本地 OCR，保留视觉信息。

## 第23期：微信 iLink 通道（文本 MVP）

**是什么**：通过微信 iLink 协议接入，支持在微信里和 Agent 对话。

**为什么**：移动场景下用户更习惯在微信里交互；终端不适合移动设备。

**怎么做**：

*进程级入口*
- `paicli wechat setup`：扫码绑定
- `paicli wechat start`：启动通道
- `paicli wechat status`：查看状态
- `paicli wechat daemon start|stop|restart|status|logs`：守护进程管理

*交互式入口*
- `/wechat`：扫码绑定并在当前进程后台启动
- `/wechat setup`：重新扫码绑定
- `/wechat status`：查看状态
- `/wechat stop`：停止通道

*二维码显示*
- 支持在 Warp / iTerm2 / WezTerm 等兼容终端内直接显示 260px PNG 二维码
- 不支持终端图片协议时回退为字符二维码和链接

*通信协议*
- iLink `getupdates` 长轮询收消息
- `sendmessage` 分片回消息
- 不依赖 SSE

*消息处理*
- 只接受绑定用户私聊
- 普通消息单并发排队
- `/help`、`/status`、`/pause`、`/resume`、`/stop` 走队列外控制路径

*消息格式*
- 微信侧用户消息会回显到 PaiCLI 终端 transcript
- PaiCLI 终端继续显示 thinking / 工具调用过程，微信侧只接收 assistant 正文
- 保留 ClawBot 稳定支持的 Markdown 子集（列表、引用、粗体、行内代码、真实代码块）
- 把标题转成粗体标题、把表格转成移动端更稳的键值/列表
- 过滤图片 Markdown / H5-H6 / 中文斜体等兼容性差的标记

*安全策略*（非交互式默认拒绝）
- 只读工具：默认允许
- `write_file` / `create_project`：受 workspace PathGuard 限制
- `execute_command`：必须精确命中命令白名单
- `mcp__*`：必须命中 MCP 白名单
- `revert_turn` 和浏览器会话切换：默认拒绝

**当前文本 MVP 边界**：保留图片 / 文件消息的媒体元数据提示，但 CDN 下载解密、图片块输入和 `/send` 文件推送仍待后续媒体链路补齐。

**关键权衡**：微信通道使用更严格的非交互式安全策略，避免用户在移动端误操作。

## 📌 面试要点

**Q：这么多新特性，哪些是核心？**
- 第12期长上下文工程：动态预算是基础能力增强
- 第15期 Skill 系统：架构演进，从工具到专家手册
- 第16期 TUI 产品化：用户体验升级

**Q：微信通道为什么用更严格的安全策略？**
非交互式场景下用户无法看到完整上下文，误操作风险更高。移动端用户更可能在碎片时间使用，注意力分散，必须收紧默认权限。

**Q：为什么 Skill 系统不给单独审批维度？**
Skill 本质是"告诉 Agent 怎么思考"，不是"绕过安全门控"。Skill 内调用危险工具仍走既有 HITL，保证审批粒度一致。

**Q：LSP 诊断为什么不阻塞工具主流程？**
诊断失败（JavaParser 解析异常、LSP server 不可用）不应让 `write_file` 失败。诊断是辅助反馈，不是强依赖。
