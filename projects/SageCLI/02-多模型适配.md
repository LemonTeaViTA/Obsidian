# 多模型适配

**是什么**：一套代码接入多家国产大模型（DeepSeek / GLM / Qwen / Kimi / StepFun）的适配层。

**为什么**：各平台协议兼容 OpenAI 但各有差异（endpoint、上下文窗口、reasoning 字段名、图片格式等），如果每个平台写一个子类，差异就变成了类层次，加一个平台要写代码。

**怎么做**：
- `LlmClient` 接口定义统一抽象，能力查询（是否支持工具/缓存/图片）全有 default 默认值
- `AbstractOpenAiCompatibleClient` 封装通用逻辑（SSE 解析、流式 tool_call 拼接、token 计数）
- `SeriesQuirks` 是一个不可变 record 注册表，每个模型系列的差异全部描述在这里，查表即用
- 加一个新平台：往注册表加一条记录，不写新类
- `FallbackLlmClient` 装饰器：主模型失败自动切备用，对上层透明

**关键权衡**：数据驱动（差异是配置）vs 类继承（差异是代码）——前者扩展成本几乎为零，代价是 SeriesQuirks 字段越来越多时需要维护。

## 面试 Q&A

**Q：为什么不直接让每个平台继承一个抽象类？**
类继承把差异固化成代码，加平台必须写子类。数据驱动把差异变成注册表里的一行记录，加平台只改配置，业务逻辑完全不动。这是 LiteLLM 的核心思路。

**Q：流式 tool_call 为什么容易出 bug？**
普通文本只需拼接 content 碎片。tool_call 是结构化对象，name 和 arguments 也被切碎分 chunk 下发，需要按 index 用 accumulator 追踪并拼接，最后一次性组装。任何 chunk 乱序或漏掉都会导致工具调用失败。

**Q：FallbackLlmClient 故障转移怎么触发？**
主模型调用抛异常（超时、HTTP 错误等）时切换到备用 LlmClient，整个切换对调用方透明，因为 FallbackLlmClient 本身也实现 LlmClient 接口。
