# 三条执行路径

**是什么**：三种递进的任务编排策略，对应不同复杂度的任务场景。

**为什么**：单一策略无法同时满足轻量灵活（ReAct）、结构化可并行（Plan-Execute）、有质量门控（Multi-Agent）三种需求。

**怎么做**：

*ReAct*
- 单 Agent while 循环：调工具 → 观察结果 → 继续，直到 LLM 不再调工具
- AgentBudget 三道保险阀（优先级：停滞检测 > token 上限 > 硬轮数 50）
- 停滞检测：对每轮工具调用集合取签名，连续 N 轮相同判停滞

*Plan-and-Execute*
- 先让 LLM 生成 DAG 任务计划，再按拓扑排序分批并行执行
- 解析计划两遍扫描：第一遍建节点，第二遍连依赖边（解决前向引用）
- 任务失败且进度不足 50% 时触发重规划（最多 2 次）

*Multi-Agent*
- Planner 拆任务 → Worker 池并发执行 → Reviewer 每步独立审查
- Worker 池化（BlockingQueue），防止同一实例被并发复用导致历史污染
- Reviewer 按步 new 独立实例；审查失败带 previous_output + issues 重试，最多 2 次

**关键权衡**：这是「规划-执行耦合度 vs 可控性/可并行」的谱系，不是越复杂越好，任务越简单越该走轻量路径。

## 面试 Q&A

**Q：ReAct 为什么不直接写死最大轮数？**
主退出条件交给 LLM（不再调工具），AgentBudget 只是保险阀。写死轮数会在长上下文场景提前截断有效任务；停滞检测 + 硬轮数兜底已经足够安全。

**Q：停滞检测的局限是什么？**
只能抓「连续 N 轮工具名+参数完全相同」的重复动作型死循环。反例：A/B 两工具交替横跳、参数含时间戳每次不同、语义无进展但参数微调——这些只能靠硬轮数兜底。

**Q：为什么计划解析要两遍扫描？**
依赖字段可能引用还没建好的节点（前向引用），必须先建全部节点再连边。重编号顺带解决 LLM 生成 id 不规范的问题。

**Q：Multi-Agent 并发时如何保证线程安全？**
Worker 池化防止同一实例并发复用（历史状态可变）；Reviewer 独立实例无竞争；状态更新加锁；每步独立缓冲区按顺序 flush 输出。

**Q：Reviewer 解析失败为什么默认不通过？**
fail-closed 策略：宁可多重试也不放行可能有问题的输出。区别于 Reviewer LLM 调用整体失败时 approved=true 放行——那是基础设施故障，不应让审查器故障阻塞主流程（内容不可信 vs 服务不可用，两种情况，方向相反都合理）。
