# 长上下文工程

**是什么**：防止对话历史超出模型上下文窗口的动态压缩机制。

**为什么**：不能等窗口真的满了再压缩——生成摘要本身需要消耗 token 空间，满了就没空间生成摘要了。

**怎么做**：
- 压缩触发线 = 窗口大小 - summaryReserve（摘要空间）- buffer（余量），是绝对值不是比率
- 触发后 5 步压缩：找分割点 → 取前段发给 LLM 生成摘要 → 摘要作为 system message 插到头部 → 保留后段原始历史 → 更新 token 计数
- 分割点必须落在 user turn 边界（不能切断 assistant/tool 配对）
- 成本估算：三档计价（input / output / cached），Pricing.UNKNOWN 不拒绝请求只是不计费

**关键权衡**：触发线用绝对值而非比率——比率在大窗口下浪费太多，在小窗口下留量不够；绝对值行为稳定但需要按模型配置 summaryReserve。

## 面试 Q&A

**Q：为什么分割点必须落在 user turn 边界？**
assistant 的 tool_call 消息和 tool result 消息是强配对关系，切断任意一方会破坏对话格式，模型会报错或产生幻觉。user turn 是语义上的自然断点，切这里最安全。

**Q：绝对触发线 vs 比率触发线的区别？**
比率（如 80%）在 128k 窗口下触发点是 102k，在 8k 窗口下是 6.4k——相差悬殊，行为不一致。绝对值配合固定的 summaryReserve，跨模型"留多少余量"的语义一致。

**Q：Pricing.UNKNOWN 是什么情况？**
接入了一个没有录入定价信息的新模型。选择不拒绝请求、只是成本显示为 0——降级容忍，不影响功能可用性。
