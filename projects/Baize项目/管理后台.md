# 管理后台

> 问题：管理后台是怎么设计的？为什么 Provider 配置要做成数据库可切换的，它又是怎么和聊天模块的 `LlmProviderRouter` 联动的？

管理后台是仅 `ROLE_ADMIN` 可访问的运维控制面，承担四件事：**用户管理、模型 Provider 配置、邀请码管理、管理员账号引导**。它的核心价值在于把原本写死在配置文件里的运行时参数（用哪个 LLM、用哪个 Embedding、谁能注册）下沉到数据库，让运营无需重启、无需改代码就能调整系统行为。

## 一、模块边界与参与文件

| 文件 | 职责 |
| --- | --- |
| `controller/AdminController.java` | 管理端点（users / providers / invite-codes） |
| `service/ModelProviderConfigService.java` | LLM / Embedding provider 配置 |
| `service/InviteCodeService.java` | 邀请码生成与校验 |
| `config/AdminUserInitializer.java` | 管理员账号引导创建 |
| `model/ModelProviderConfig.java` | Provider 配置实体 |
| `model/InviteCode.java` | 邀请码实体 |

所有端点挂在 `/api/v1/admin/**` 下，统一由 Spring Security 限定 `ROLE_ADMIN`。

## 二、用户管理

最基础的一组 CRUD 端点，给管理员一个统一的用户视图与角色管控能力：

```
GET    /api/v1/admin/users              — 查询所有用户
GET    /api/v1/admin/users/{userId}     — 查询单个用户
PUT    /api/v1/admin/users/{userId}/role — 修改用户角色
DELETE /api/v1/admin/users/{userId}     — 删除用户
```

角色修改是这里最敏感的操作，它直接决定一个账号能否访问整个管理后台，因此自身就受 `ROLE_ADMIN` 保护。

## 三、模型 Provider 配置（核心设计）

### 1. 为什么要做成数据库可切换

如果把 LLM / Embedding 的 `model`、`apiBaseUrl`、`apiKey` 写死在 `application.yml`，那么每次换模型（比如从自建 vLLM 切到 OpenAI、或换一个 Embedding 模型）都要改配置、重新打包、重启服务。把这些参数抽到 `model_provider_config` 表后，换模型变成一次 HTTP 调用，运营即时生效，这就是 Provider 配置存在的全部理由。

### 2. scope 与"唯一活动"约束

Provider 按 `scope` 区分用途，取值 `"llm"` 或 `"embedding"`。设计上要求**同一 scope 任意时刻只有一个活动 provider**，避免出现"无活动 provider"（聊天直接报错）或"多个活动 provider"（行为不确定）两种坏状态。

Provider 管理端点：

```
GET    /api/v1/admin/providers              — 查询所有 provider 配置
POST   /api/v1/admin/providers              — 创建新 provider
PUT    /api/v1/admin/providers/{id}         — 更新 provider
PUT    /api/v1/admin/providers/{id}/activate — 激活 provider
DELETE /api/v1/admin/providers/{id}         — 删除 provider
```

### 3. 第一个 Provider 自动激活

新建 provider 时会先数一下当前 scope 下已有几个，如果是第一个就自动置为活动，省去运营"建完还要手动激活一次"的额外步骤，也保证系统从空配置到可用之间没有断档：

```java
// createProvider 节选
if (config.getScope() == null || config.getModel() == null || config.getApiBaseUrl() == null) {
    throw new CustomException("缺少必填字段");
}

// 如果是第一个 provider，自动激活
long count = modelProviderConfigRepository.countByScope(config.getScope());
if (count == 0) {
    config.setActive(true);
}
return modelProviderConfigRepository.save(config);
```

### 4. 激活的原子性：先停用，再激活

`activateProvider` 必须先把同 scope 下的其他活动 provider 全部停用，再激活目标 provider，这一步保证"唯一活动"约束不被破坏：

```java
// activateProvider 节选
ModelProviderConfig config = modelProviderConfigRepository.findById(id)
    .orElseThrow(() -> new CustomException("Provider 不存在"));

// 停用同 scope 的其他 provider
List<ModelProviderConfig> others =
    modelProviderConfigRepository.findByScopeAndIsActive(config.getScope(), true);
for (ModelProviderConfig other : others) {
    other.setActive(false);
    modelProviderConfigRepository.save(other);
}

// 激活当前 provider
config.setActive(true);
return modelProviderConfigRepository.save(config);
```

> [!note] 为什么强调原子性
> 这个"先停后启"的过程必须在数据库事务里完成。如果停用成功而激活失败，系统会落到"无活动 provider"状态，聊天直接不可用。用事务包住才能保证要么完整切换，要么完全回滚。

### 5. 与聊天模块 `LlmProviderRouter` 的联动

这是整个 Provider 设计的落点。聊天链路真正发起 LLM 调用前，会通过 `getActiveProvider(scope)` 取当前活动配置：

```java
// getActiveProvider 节选
List<ModelProviderConfig> configs =
    modelProviderConfigRepository.findByScopeAndIsActive(scope, true);
if (configs.isEmpty()) {
    throw new CustomException("未配置活动的 " + scope + " provider");
}
// 多个活动时取第一个（可扩展为负载均衡）
ModelProviderConfig config = configs.get(0);
return new ActiveProviderView(config.getModel(), config.getApiBaseUrl(), config.getApiKey());
```

因为 `LlmProviderRouter` 是在每次请求时按活动 provider 构建客户端的，管理员在后台 `activate` 一个新 provider 后，**下一次聊天请求就会自动走新模型，无需重启**。这就是"运行时切换"的本质：后台改的是数据库里的 `is_active` 标志，聊天侧每次都现查现用。`getActiveProvider` 返回列表时取第一个，也为后续做多活动 provider 的负载均衡留了扩展口。

> [!tip] 切换 Embedding 的隐藏代价
> 切 LLM 是无状态的，立刻生效即可。但切 Embedding provider 要当心：已入库文档的向量是用旧模型生成的，新模型维度或语义空间不同会导致检索失真，必要时需对历史文档**重新向量化**。详见 [[混合搜索与检索]]。

## 四、邀请码管理

邀请码用于控制谁能注册，是一种轻量的准入闸门。规则上是 **8 位大写字母 + 数字**，并支持配置**最大使用次数**和**过期时间**两个维度。

```
POST   /api/v1/admin/invite-codes        — 生成邀请码
GET    /api/v1/admin/invite-codes        — 查询所有邀请码
DELETE /api/v1/admin/invite-codes/{code} — 删除邀请码
```

生成时随机出码并查重，碰撞概率极低，重复就重生成：

```java
// generateCode 节选
String code = RandomStringUtils.randomAlphanumeric(8).toUpperCase();
while (inviteCodeRepository.existsByCode(code)) {
    code = RandomStringUtils.randomAlphanumeric(8).toUpperCase();
}
InviteCode inviteCode = new InviteCode();
inviteCode.setCode(code);
inviteCode.setMaxUses(maxUses);
inviteCode.setUsedCount(0);
inviteCode.setExpiresAt(expiresAt);
inviteCode.setCreatedAt(LocalDateTime.now());
return inviteCodeRepository.save(inviteCode);
```

注册时 `validateAndUse` 做三道校验——存在、未过期、未用满，通过后把 `usedCount` 加一：

```java
// validateAndUse 节选
InviteCode inviteCode = inviteCodeRepository.findByCode(code)
    .orElseThrow(() -> new CustomException("邀请码不存在"));
if (inviteCode.getExpiresAt() != null && inviteCode.getExpiresAt().isBefore(LocalDateTime.now())) {
    throw new CustomException("邀请码已过期");
}
if (inviteCode.getUsedCount() >= inviteCode.getMaxUses()) {
    throw new CustomException("邀请码已用完");
}
inviteCode.setUsedCount(inviteCode.getUsedCount() + 1);
inviteCodeRepository.save(inviteCode);
```

`maxUses` 设为 1 就是一次性邀请码，设大一些就是一码多人共享；`expiresAt` 控制时间窗。两个维度组合能覆盖"单人定向邀请"和"限时活动批量发码"等不同场景。

## 五、管理员账号引导（Bootstrap）

系统首次部署时数据库里没有任何管理员，会陷入"要管理员才能建管理员"的死锁。`AdminUserInitializer` 用应用启动事件破这个局：在 `ApplicationReadyEvent` 时，若 `ADMIN_BOOTSTRAP_ENABLED` 开启**且当前没有任何 `ROLE_ADMIN`**，就从 `.env` 读取用户名、密码、组织标签创建首个管理员。

```java
// onApplicationReady 节选
if (!adminBootstrapProperties.isEnabled()) {
    return;
}
long adminCount = userRepository.countByRole("ROLE_ADMIN");
if (adminCount > 0) {
    logger.info("管理员账号已存在，跳过引导创建");
    return;
}
User admin = new User();
admin.setUsername(adminBootstrapProperties.getUsername());
admin.setPassword(passwordEncoder.encode(adminBootstrapProperties.getPassword()));
admin.setRole("ROLE_ADMIN");
admin.setPrimaryOrgTag(adminBootstrapProperties.getPrimaryOrg());
admin.setCreatedAt(LocalDateTime.now());
userRepository.save(admin);
```

"已存在管理员则跳过"这层判断让引导**天然幂等**：重启再多次也不会重复建账号。密码也始终经 `passwordEncoder` 加密入库，不存明文。

> [!note] 用完即关
> 引导创建只为解决冷启动。账号建好后必须在 `.env` 里把 `ADMIN_BOOTSTRAP_ENABLED=false`，生产环境绝不长期开启——否则一旦管理员账号被全部删除，启动时又会用 `.env` 里的固定凭据自动重建，等于留了一道后门。

## 六、安全注意事项

| 事项 | 做法 |
| --- | --- |
| `apiKey` 落库 | 建议加密存储，日志中绝不打印 |
| `apiKey` 展示 | 前端脱敏，如 `sk-***abc` |
| 引导开关 | 创建成功后立即关闭，生产环境不长开 |
| 激活切换 | 用事务包住"先停后启"，杜绝无活动/多活动 |
| 邀请码强度 | 8 位查重已够用，对安全要求更高可加长 |

## 七、面试速答

- **运行时换模型不重启怎么做到的？** 把 provider 配置放数据库，聊天侧每次请求经 `getActiveProvider` 现查现用，后台 `activate` 改的是 `is_active` 标志，下一次请求即生效。
- **怎么保证任何时候都恰好一个活动 provider？** 创建时第一个自动激活补足"下限"，激活时先停同 scope 其他再启目标守住"上限"，整个激活过程放在事务里保证原子。
- **管理员从哪来？** 启动事件里检测无管理员且开关打开时，从 `.env` 引导创建一个，幂等且用完即关。
