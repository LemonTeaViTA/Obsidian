# 评测体系与性能基线

> 问题：你的 RAG 项目怎么证明改动是有效的？评测体系是怎么建的？系统能扛多少并发，瓶颈在哪？
> 本笔记分两部分：PART A 算法评测（数据集 / RAGAS / retrieval 指标 / 消融历史），PART B 性能基线（vLLM 压测 / 多层缓存）。管道实现见 [[RAG管道设计]]，检索细节见 [[混合搜索与检索]]。

> [!tip] 一句话定位
> 本项目最大的差异化**不是某个算法，而是评测闭环**。大多数 RAG 系统跑不出可对照的数据，是因为没建立离线评测 + 消融实验闭环。Baize 用 RAGAS 三指标 + retrieval-only 指标追踪每一次改动，每个组件都有消融数据，并在公开 benchmark（RAGBench）上对照业界水平，验证算法栈不依赖自造题虚高。

# PART A · 算法评测

## 一、评测数据集

三个数据集分工明确：自造集做主力基线，公开集做横向对照，早期对比集验证解析。

| 数据集 | 题数 | 类型 | 用途 |
|---|:---:|---|---|
| `comprehensive_qa.json` | 159 | 中文自造（基于 wiki + Java 技术文档） | 主力对照基线 |
| `ragbench_mixed.json` | 100 | 英文公开 benchmark（hotpotqa / finqa / tatqa / techqa / emanual） | 业界横向对照 |
| `diverse_eval.json` | 120 | 多列 PDF + 表格 | 早期解析对比 |

> [!note] 为什么要跑公开 benchmark
> 自造题容易"出题人即答题人"导致分数虚高。跑 RAGBench 100 题英文公开集，是为了验证整套算法栈（解析→分块→检索→生成）在没见过的题型上同样站得住，分数不是过拟合自造数据的产物。

## 二、指标体系

分两类：RAGAS 三指标依赖 LLM-as-judge 评生成质量，retrieval-only 指标不依赖 LLM 评召回质量。

### RAGAS 三指标（LLM-as-judge）

| 指标 | 量化的是什么 | 通俗解释 |
|---|---|---|
| **Faithfulness** | 答案拆成原子声明，每条声明能否在 retrieved contexts 里找到支撑 | 是否在编造（幻觉） |
| **AnswerRelevancy** | 答案与问题的语义相关性 | 是否答非所问 |
| **ContextPrecision** | retrieved chunks 跟 ground truth 的相关排名 | 召回精度（相关的有没有排前面） |

### Retrieval-only 指标（不依赖 LLM）

| 指标 | 量化的是什么 |
|---|---|
| **Recall@k** | top-k 里是否有相关 chunk |
| **MRR** | 第一个相关 chunk 的倒数排名 |
| **NDCG@k** | 考虑顺序的综合排名质量 |

> [!note] 相关性判定方法：Jaccard ≥ 0.3 OR substring containment ≥ 8 token
> retrieval 指标的难点是"什么算命中相关 chunk"。重新 chunking 后 gold passage 的边界跟当前切块不一定对齐，纯字符串相等会大量误判 false negative。所以判定标准放宽为：**Jaccard 相似度 ≥ 0.3 OR 子串连续匹配 ≥ 8 token**，任一满足即视为命中，解决了"边界不齐"导致的漏判。

## 四、改进 / 消融历史（核心差异化）

每一行都是一次真实改动 + 一次重跑评测，这张表就是"评测闭环"的产物。从 Tika-only 的 F=0.78 一路推到当前的 F=0.9261。

| 阶段 | F | AR | CP | 主要改动 |
|---|:---:|:---:|:---:|---|
| 原始（Tika only） | 0.78 | 0.40 | 0.21 | 基准 |
| +MinerU PDF 解析 | 0.91 | 0.44 | 0.20 | 双栏阅读顺序修复 |
| +Markdown 结构分片 | 0.93 | 0.47 | 0.21 | 表格 / 标题 / 列表感知 |
| +BGE-Reranker | 0.86 | 0.82 | 0.61 | top-20 候选 + 交叉编码器重排 |
| +查询改写（指代消解） | 0.92 | 0.87 | 0.90 | 多轮对话上下文还原 |
| +拒答 + 引用 + 置信度 | 0.93 | 0.87 | 0.91 | 生产保障机制 |
| +Token 预算 + 分层摘要 | 0.93 | 0.87 | 0.91 | 对话长度控制 |
| +RRF 融合 + Window | 0.93 | 0.87 | 0.91 | 检索管道升级 |
| +元数据预过滤 API | 0.91 | 0.87 | 0.91 | 索引信号扩展 |
| +章节前缀（textContent 污染版） | 0.93 | 0.87 | 0.91 | 章节信号注入向量空间 |
| +双索引（仅 sectionPath 干净版） | **0.9326** | 0.8752 | **0.9089** | 数值最优 |
| **+双索引（含 ctxSummary 干净版，当前）** | **0.9261** | 0.8735 | 0.8850 | 架构最干净 |
| +URL 噪声清洗 + retrieval 指标 | — | — | — | techqa Recall +0.60 |

> [!note] 几个关键拐点的解读
> - **+BGE-Reranker**：CP 从 0.21 → 0.61 是质变。reranker logit 区分度比所有 embedding 高一个数量级（12.42 vs 0.27），是 ContextPrecision 的关键贡献者。
> - **+查询改写**：CP 从 0.61 → 0.90，多轮指代消解让"它的等待期"这类短句还原成具体实体后才能召回。
> - **双索引最后一步 F 反而从 0.9326 微降到 0.9261**：这是**主动权衡**——把 ctxSummary 从 textContent 挪到 contentEnhanced，LLM 看到的是干净原文不被自己的转述污染，数值略降但架构长期更可控。详见 [[RAG管道设计]]。

# PART B · 性能基线

> [!warning] ADR-202 的性能目标已部分过期
> 决策文档 `docs/decisions/202-performance-testing.md` 是 2024-12 立项时写的，里面的目标值（聊天 50 QPS / 搜索 100 QPS）是**预期值，不是实测**，已被 2026-05 标记为"部分过期"。
> - 文档目标：聊天场景 **50 QPS**
> - 实测结果：vLLM（Qwen3.5-9B 单实例）在 **~15 并发**时 P99 延迟即开始劣化
> 50 QPS 与 ~15 并发之间差了一个量级。ADR-202 的方法论部分（测试场景设计、瓶颈识别框架）仍可参考，**但目标值不再有效，以实测数据为准**。

## 五、vLLM 部署压测

对 Qwen3 系列在 RTX 4090D × 8 上压测，测了 5 种部署方案。硬件分配：GPU 0（MinerU）、GPU 4（Embedding + Reranker），其余给 LLM。

### 直接 API 压测对比（100 并发）

| 配置 | GPU 数 | 上下文 | 100 并发 P95 | QPS 峰值 |
|---|:---:|:---:|:---:|:---:|
| TP=2 | 2 | 16K | 22.3s | 4.46 |
| TP=4 | 4 | 32K | 17.6s | 4.68 |
| TP=4 + TP=2 LB | 6 | 混合 | 18.3s | 4.22 |
| **3×TP2 LB** | **6** | **16K** | **12.4s** | **6.66** |
| TP=4 + TP=1 LB | 5 | 混合 | 49.0s | 1.83 |

> [!tip] 3×TP2 是高并发最优解
> 6 卡跑 3 个 TP=2 实例做负载均衡，QPS 峰值 6.66、P95 12.4s，明显优于单个 TP=4。两条工程经验：
> - **4090D 无 NVLink，TP=4 是单实例的实际上限**，再往上扩张靠多实例而非更大 TP。
> - **同构多实例 > 异构多实例**：绝对不要混合不同 TP 的实例做负载均衡（木桶效应，TP=4+TP=1 直接掉到 1.83 QPS）。

### 全链路 WebSocket 压测（真实用户体验）

直接 API 压的是 GPU，全链路压的才是用户真实感受到的延迟（含检索 + reranker + LLM）。

| 并发 | 成功率 | P95 |
|---|:---:|:---:|
| 5 | 100% | 17.2s |
| 10 | 100% | 22.2s |
| 15 | 100% | 27–29s |
| 20 | 75% | 超时 |

> [!warning] 真实上限是 15 并发，瓶颈是整条 RAG 管线而非单纯 GPU
> 20 并发时成功率掉到 75% 开始超时，所以**全链路实际上限定为 15 并发**。关键在于：直接打 vLLM 能到 100 并发量级，但叠加完整 RAG 管线（混合检索 + Reranker HTTP 同步阻塞 + ES 连接池）后上限骤降——瓶颈是**整条管线**，不是 GPU 一个点。这也是 ADR-202 的 50 QPS 目标对不上的根本原因。
> 文件上传不抢聊天资源（Kafka 异步解耦，上传 50 并发 P95=980ms）。适合规模：20–30 人团队日常使用，同时聊天 3–5 人体验流畅。

当前生产配置：TP=4（GPU 2,3,5,6），32K 上下文。若 GPU 1 长期可用，可切换到 3×TP2（GPU 1+2 / 3+5 / 6+7）提升高并发性能。

## 六、多层缓存优化

全链路 P95=27s 的优化方向是多层缓存，减少重复计算。已实施前两层，第三层在规划中。

| 层级 | 缓存内容 | 存储 / Key | TTL | 收益 / 状态 |
|---|---|---|:---:|---|
| 阶段一 | Embedding 向量 | Redis `emb:v:{SHA256(text+modelVersion)}` | **24h** | 节省 0.3–0.5s/次 + 省 token，已上线 |
| 阶段二 | Query Rewrite 改写结果 | Redis `qr:{SHA256(userMessage)}` | **12h** | 相同问题跳过 LLM 改写，节省 1–3s，已上线 |
| 阶段三 | 语义缓存（整答案） | ES 索引 `semantic_cache`（kNN + 权限过滤） | 规划中 | 见下 |
| 阶段四 | 搜索结果缓存（可选） | Redis `search:result:{...}` | 30min | 跳过 ES + Reranker，节省 1–2s |

> [!note] 阶段三语义缓存（下一步重点）
> 相似问题直接返回缓存的 LLM 回答，跳过整个 RAG 管线（搜索 + Reranker + LLM）。设计要点：
> - **相似度阈值 cosine ≥ 0.92**，命中时模拟流式返回（每 30ms 一个 chunk）。
> - 存 ES 单独索引天然支持 kNN + 权限隔离（filter by userId OR orgTags），不会跨租户泄露。
> - 失效：文档删除 / 重索引时按 sourceFileMd5s `deleteByQuery`。
> - 预期 30% 命中率 → 等效并发降至 ~10，P95 < 20s。这是把"15 并发上限"往上拉的最有杠杆的一步。

> [!tip] Embedding / Query Rewrite 缓存的失效设计
> - Embedding cache 的 key 含 `modelVersion`，**模型切换自动失效**，不会读到旧模型的向量。
> - Query Rewrite cache 的 key 含 `conversationId`，**防止跨会话上下文串味**；改写结果与原文相同时不缓存（无意义）。
> 两者都有配置开关（`EMBEDDING_CACHE_ENABLED` / `QUERY_REWRITE_CACHE_ENABLED`，默认开启）。
