## 一、两张指标表（地基，背死）

### 1. 检索指标（retrieval-only，不依赖 LLM，调参时用）

| 指标 | 衡量什么 | 关键点 |
|---|---|---|
| **Recall@k** | 该找的相关 chunk，前 k 里找回多少 | 怕**漏**。Recall@5=0.35 → 仅 35% 的问题相关 chunk 进了 top-5 |
| **Precision** | 召回的 top-k 里，有多少是相关的 | 怕**脏** |
| **MRR** | 第一个相关结果排多前 | **排名取倒数**：排1=1.0，排2=0.5，排3=0.33 |
| **NDCG@k** | 整体排序质量 | **看位置**，相关的排越前得分越高（Recall 只看在不在前 k，NDCG 看排第几） |

### 2. RAGAS 指标（生成质量，靠 LLM 评判）

| 指标 | 管哪端 | 衡量什么 | 怎么算 / 低了怎么修 |
|---|---|---|---|
| **ContextPrecision** | **检索** | 相关 chunk 有没有排前面 | 低 → 上 **Reranker** / 改召回 |
| **Faithfulness** | **生成** | 答案有没有瞎编 | 拆原子声明，逐条查 context 有无支撑；低 → 调 prompt / 拒答 / 降温 |
| **AnswerRelevancy** | **生成** | 答案切不切题（答非所问） | 由答案反推问题，比对与原问题语义相似度；低 → 改 prompt / 查询改写 |

> [!tip] 口诀
> **检索 4 指标**：Recall 怕漏、Precision 怕脏、MRR 看第一发、NDCG 看排序。
> **RAGAS 3 指标**：带 **Context** 的管检索，带 **Faith / Answer** 的管生成。

### 诊断逻辑（会用指标定位问题，加分）
- **Faith 高 + CP 低** → 检索的锅（LLM 老实，但喂的 context 排序差）→ 上 **Reranker**
- **Faith 低 + CP 高** → 生成的锅（检索准，但 LLM 瞎编）→ 调 prompt / 拒答

## 二、招牌数据（讲成果时甩，必背）

| 场景 | 数据 | 记忆 |
|---|---|---|
| 整体检索三件套 | **NDCG@5 0.81 / Recall@5 0.97 / MRR 0.92**（hotpotqa NDCG 0.94） | **N8 R9·7 M9·2**；Recall>MRR |
| 双索引改造 | **Faithfulness 0.91 → 0.93**（召回不降） | 涨 2 个点 |
| URL 碎片清洗 | 该类文档 **Recall@5 0.35 → 0.95**，整体 **NDCG +0.18** | 三五到九五（最戏剧） |

> "整体做到 **NDCG@5 0.81、Recall@5 0.97、MRR 0.92**。这是一步步优化来的：加 **Reranker** 把 ContextPrecision 从 **0.21 拉到 0.61**（最关键一跳）；做**双索引**让 Faithfulness 从 **0.91 回到 0.93**；清洗 **URL 碎片**让技术文档子集 Recall 从 **0.35 飙到 0.95**。"

## 三、核心讲法题（对照简历 bullet）

### Q1. 为什么 RRF 而不是加权融合？k=60 怎么定？（简历 42 行）
- **RRF 原因**：BM25 分数 0–30、向量 cosine 0–1，**尺度差几十倍**，直接相加被 BM25 主导；归一化又因不同查询分布不同而不稳定。RRF **只看排名不看绝对分数**，公式 `score = Σ 1/(k+rank)`，两路排名分天然同尺度，鲁棒。
- **k=60**：验证集上网格搜索 k=30/60/90，用 **NDCG@5 和 MRR**（retrieval-only、不依赖 LLM、可复现）；k=60 最优。k 小→头部过度集中，误召一个就伤；k 大→尾部噪声混入。
- **接 reranker**：RRF 召回 **20 个候选 → reranker 精排 → top-5** 给 LLM。

### Q2. Reranker 是干什么的？为什么需要？（简历 42/44 行）
- **双塔（bi-encoder，embedding）**：query 和 chunk **各自编码**算 cosine，快、可离线预计算、扛百万级，但**交互少、精度有限** → 负责**第一阶段宽召回**。
- **交叉（cross-encoder，BGE-reranker-v2-m3，port 8767）**：query+chunk **拼一起过模型**，全 attention 细粒度交互、准，但**每对都要现算、贵** → 只能在**小候选集（20）上精排**。
- **不重复，是分工**：双塔快但糙、交叉准但慢，两阶段各干各擅长的。数据：CP **0.21→0.61**，reranker logit 区分度比 embedding 高一个数量级（约 12.4 vs 0.27）。

### Q3. 双索引架构（简历 42/63 行）
- **textContent**：干净原文，**只给 LLM 生成读**。
- **contentEnhanced**：`[sectionPath] + ctxSummary + 原文`，**向量和 BM25 召回都基于它**。
- ctxSummary 是 LLM 在**文档入库时**生成并存下（chunk 固有属性，不随 query 变，避免查询时重复算）。
- **核心痛点 = Faithfulness**：之前把 ctxSummary 也给 LLM 看，LLM 复述这些二手转述被 RAGAS 判 **unsupported**，Faithfulness 掉；改成**生成侧只读干净原文**后，**0.91→0.93，召回不降**。
- **借鉴 Anthropic Contextual Retrieval**：分块让 chunk 脱离上下文（"营收增长 3%"不知哪个公司哪年 → 召回不到），补章节+摘要让 chunk **自包含**。

### Q4. 拒答机制 + 置信度（简历 46 行：低相关性拒答）
- **拒答信号**：取 **reranker 最高分 maxScore**，低于阈值（MIN_ACCEPTANCE_SCORE）或没召回到内容 → 直接返回拒答语，**不调 LLM**。
- **置信度（≠拒答）**：答了之后标 high/medium/low，由 **maxScore + 引用数量**双因素定（maxScore≥2.0 且引用≥2→high；≥0 且引用≥1→medium；否则 low）。
- **为什么不让 LLM 硬答**：企业知识库问的是公司专有信息，检索不到却用预训练知识硬答 = **编造/张冠李戴**，是事故。**底线：宁缺毋滥。**

### Q5. URL 碎片清洗（简历 64 行）—— 用三段式
1. **怎么发现**：RAGBench **techqa 子集** Recall@5 只有 0.35，明显低于其它子集 → 做**失败案例分析**，把召回失败 query 的 top-5 **dump 出来看**。
2. **根因机制**：发现 top 位的 chunk 正文全是 `[http://www.ibm.com/...]` URL 引用碎片（HTML→Markdown 残留）。危害两层：**① 挤占 chunk 正文**把答案文字挤出去；**② 污染检索信号**，全 URL 的 chunk 反而排 top-1，把真相关 chunk 挤出 top-5。**不是答案不在库里，是被噪声压下去了。**
3. **解决+数据**：加 4 条正则清洗 → techqa **Recall@5 0.35→0.95，整体 NDCG +0.18**。启示：**RAG 瓶颈常在数据质量，不在模型。**

### Q6. Jaccard + substring 双判定（简历 65 行）
- **问题**：改分块策略后，按旧分块标的 gold passage 与新 chunk 边界对不齐；精确匹配会把"含答案但不完全相等"的 chunk 误判没召回 → **recall 假性低估**。
- **为什么不重标**：消融实验分块频繁变，每次重标 159+100 题成本爆炸 → 用模糊匹配让**评测与分块解耦**，gold 只标一次。
- **两个判定（OR，任一命中即算召回）**：
  - **Jaccard ≥ 0.3**：token 集合重叠比 → 抓两 chunk 部分重叠
  - **substring containment ≥ 8 token**：含连续 ≥8 token 子串 → 抓小 gold 被塞进大 chunk（此时 Jaccard 会偏低，靠 substring 补）
  - **互补**：覆盖不同的边界错位模式。

### Q7. 流式 / thinking-content / 模型降级（简历 43 行）
- **为什么流式（SSE）**：降低**首字延迟（time-to-first-token）**——完整答案要 5–8s，流式让用户 1s 内看到首字；长连接一次性返回还有超时断连风险。
- **thinking/content 双流**：Qwen3 带 thinking。vLLM 加 `--reasoning-parser qwen3`，SSE delta 分 `reasoning_content`（思考过程，前端折叠框）和 `content`（正式答案）。thinking 也是 Qwen3 死循环根源。
- **模型降级**：`LlmProviderRouter` 抽象 + `ModelProviderConfigService` 管 active provider；主模型超时/报错抛异常 → **故障转移到备用 provider**（如主 vLLM、备 DeepSeek API）。

---

### Q8. 三段式门控触发条件（简历 46 行）
- 用 **maxScore**（reranker 给所有候选打分里的**最高分**）跟阈值比，分三档：
  - `maxScore < 0.3` → **低相关性：拒答**（不调 LLM）
  - `0.3 ≤ maxScore < 0.6` → **中等：关 thinking 直接答**
  - `maxScore ≥ 0.6` → **高相关性：开 thinking**（但当前 thinking 硬编码 false 保底）

### Q9. LLM 死循环（简历 60 行：高并发 LLM 死循环）
- **根因**：低相关性 RAG 结果 + 复杂 system prompt + thinking 模式 → 模型进入**无限推理循环**，`reasoning_content` 一直涨、`content` 永不输出。
- **解法**：① 三段式门控（低相关直接拒答，不喂复杂 context）；② `presence_penalty=1.5` 防重复；③ 当前 `enable_thinking` 硬编码 false 保底。超时兜底只是补救，不是根本解。

### Q10. 检索退化 / 高并发（简历 60 行：高并发检索退化）
- **现象**：全链路实测 5/10/15 并发成功率 100%，**20 并发降到 75%**、超时。
- **瓶颈不是 vLLM，是整条 RAG 管线**：reranker（HTTP 同步阻塞）+ ES 连接池 + vLLM KV cache 同时打满。
- **解决措施（多层缓存 + 部署调优）**：
  - Embedding 缓存（Redis，TTL 24h，省 0.3–0.5s）
  - Query Rewrite 缓存（TTL 12h，省 1–3s）
  - 语义缓存（**规划中**，cosine≥0.92 命中直接返答案、跳过整条管线，预期 30% 命中→等效并发降到 ~10）
  - vLLM 部署：TP=4 单实例 / 同构多实例，**不混合异构**（木桶效应）
- **诚实话术**：稳定上限 **15 并发**（够 20–30 人团队）；**没彻底解决**，reranker 同步阻塞根因还在，下一步靠语义缓存。承认边界比说"解决了"更可信。

## 四、面试避坑提醒（我犯过的）
- ❌ 数据集叫 **RAGBench**（五领域：hotpotqa/finqa/tatqa/techqa/emanual）+ 自建中文 159 题，别答"忘了"。
- ❌ "检索不到 LLM 也能用已学知识回答" → 企业场景这是**幻觉事故**，应**拒答**。
- ❌ "双索引是给 LLM 更多信息" → 反了，**给 LLM 更干净（只读原文）**，给召回端更多信号。
- ❌ 双索引招牌指标是 **Faithfulness 0.91→0.93**，不是 recall。
- ❌ **NDCG@5 = 0.81**（别说成 0.82）；Recall@5 0.97 > MRR 0.92。
- ❌ 答对了又撤回（如模型降级"我没了解过"）→ **先把想到的说出来**。
- ❌ 只说结论不说过程 → 任何 bullet 都套「发现→机制→解决+数据」。
- ❌ 被问"解决了吗"别吹"解决了" → 说"缓解到满足业务规模，根因仍在，下一步…"。
- ✅ 主动讲"双塔 vs 交叉、两阶段取舍"是加分项。

## 五、vLLM 部署调优（高并发场景必讲）

### 硬件背景：RTX 4090D × 8（无 NVLink，卡间走 PCIe）

**Qwen3.5-9B 模型权重约 18GB(BF16)**，加 KV cache 必须多卡 TP 分摊。

### 4090D 五方案对比压测（100 并发直接 API）

| 配置 | GPU 数 | P95 | QPS |
|---|---|---|---|
| TP=2 | 2 | 22.3s | 4.46 |
| TP=4 | 4 | 17.6s | 4.68 |
| TP=4 + TP=2 混合 LB | 6 | 18.3s | 4.22 |
| **3×TP2 同构 LB** | **6** | **12.4s** | **6.66** ← 高并发最优 |
| TP=4 + TP=1 混合 LB | 5 | 49.0s | 1.83 ← 最差 |

### 三条核心结论（这才是调优方法论）
1. **TP=4 是单实例甜点**：4090D 无 NVLink，TP 越大 PCIe 通信开销越高，TP=4 是收益/代价平衡点。
2. **同构多实例 > 异构混合**：3×TP2 高并发最优；TP=4+TP=1 混合最差（**木桶效应**被最慢实例拖垮）。**绝不要混合不同 TP 做 LB。**
3. **低延迟 vs 高并发分场景**：低延迟选 TP=4（32K 上下文）；高并发选 3×TP2（6 卡三实例）。

### 全链路 WebSocket 压测（真实用户体验）

| 并发 | 成功率 | P95 |
|---|---|---|
| 5 / 10 / 15 | 100% | 17 → 29s |
| 20 | 75% | 超时 |

→ 稳定上限 **15 并发**，**真正瓶颈不是 vLLM，是 reranker 同步阻塞 + ES 连接池**。

### B200 换卡推算（基于规格推算，面试如实说是估算）

| 维度 | 4090D TP=4 | B200 单卡 |
|---|---|---|
| 显存 | 4×24GB=96GB | 180GB |
| 模型装法 | TP=4 分 4 卡 | **TP=1 单卡**（18GB 模型+162GB KV cache） |
| 卡间通信 | PCIe（有损耗） | **无**（单卡） |
| TTFT 估算 | 5–8s | **2–4s**（无通信开销+大 KV cache） |
| 并发上限估算 | ~15（全链路） | **30–50+**（但届时 reranker 成新瓶颈） |
| NVLink（TP=2 扩展） | 无，PCIe 效率低 | NVLink 5.0，扩展效率远高 |

> **换卡后注意**：vLLM 不再是瓶颈，**reranker 同步阻塞会暴露为新主要瓶颈**，需同步改为异步/批处理。

### 话术（面试讲性能调优）
> "我们在8×4090D 上压测了 5 种 vLLM 部署方案，因为 4090D 无 NVLink，TP=4 是单实例甜点，高并发下 3×TP2 同构多实例最优(QPS 6.66)。混合异构最差——木桶效应。全链路发现真正瓶颈是 reranker 同步阻塞，配合多层缓存后稳定支撑 15 并发。如果换 B200，单卡 180GB 直接 TP=1 跑 9B 模型，TTFT 预计降到 2–4s，并发能力大幅提升，但届时 reranker 会成新瓶颈。"

### Q12. 离线评测 vs 线上真实效果的差距（场外高频题）
> 考点：你有没有真的面对过线上数据，不只是刷测试集分数。

**三个主要差距**：

1. **查询分布不同（最常见）**
   - 测试集：精心构造的完整句子
   - 真实用户：口语化、省略主语、有指代词（"那它的续保条件呢"）、打错字
   - 这是项目里做**查询改写/指代消解**的真实动机——测试集里指代词少，线上比例高得多

2. **并发问题，离线根本测不出来**
   - 测试集串行跑，根本暴露不了高并发场景
   - 内测才发现：20 并发 P95 超时（成功率 75%）、LLM 死循环在特定低相关 query + 并发时才触发

3. **边界 query：知识库覆盖外 + 复合问题 + 闲聊**
   - 用户会问知识库完全没有的内容 → 考验拒答机制
   - "你好啊" 这类闲聊 → 意图路由要能识别跳过检索

**话术（直接背）**：
> "离线和线上最大的差距有两块：一是**查询分布**——测试集是完整句子，真实用户口语化、有指代词，所以我们做了查询改写；二是**并发问题**——测试集串行跑发现不了，内测才发现 20 并发超时和 LLM 死循环。这也是简历里写'发现并解决高并发下的检索退化'的来源——离线根本暴露不了。"
