# 系统架构总览

> 问题：用 5 分钟讲清楚 Baize 是个什么系统？整体架构怎么分层？为什么选 Kafka / ES / Redis / MinIO 这套组合？
> 理论基础：[[LLM/RAG基础与架构|RAG基础与架构]]（RAG 是整个系统的核心范式）
> 本笔记是整个 Baize 项目的入口总览，每个业务域都有独立深挖笔记，文末有完整索引。

> [!tip] 一句话定位
> SmartPAI / Baize 是一个**基于 RAG（检索增强生成）的企业级 AI 知识库系统**：用户上传文档 → 解析向量化入库 → 通过混合搜索召回 → LLM 流式问答。采用**微服务架构思想 + 消息队列异步解耦**，核心难点不在单点算法，而在把解析、检索、生成、权限、配额这几条链路工程化串起来并保证多租户隔离。

---

## 一、整体架构

系统是一个 Spring Boot 单体后端，但内部按业务域清晰分层，并通过 Kafka 把重负载的文件处理链路异步解耦出去。

```
┌─────────────┐
│   前端 Vue3  │
└──────┬──────┘
       │ HTTP / WebSocket
       ↓
┌─────────────────────────────────────────────────────────┐
│                    Spring Boot 后端                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌─────────┐   │
│  │Controller│→ │ Service  │→ │Repository│→ │ MySQL   │   │
│  └──────────┘  └──────────┘  └──────────┘  └─────────┘   │
│                      ↓                                    │
│              ┌───────┴───────┐                            │
│              ↓               ↓                            │
│         ┌────────┐      ┌────────┐                        │
│         │ Redis  │      │ Kafka  │                        │
│         │ (缓存) │      │ (异步) │                         │
│         └────────┘      └───┬────┘                        │
│                             ↓                             │
│                    ┌─────────────────┐                    │
│                    │ FileProcessing   │                   │
│                    │ Consumer         │                   │
│                    └────┬────────┬────┘                   │
│                         ↓        ↓                        │
│                    ┌────────┐ ┌──────────────┐            │
│                    │ MinIO  │ │ Elasticsearch │           │
│                    │ (文件) │ │ (搜索+向量)   │            │
│                    └────────┘ └──────────────┘            │
└─────────────────────────────────────────────────────────┘
                              ↓
                    ┌──────────────────┐
                    │   外部 AI 服务    │
                    │ vLLM / DeepSeek   │
                    │ Embedding API     │
                    └──────────────────┘
```

> [!note] 分层职责
> - **Controller**：9 个 REST + WebSocket 端点，只做参数校验与鉴权入口
> - **Service**：28 个业务服务，承载核心逻辑
> - **Repository**：18 个数据访问层（JPA + Redis）
> - **Consumer**：Kafka 消费者，承接异步文件处理
> 同步链路（聊天、检索、鉴权）走 Controller→Service；重负载链路（文件解析、向量化）通过 Kafka 推给 Consumer，避免阻塞 HTTP 主线程。

## 二、七大业务域

整个系统按职责切成 7 个业务域，每个域有独立的深挖笔记。

| # | 业务域 | 职责 | 关键类 | 深挖笔记 |
|---|---|---|---|---|
| 1 | 认证与权限 | 注册登录、JWT 验证、角色控制、组织标签过滤 | `SecurityConfig` / `JwtAuthenticationFilter` / `OrgTagAuthorizationFilter` / `UserService` | [[用户管理与权限]] |
| 2 | 文件上传处理 | 分片上传、合并、MinIO 存储、Kafka 异步解析、向量化、ES 索引 | `UploadService` / `FileProcessingConsumer` / `ParseService` / `VectorizationService` | [[文件上传机制]] |
| 3 | 聊天与 LLM | WebSocket 连接、消息处理、上下文构建、LLM 流式调用、响应解析 | `ChatWebSocketHandler` / `ChatHandler` / `LlmProviderRouter` / `DeepSeekClient` | [[聊天助手模块]] |
| 4 | 检索 | 混合搜索（BM25 + 向量）、权限过滤、embedding 生成 | `HybridSearchService` / `EmbeddingClient` / `EsConfig` | [[混合搜索与检索]] |
| 5 | 配额与限流 | LLM/Embedding token 预算、固定窗口限流、余额管理 | `UsageQuotaService` / `RateLimitService` / `UsageBalanceService` | [[配额与限流]] |
| 6 | 充值支付 | 充值包、订单创建、微信支付回调、余额充值 | `RechargeService` / `WxPayService` / `RechargeOrder` | [[支付与充值]] |
| 7 | 管理后台 | 用户管理、系统状态、使用仪表盘、邀请码、模型配置 | `AdminController` / `ModelProviderConfigService` / `InviteCodeService` | [[管理后台]] |

### 两条主链路

整个系统的价值都跑在两条链路上，其余业务域是支撑。

**文件处理链路（离线入库，异步）**：
```
UploadController → UploadService (MinIO) → Kafka → FileProcessingConsumer
  → ParseService (解析) → VectorizationService (向量化) → ElasticsearchService (索引)
```

**聊天链路（在线问答，同步流式）**：
```
ChatWebSocketHandler (JWT 验证) → ChatHandler.processMessage()
  → HybridSearchService (检索) → ChatHandler.buildContext() (三段式门控)
  → LlmProviderRouter.streamResponse() → DeepSeekClient (流式)
  → processChunk() (解析 reasoning/content) → WebSocket 返回
```

> [!tip] 为什么文件处理要异步、聊天要同步
> 文件解析+向量化是分钟级的重任务，HTTP 长连接会超时、占线程，所以丢给 Kafka 异步消费；聊天问答需要逐字回显，天然适合 WebSocket 双向流式。两条链路的同步/异步取舍正好相反，是面试常被追问的设计点。

## 三、技术栈与选型理由

| 层 | 技术 | 版本 |
|---|---|---|
| 后端框架 | Spring Boot / Java / Maven | 3.4.2 / Java 17 |
| 主库 | MySQL | 8.0 |
| 缓存 / 会话 | Redis | 7.0 |
| 消息队列 | Kafka | 3.2.1 |
| 搜索引擎 | Elasticsearch（文本 + 向量混合） | 8.10.0 |
| 对象存储 | MinIO | 8.5.12 |
| 主 LLM | vLLM 部署 Qwen3.5-9B（port 3598）/ DeepSeek API | — |

每个组件的"为什么选它、不选什么"是面试核心，列成对照表：

| 技术 | 选型理由 | 被替代方案 |
|---|---|---|
| **Kafka** | 异步解耦文件处理，避免 HTTP 长连接超时；支持重试和死信队列 | 线程池异步（重启丢任务）、同步处理（超时） |
| **Elasticsearch** | 一个引擎同时支持 BM25 文本搜索和向量 kNN 搜索，避免双系统 | Milvus（纯向量）+ MySQL（文本），架构复杂 |
| **Redis** | 对话历史需要快速读写，MySQL 性能不足；支持 TTL 自动过期 | MySQL（慢）、纯内存（重启丢失） |
| **MinIO** | 开源对象存储，兼容 S3 API，本地部署成本低 | 阿里云 OSS（成本高）、本地文件系统（扩展性差） |
| **WebSocket** | 聊天需要双向实时通信 | SSE（单向）、轮询（低效） |
| **JWT** | 无状态认证，适合分布式部署；支持自动刷新 | Session（有状态，需共享存储） |

> [!warning] 选型不是越多越好
> 这套组合最值得讲的是"用一个 ES 同时扛 BM25 + 向量"——如果上 Milvus 就要额外维护一套向量库 + 一套全文检索，运维和数据一致性成本陡增。选型理由要落到具体 tradeoff，不要罗列技术名词。LLM 选型（Embedding / Reranker / 主模型）详见 [[模型选型]]。

## 四、跨域关注点（Cross-cutting Concerns）

业务域之间横切的四类关注点，是系统工程化质量的体现。

### 多租户隔离

- **组织标签（orgTag）**：每个文档、用户都带 orgTag
- **层级关系**：数据库 `parentTag` 字段维护父子关系，子标签可访问父标签资源
- **双重过滤**：`OrgTagAuthorizationFilter`（请求入口）+ `HybridSearchService.searchWithPermission()`（检索时 ES `filter` 子句）

> [!warning] 权限绝不能绕过
> 直接查 ES 会泄露跨组织数据。检索必须经过 `searchWithPermission()`，它把 `userId == 本人 OR public == true OR orgTag IN 用户有效标签`叠加成 ES filter 子句。这是多租户系统的红线，详见 [[用户管理与权限]]。

### 异常处理

- **全局异常处理器**：`GlobalExceptionHandler.java`
- **自定义异常**：`CustomException` / `RateLimitExceededException` / `InsufficientBalanceException`
- **Kafka DLT**：消费失败重试 3 次后进入 `file-processing-dlt` 死信队列，不阻塞后续消息

### 日志与监控

- **框架**：SLF4J + Logback
- **关键日志点**：`ChatHandler`（每条消息流程）、`FileProcessingConsumer`（文件任务）、`LlmProviderRouter`（LLM 调用与 token 统计）、`HybridSearchService`（搜索与权限过滤）

### 性能优化

- **Redis 缓存**：对话历史、组织标签、JWT token、PDF 预览
- **ES 批量索引**：`ElasticsearchService.bulkIndex()` 批量写入
- **连接池**：数据库 / Redis / ES / WebClient 全部走连接池
- **异步处理**：Kafka 解耦文件处理，主线程不阻塞

## 五、部署架构

### 本地开发

```bash
# 1. 启动依赖服务（MySQL/Redis/Kafka/ES/MinIO）
docker-compose -f docs/docker-compose.yaml up -d

# 2. 启动 vLLM（Qwen3.5-9B）
cd Qwen3.5-9B && ./start_llm.sh

# 3. 启动后端
mvn spring-boot:run
```

### 生产部署

| 组件 | 高可用方案 |
|---|---|
| 容器化 | Docker + Docker Compose |
| 反向代理 | Nginx（`docs/nginx.conf`） |
| 数据库 | MySQL 主从复制 |
| 缓存 | Redis Sentinel |
| 消息队列 | Kafka 集群（3 节点） |
| 搜索引擎 | Elasticsearch 集群（3 节点） |

大规模文档场景下的扩展思路详见 [[百万级扩展方案]]。
