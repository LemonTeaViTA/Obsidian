# 配额与限流

> 问题：用户调一次 LLM 到底消耗多少 token 是流式响应结束后才知道的，那你怎么保证用户不会"先把钱花超、扣的时候才发现余额是负的"？为什么用"预扣-结算"而不是"用完再扣"？
> 理论基础：[[Redis 基础]]

配额与限流是 Baize 的两道闸门：**配额**管"花了多少 token、够不够扣"，**限流**管"单位时间内能调几次"。两者都重度依赖 Redis，前者用它存预扣台账，后者用它做原子计数器。核心类是 `UsageQuotaService`（reserve / settle / abort）和 `RateLimitService`（固定窗口）。

---

## 一、Reserve-Settle 预扣结算机制

这是这篇文档最值钱的面试点。LLM 调用有个天然麻烦：**实际消耗的 token 数要等流式响应彻底结束才能算出来**（completion 长度不可预知）。如果"用完再扣"，会出两个问题。

> [!warning] deduct-after（用完再扣）的两个坑
> 1. **超支**：用户余额只剩 100 token，发起一次可能生成 5000 token 的请求。等响应结束才扣，账户直接变成 -4900。钱已经花出去了，扣不回来。
> 2. **并发竞态**：同一用户同时发起 3 个请求，每个都"先查余额够、再生成、最后扣"。三个请求都在生成阶段看到的是同一个旧余额，结果三笔一起扣，余额被扣穿。

所以 Baize 采用 **reserve → settle / abort** 三段式，把"扣"提前到调用前，把"退"放到调用后。

### 三个动作

| 动作 | 方法 | 时机 | 做什么 |
|---|---|---|---|
| Reserve 预扣 | `reserveLlmTokens()` | LLM 调用**前** | 按 `估算prompt + maxCompletion` 预扣，写预扣台账 |
| Settle 结算 | `settleReservation()` | 响应**正常结束** | 算差额，把"预扣 - 实际"多扣的退回 |
| Abort 回滚 | `abortReservation()` | 调用**异常** | 全额退还预扣，当作没花过 |

> [!tip] 为什么这样设计：把不确定性变成"先扣上限，再退多余"
> 预扣的金额是 `estimatedPromptTokens + maxCompletionTokens`——用**生成上限**（maxCompletionTokens）当预扣额。这等于先按"最坏情况"把钱锁住，余额不够就当场 `InsufficientBalanceException` 拒绝，根本进不到 LLM 调用。
> 真实消耗几乎总是小于上限，所以 settle 阶段几乎总是"退钱"而不是"补扣"。这样就把"事后可能扣穿"的风险，转化成了"事前锁定上限、事后退多余"的安全模型。并发竞态也一并解决：扣是在调用前一次性原子完成的，三个并发请求会各自先扣各自的预扣额，第三个发现余额不够就被挡住，不会都看到旧余额。

### 调用链

```
LlmProviderRouter.streamResponse() 开始
  → estimateChatTokens(messages)        估算 prompt tokens
  → RateLimitService.checkChatByUser()  先过限流闸门
  → reserveLlmTokens()                  检查余额 → 预扣 → 返回 TokenReservationBundle(reservationId)
  → [LLM 流式响应]  StreamUsageTracker 累加实际 tokens
  → 正常结束: settleReservation(reservation, actualTokens)  退差额 + 落消费记录
  → 异常:     abortReservation(reservation)                 全额退还
```

### reserve：预扣

预扣额取 prompt 估算值加生成上限，余额不足直接抛异常，绝不静默放行。预扣信息写进 Redis（TTL 10 分钟），key 为 `reservation:{reservationId}`。

```java
// UsageQuotaService.reserveLlmTokens(userId, estimatedPromptTokens, maxCompletionTokens)
int estimatedTotalTokens = estimatedPromptTokens + maxCompletionTokens;

UsageBalance balance = usageBalanceService.getBalance(userId);
if (balance.getBalance() < estimatedTotalTokens) {
    throw new InsufficientBalanceException("余额不足");   // 进不到 LLM 调用
}

String reservationId = UUID.randomUUID().toString();
usageBalanceService.deduct(userId, estimatedTotalTokens, "LLM预扣-" + reservationId);

// 预扣台账写 Redis，TTL 10 分钟
redisTemplate.opsForValue().set("reservation:" + reservationId, bundle, 10, TimeUnit.MINUTES);
return bundle;   // TokenReservationBundle
```

### settle：结算退差额

```java
// settleReservation(reservation, actualTokens)
int actualTotalTokens = actualPromptTokens + actualCompletionTokens;
int estimatedTotal    = reservation.getEstimatedPromptTokens() + reservation.getEstimatedCompletionTokens();
int diff = estimatedTotal - actualTotalTokens;

if (diff > 0) {   // 预扣多了，退回
    usageBalanceService.refund(reservation.getUserId(), diff, "LLM结算退款-" + reservation.getReservationId());
}
usageBalanceLlmService.save(record);                       // 落 UsageBalanceLlm 消费记录
redisTemplate.delete("reservation:" + reservation.getReservationId());
```

### abort：异常全额回滚

```java
// abortReservation(reservation) —— LLM 调用抛异常时
int estimatedTotal = reservation.getEstimatedPromptTokens() + reservation.getEstimatedCompletionTokens();
usageBalanceService.refund(reservation.getUserId(), estimatedTotal, "LLM预扣回滚-" + reservation.getReservationId());
redisTemplate.delete("reservation:" + reservation.getReservationId());
```

> [!note] 预扣台账 TTL 10 分钟的隐患
> 预扣信息在 Redis 里 TTL 是 10 分钟。如果一次 LLM 流式响应超过 10 分钟才结束，台账已经过期被清掉，settle 时找不到预扣记录会失败——预扣的钱就退不回来了。长文本 / 慢推理场景要留意这个边界，必要时调大 TTL。

## 二、固定窗口限流

`RateLimitService` 用 Redis 的 `INCR + EXPIRE` 实现**固定窗口计数器**。原理是每个 (动作, 主体, 窗口) 一个计数器 key，请求进来 `INCR` 加一，超过阈值就抛 `RateLimitExceededException`。

```java
// RateLimitService.checkChatByUser(userId)
String key = "rate_limit:chat:user:" + userId;

Long current = stringRedisTemplate.opsForValue().increment(key);   // 原子 +1
if (current != null && current == 1) {                              // 首次请求才设过期
    stringRedisTemplate.expire(key, windowSeconds, TimeUnit.SECONDS);
}
if (current != null && current > max) {
    throw new RateLimitExceededException("聊天请求过于频繁，请稍后再试");
}
```

两个关键点：`INCR` 本身是原子的，天然抗并发；`EXPIRE` 只在 `current == 1`（窗口内第一次请求）时设置，这样过期时间随窗口首请求起算，窗口到点计数器整体清零，下个窗口从头计数。

### 限流维度与阈值

来自 `RateLimitProperties`（前缀 `rate-limit`，可在 `application.yml` 覆盖）：

| 维度 | 主体 | 阈值 | key 形态 |
|---|---|---|---|
| 注册 | 每 IP | 10 次/小时 | `rate_limit:register:ip:{ip}` |
| 登录 | 每用户 | 20 次/小时 | `rate_limit:login:user:{userId}` |
| 聊天 | 每用户 | 60 次/小时 | `rate_limit:chat:user:{userId}` |
| 搜索 | 每用户 | 100 次/小时 | `rate_limit:search:user:{userId}` |
| 上传 | 每用户 | 30 次/小时 | `rate_limit:upload:user:{userId}` |

注册按 **IP** 限是因为还没有用户身份（防批量注册），其余按 **userId** 限。

```yaml
# application.yml 覆盖示例
rate-limit:
  chat-per-hour-per-user: 100   # 聊天 60 → 100
```

> [!note] 为什么用固定窗口而不是滑动窗口
> 固定窗口在窗口**边界**会有"突刺"：如果用户在第 1 个窗口最后一秒打满 60 次、第 2 个窗口第一秒又打满 60 次，相邻 2 秒内实际通过了 120 次（2x 阈值）。滑动窗口（Redis Sorted Set 存时间戳）能消除突刺，但每次都要 `ZADD + ZREMRANGEBYSCORE + ZCARD`，开销和内存都更大。
> 当前业务量下突刺无害，所以选了实现简单、单次只两条 Redis 命令的固定窗口。这是典型的"够用就好"权衡——需要更精确时再升级为滑动窗口。

## 三、连接池：基础设施层的并发控制（ADR-201）

应用层限流挡的是"单用户调太频繁"，但还有一层是"整机能扛多少并发连接"。ADR-201 的做法是给每个稀缺资源配连接池上限，把并发数限制在可预测的范围内。

| 资源 | 池实现 | 关键上限 | 算依据 |
|---|---|---|---|
| MySQL | HikariCP | `maximum-pool-size: 20` | 100 并发 × 0.1s 持有 = 10 理论值，留 2 倍余量 |
| Redis | Lettuce | `max-active: 50` | 缓存/限流/token 访问频繁，留足余量避免等待 |
| LLM HTTP | Reactor Netty | `maxConnections: 50` | 并发聊天 20-30，留 2 倍余量 |
| Kafka 消费 | listener | `concurrency: 3` | 文件处理慢，3 线程够用，过多会打爆 Embedding API |

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 30000
  data:
    redis:
      lettuce:
        pool:
          max-active: 50
          max-wait: 3000
```

> [!tip] 连接池不是越大越好
> ADR-201 的经验教训：早期把 `maximum-pool-size` 设成 100，反而把 MySQL（默认最大连接 151）压垮了。连接池要按"数据库最大连接数 ÷ 应用实例数"反推，留余量而非顶满。另外 LLM 流式响应可能 60 秒，HTTP 响应超时必须设到 120 秒，否则会频繁误超时。

## 四、面试速答

> [!tip] 一句话版
> "LLM 实际 token 数要等流式响应结束才知道，所以不能'用完再扣'——会扣穿余额、并发还会竞态。Baize 用 reserve-settle：调用前按 `prompt估算 + 生成上限` 一次性预扣，余额不够当场拒绝；正常结束 settle 退多扣的差额；异常 abort 全额回滚。这样把'事后可能超支'变成'事前锁上限、事后退多余'。限流是 Redis `INCR+EXPIRE` 固定窗口，聊天 60 次/小时/用户、搜索 100、登录 20、注册 10 次/小时/IP；选固定窗口因为单次只两条命令，边界突刺在当前量级无害。再下面一层是 ADR-201 的连接池上限（Hikari 20 / Lettuce 50 / Netty 50），把整机并发钉死在可预测范围。"
