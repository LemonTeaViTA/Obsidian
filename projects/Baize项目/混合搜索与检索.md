# 混合搜索与检索

> 问题：你的 RAG 检索为什么从"加权融合 BM25 + 向量"改成了 RRF + Reranker + Window 三层管道？每一层解决什么问题，有哪些消融数据支撑？
> 理论基础：[[LLM/RAG检索策略|RAG检索策略]]

> [!note]
> 本文是 [[RAG管道设计]] 的检索环节深挖版。那篇文档把检索一笔带过，本文把在线检索管道（§六）和它依赖的索引存储（§五）讲透。生成环节、解析、分块仍看 [[RAG管道设计]]。

## 在线检索管道全貌

`HybridSearchService.searchWithPermission()` 在 2026-05 演化为完整的三层管道：

```
查询 → (1) RRF 融合 → (2) Reranker rerank → (3) Window 扩展 → 最终 top-K
```

三层各管一件事：RRF 解决"召回阶段两种信号怎么合"，Reranker 解决"召回回来的候选谁更相关"，Window 解决"chunk 边界切碎的语义怎么补回来"。下面逐层拆。

---

## 第一层：RRF 融合（倒数排名融合）

`searchWithRRF()`（默认开启）。核心是发**两次独立查询**再用倒数排名合并，而不是在一次 bool 查询里把两种 should 分数相加。

```
查询 A：纯 KNN（vector 字段）→ top-N
查询 B：纯 BM25（contentEnhanced 字段）→ top-N
融合：score = Σ 1 / (k + rank)，k = 60
去重后取 top candidate_size（默认 20）
```

注意两路查询的目标字段是分开的：KNN 打 `vector` 字段（embedding 召回），BM25 打 `contentEnhanced` 字段（带 sectionPath + ctxSummary 的增强文本，上下文双索引）。

### 为什么用 RRF 而不是加权融合

这是最值钱的面试点。旧版（ADR-004，2024-11）是在一次 ES bool 查询里把 BM25 的 `match` 和 KNN 放进两个 `should`，让 ES 把分数直接相加。问题在于：

> [!warning] 尺度失配
> BM25 分数范围大约 0-30，cosine 相似度范围 0-1。两者直接相加，BM25 永远压过向量分。要"加权融合"就得先归一化，而归一化方案多、超参难调、不同 query 分布还不稳定。

RRF 不看绝对分数，只看**排名**。每路查询里 chunk 排第几，就贡献 `1/(k+rank)` 的分数，两路相加。这样：

| 维度 | 加权融合（旧） | RRF（新） |
|---|---|---|
| 是否依赖绝对分数 | 是，需归一化 | 否，只看 rank |
| 尺度失配问题 | 严重（0-30 vs 0-1） | 完全规避 |
| 超参数量 | 两路权重 + 归一化方式 | 只有一个 k=60 |
| 鲁棒性 | 随 query 分布波动 | 强 |

> [!tip]
> RRF 的 `k=60` 是社区经验值，作用是压低头部排名的边际差距（rank 1 和 rank 2 的分差不会过大），让两路都有相关 chunk 时更容易把它们一起顶上来。整个融合**只有这一个超参**，这正是它鲁棒的原因。

### 回退链

```
RRF 失败 → 回退到 KNN 召回 + BM25 rescore（旧版本逻辑）
```

旧的 "KNN×0.2 + BM25×1.0 rescore" 逻辑没有删，留作 fallback。新路径出问题时检索不至于全挂。

## 第二层：Reranker 重排（Cross-Encoder）

RRF 给出 20 个候选后，调用 **BGE-reranker-v2-m3** 做精排。它是一个**独立的 Python 服务**，跑在 8767 端口，和主 LLM、embedding 服务都分开部署。

```yaml
reranker:
  url: http://localhost:8767
  enabled: true
  top-k: 5            # 最终返回数
  candidate-size: 20  # 送入 reranker 的候选数
```

流程是 candidate-size 20 → reranker 打分 → 取 top-k 5。

### 为什么 reranker 这么关键

embedding 是双塔（query 和 doc 分别编码再算 cosine），reranker 是交叉编码器（query + doc 拼起来过一遍模型），后者能建模 query-doc 之间的交互，区分度天然高一个量级。

> [!tip] 消融数据：区分度差一个数量级
> reranker 的 logit 区分度是 **12.42**，而所有 embedding 模型的区分度都在 **0.27** 量级（Qwen3-Embedding-0.6B 实测 0.251）。差距约 40 倍。
>
> 体现在指标上：引入 BGE-Reranker 把 **ContextPrecision 从 0.21 拉到 0.61**，是 CP 提升的关键贡献者。

改进历史里这一步的痕迹很清楚（注意 reranker 主要拉 AR/CP，F 因排序变化短暂回落）：

| 阶段 | F | AR | CP |
|---|:---:|:---:|:---:|
| +Markdown 结构分片 | 0.93 | 0.47 | 0.21 |
| **+BGE-Reranker** | 0.86 | **0.82** | **0.61** |

## 第三层：Window 扩展（相邻 chunk 拼接）

`expandWithWindow()`（默认开启）。命中的 chunk 自动取**前 1 + 后 1** 个相邻 chunk 拼起来给 LLM。

```yaml
search.window:
  enabled: true
  size: 1            # 前后各 1 个 chunk
```

> [!note] 为什么需要 Window
> 分块时 chunk 边界可能把语义切碎。比如问"3.2 节讲什么"，答案的开头在命中 chunk 末尾、结尾落到下一个 chunk。只返回命中 chunk 会丢一半。取相邻 chunk 把上下文补回来，代价是 context 略长。

注意 Window 在 rerank **之后**做：先用 reranker 选出最相关的 5 个命中 chunk，再围绕它们扩窗，而不是对 20 个候选都扩窗（否则 context 会爆）。

## 双索引架构（检索的存储基础）

RRF 两路查询打不同字段，这背后是 §五 的双索引设计（对标 Anthropic Contextual Retrieval）。单索引 `knowledge_base`（ES 8.10.0），关键字段：

| 字段 | 类型 | 用途 | 含 ctxSummary/sectionPath |
|---|---|---|:---:|
| `textContent` | text (ik 分词) | LLM 看到的干净原文 | 否 |
| `contentEnhanced` | text (ik 分词) | BM25 倒排索引匹配 | 是 |
| `vector` | dense_vector (dims=1024) | KNN 语义召回 | 是 |
| `sectionPath` | keyword | 元数据预过滤（前缀匹配） | — |
| `chunkType` | keyword | 元数据预过滤（精确匹配） | — |
| `fileMd5`/`chunkId`/`pageNumber`/`anchorText` | metadata | 引用溯源 | — |
| `userId`/`orgTag`/`public` | 权限字段 | 多租户过滤 | — |

> [!tip] 为什么召回和生成看不同文本
> 召回阶段（embedding + BM25）需要更多信号让相关 chunk 排上来，所以喂 `contentEnhanced`（`[sectionPath] + ctxSummary + 原文`）。但 LLM 生成时若看到 ctxSummary 这种"二手转述"，RAGAS Faithfulness 会把转述内容判为 unsupported（不在 ground truth 文档里）。所以 LLM 只看 `textContent` 干净原文。Anthropic 论文也明确建议 retrieval 后回查原文给 generator。

embedding 输入的拼法：

```java
// VectorizationService.vectorizeWithUsage()
String embeddingInput = "[" + sectionPath + "] " + ctxSummary + "\n\n" + chunk原文;
List<Float> vec = embeddingClient.embed(embeddingInput);
```

为什么用 ES 不用 Milvus：一个引擎原生同时支持 BM25 + KNN；`filter` 子句天然支持权限过滤；复用已有 ES 运维成本低。

## 元数据预过滤

`SearchController` 接受可选过滤参数，不传则等同默认混合检索：

| 参数 | 作用 | 匹配方式 |
|---|---|---|
| `fileMd5` | 限定单文档检索 | 精确 |
| `sectionPathPrefix` | 章节前缀（如"第3章"） | 前缀 |
| `chunkType` | 类型（text/table/list/code） | 精确 |

这一步是在 ES 检索时下推的预过滤，缩小候选空间，不是召回后再过滤。

---

## 权限过滤（filter clause）

权限不是后置过滤，而是作为 ES `filter` 子句叠加进检索，保证返回结果数和相关性都不被破坏。

```
should: userId == userDbId
        OR public == true
        OR orgTag IN userEffectiveTags（含层级）
minimumShouldMatch = 1
```

`userEffectiveTags` 是组织标签的**层级展开**：用户属于 `team`，沿数据库 `OrganizationTag.parentTag` 递归向上查到 `[team, dept, company]`（不是按点号字符串分割）。结果缓存进 Redis，TTL 1 小时。详见 [[用户管理与权限]]。

> [!warning]
> 不要绕过 `HybridSearchService` 直接调 `esClient.search()`，也不要移除 `filter` 子句——会泄露跨组织数据。权限过滤必须在 ES 层做，应用层后过滤会导致返回结果不足 topK。

## 演进：从加权融合到 RRF + Reranker + Window

这是这条管道最适合讲故事的地方。

> [!tip] 一句话面试版
> "最早是 ES 一次 bool 查询里把 BM25 和 KNN 分数直接相加（ADR-004，KNN×0.2 + BM25×1.0 rescore），但 BM25 是 0-30、cosine 是 0-1，尺度失配让权重根本调不准。后来换成 RRF——发两次独立查询只看排名 `Σ1/(k+rank)`，超参只剩一个 k=60，彻底规避了归一化问题；再叠一层交叉编码器 Reranker（区分度 12.42 vs embedding 0.27），把 ContextPrecision 从 0.21 干到 0.61；最后用 Window 补 chunk 边界切碎的语义。旧的 KNN+BM25 rescore 留作 RRF 失败的 fallback。"

| 阶段 | 融合方式 | 精排 | 上下文 |
|---|---|---|---|
| 旧（2024-11，ADR-004） | KNN×0.2 + BM25×1.0 rescore，一次 bool 查询分数相加 | 无 | 仅命中 chunk |
| 新（2026-05，当前） | RRF（两次独立查询，k=60） | BGE-reranker-v2-m3，20→5 | ±1 相邻 chunk |

> [!note] ADR-004 哪些结论还成立
> "用 ES 同时承载 BM25 + KNN"这个基础架构决策仍然正确（一个引擎、权限过滤天然支持、运维成本低）。被推翻的只是**具体融合方式**——从"分数相加/加权"换成了"RRF 排名融合 + 交叉编码器重排"。所以 ADR-004 的状态是"已采纳，2026-05 演进"，不是废弃。

当前基线（comprehensive_qa.json，159 题中文自造，2026-05-29）：F=0.9261 / AR=0.8735 / CP=0.8850。检索专项指标（ragbench_mixed，100 题英文）整体 Recall@5=0.970 / MRR=0.924 / NDCG@5=0.814。详细消融见 [[评测体系与性能基线]]。
