# 聊天助手模块

## 一、模块定位

聊天助手模块是派聪明系统的**核心交互组件**，承载用户与系统之间的主要对话能力。

**核心能力**：
1. **实时通信**：WebSocket 双向通信，支持流式返回
2. **上下文管理**：Redis 存储会话历史，支持多轮对话
3. **知识检索**：深度集成 Elasticsearch 混合检索
4. **Prompt 构建**：动态生成高质量 Prompt，引导模型生成

## 二、技术选型

| 功能模块 | 技术选型 | 备注 |
| --- | --- | --- |
| 实时通信 | WebSocket（Spring WebSocket） | 支持 STOMP 子协议 |
| 对话上下文存储 | Redis（Spring Data Redis） | 高性能缓存，支持 TTL |
| 本地知识库（当前） | Elasticsearch | 支持混合检索 |
| 本地知识库（规划） | Faiss | 提升向量检索性能 |
| 语言模型调用 | DeepSeek API | 通过 WebClient 调用 |
| Prompt 管理 | 自研模板引擎 | 支持动态模板和变量替换 |
| 异步处理 | Spring WebFlux | 支持响应式编程 |
| 安全认证 | JWT | 确保 WebSocket 连接安全 |

## 三、关键流程

### 1. 用户发起对话流程

```
1. 客户端发起 WebSocket 连接请求（携带 JWT Token）
2. 服务端验证用户身份和权限
3. 建立 WebSocket 长连接
4. 用户发送问题 → 服务端接收并解析
5. 获取或创建会话 ID（conversationId）
6. 启动知识库检索流程：
   - 调用 /api/search/hybrid 接口
   - 执行混合检索（KNN 向量 + BM25 关键词）
   - 筛选、排序、提取关键内容和出处
7. 构建 Prompt：
   - 选择合适的 Prompt 模板
   - 填充检索结果
   - 添加系统级指令
   - 管理上下文长度
8. 调用大模型 API（DeepSeek）
9. 流式接收模型生成内容
10. 通过 WebSocket 实时推送给客户端
11. 更新 Redis 中的对话历史
12. 刷新会话过期时间
```

**流程图**：

```
用户提问
  ↓
WebSocket 接收
  ↓
解析 + 获取会话 ID
  ↓
混合检索（ES）
  ├─ KNN 向量检索
  └─ BM25 关键词检索
  ↓
构建 Prompt
  ├─ 选择模板
  ├─ 填充检索结果
  └─ 管理上下文
  ↓
调用 DeepSeek API
  ↓
流式返回
  ↓
WebSocket 推送
  ↓
更新 Redis 历史
```

### 1.5 当前完整在线管道（15 步）

> [!note] 上面的 12 步是 2026-05 早期视角，已升级
> 真实的 `ChatHandler.processMessage()` + `LlmProviderRouter.streamResponse()` 远不止"检索→拼 Prompt→调模型"。当前管道补齐了意图路由、指代消解、多轮去重、token 预算裁剪、引用溯源、拒答与置信度等环节。面试讲 RAG 在线链路时建议按这 15 步展开。

```
 1. 限流检查（RateLimitService.checkChatByUser）
 2. 获取/创建 conversationId
 3. 加载历史 + 摘要（分层对话历史）
 4. 意图路由：闲聊问题直接跳过检索
 5. 查询改写（指代消解，rewriteQuery）
 6. 混合检索（带组织标签权限，searchWithPermission）
 7. 多轮去重（已用过的 chunk 不重复返回）
 8. 构建 context（chunks + sectionPath + 引用编号映射）
 9. 拒答判定：context 为空 或 maxScore < MIN_ACCEPTANCE_SCORE → 直接拒答，不调 LLM
10. token 预算裁剪（trimHistoryToBudget，保护最近 minRecentTurns 轮）
11. 流式 LLM 调用 + 异步会话摘要（被裁剪的历史压进 summary，下一轮生效不阻塞当前）
12. 提取 LLM 答案中的引用编号 → 持久化引用映射
13. 兜底：LLM 没标 (来源#N) 时自动追加"参考来源"块
14. 计算 answer-level 置信度（high / medium / low）
15. 写回对话历史
```

> [!tip] 拒答机制为什么放在调 LLM 之前
> 低相关性 context 喂给模型最容易触发幻觉，也是 Qwen3 死循环的诱因之一。所以第 9 步在 `context.isBlank() || maxScore < MIN_ACCEPTANCE_SCORE` 时直接返回拒答语，根本不发起 LLM 请求，省 token 又防幻觉。

**指代消解（query rewrite）**：query 含"它/那个/这个/他们"等指代词，或长度 < 15 字时触发。输入 summary + 最近 3 轮历史 + 当前问题，让 LLM 还原成具体实体；结果按 conversationId 缓存到 Redis（12h TTL，防止跨会话上下文串味）。

```
History: 用户问"重疾险 50 万方案多少钱"，助手答"年缴 4800"
当前问: "它的等待期是多久"
改写后: "重疾险 50 万方案的等待期是多久"
```

**引用溯源 (来源#N)**：
- Prompt 强制模型每句话标注 `(来源#N)`
- finalize 阶段从输出里提取引用编号，持久化到 conversation history
- 兜底：输出无引用时自动追加 `**参考来源：** - (来源#1: 文件名 | 第X页) ...`

**Answer-level 置信度**（reranker maxScore + 引用密度 → 信心徽章）：

| 条件 | 置信度 |
| --- | --- |
| maxScore ≥ 2.0 且引用 ≥ 2 个 | high |
| maxScore ≥ 0.0 且引用 ≥ 1 个 | medium |
| 其他 | low |

**token 预算裁剪与分层摘要**：预算来自 `ai.context.max-input-tokens`（默认 16000）。从最早历史开始丢弃，但保护最近 N 轮；被丢弃的消息由 `ConversationSummaryService.updateSummaryAsync()` 异步压缩进 summary，下一轮才生效，不阻塞当前响应。

### 2. 新建会话流程

```
1. 客户端发送"创建会话"请求（REST 接口）
2. 服务端验证用户身份
3. 生成全局唯一的 conversationId
4. 准备空的历史记录结构
5. 在 Redis 中建立用户和会话 ID 的映射关系
6. 设置会话过期时间（如 24 小时或 7 天）
7. 返回 conversationId 给客户端
```

**Redis 数据结构**：

```
# 会话元信息
conversation:{conversationId} → {
  "userId": 123,
  "title": "新对话",
  "createdAt": "2025-01-01T10:00:00Z",
  "expiresAt": "2025-01-08T10:00:00Z"
}

# 对话历史
conversation:{conversationId}:history → [
  {"role": "user", "content": "什么是 RAG？"},
  {"role": "assistant", "content": "RAG 是检索增强生成..."}
]

# 用户会话列表
user:{userId}:conversations → [conversationId1, conversationId2, ...]
```

### 3. 上下文管理流程

**问题**：多轮对话时，如何让模型"记住"前文？

**解决方案**：
1. **Redis 存储历史**：每轮对话后，将 user 和 assistant 消息存入 Redis
2. **动态注入上下文**：构建 Prompt 时，从 Redis 读取最近 N 轮对话
3. **长度控制**：设置轮数上限（如最近 5 轮），避免超出模型上下文限制
4. **TTL 管理**：会话过期后自动清理，节省存储

**示例 Prompt 结构**：

```json
[
  {
    "role": "system",
    "content": "你是一位严谨的知识助手，回答必须基于检索到的文档。"
  },
  {
    "role": "user",
    "content": "什么是 RAG？"
  },
  {
    "role": "assistant",
    "content": "RAG 是检索增强生成..."
  },
  {
    "role": "user",
    "content": "它有什么优势？"  // 当前问题
  },
  {
    "role": "system",
    "content": "检索结果：\n1. RAG 可以减少幻觉...\n2. RAG 支持实时更新知识..."
  }
]
```

### 4. 流式返回流程

**为什么需要流式返回？**
- 大模型生成耗时长（5-10 秒），用户体验差
- 流式返回可以"边生成边展示"，提升交互流畅度

**实现方式**：

```java
// 调用 DeepSeek API，启用流式模式
WebClient.create()
    .post()
    .uri("https://api.deepseek.com/v1/chat/completions")
    .bodyValue(Map.of(
        "model", "deepseek-chat",
        "messages", messages,
        "stream", true  // 启用流式
    ))
    .retrieve()
    .bodyToFlux(String.class)  // 响应式流
    .subscribe(chunk -> {
        // 解析 SSE 格式的 chunk
        String content = parseChunk(chunk);
        
        // 通过 WebSocket 推送给客户端
        webSocketSession.sendMessage(new TextMessage(content));
    });
```

**客户端处理**：

```javascript
const ws = new WebSocket('ws://localhost:8080/chat');

ws.onmessage = (event) => {
  const chunk = event.data;
  // 逐段追加到页面
  document.getElementById('response').innerText += chunk;
};
```

### 5. LLM 调用与三段式门控

> [!note] 文档里写 DeepSeek，线上实际跑的是本地 vLLM
> `DeepSeekClient` 是历史命名，真正后端是本地部署的 **Qwen3.5-9B**（vLLM，port 3598）。图片解析另起一套 Qwen3-VL-8B-Instruct（port 3599）。`LlmProviderRouter` 做了 provider 抽象，可运行时切 vLLM / DeepSeek API。

**生成参数**（`AiProperties.Generation` 默认值）：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| temperature | 0.3 | 低温，问答场景求稳 |
| top_p | 0.9 | nucleus 采样 |
| max_tokens | 8000 | 最大输出（yml 未配置，沿用 Java 默认） |
| presence_penalty | 1.5 | 防止重复循环（**不要移除**） |
| --reasoning-parser | qwen3 | vLLM 启动参数，不要改成 deepseek_r1（与 Qwen3 不兼容） |

> [!warning] 三段式门控的 thinking 当前硬编码关闭
> 历史方案按 maxScore < 0.3 / 0.3–0.6 / ≥ 0.6 三档启用不同 thinking 行为。但 Qwen3 在"低相关性 RAG 结果 + 复杂 system prompt"下会触发无限 reasoning 循环，所以 `enable_thinking` 目前在 `LlmProviderRouter.buildRequest()` 里**硬编码为 false**。`maxRelevanceScore` 参数已经传进 `buildRequest()` 但暂未使用 —— 留作日后开启 thinking 的钩子。详见 ADR-002 三段式门控设计。

### 1. WebSocket 配置

```java
@Configuration
@EnableWebSocketMessageBroker
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    public void configureMessageBroker(MessageBrokerRegistry config) {
        // 启用简单消息代理

        // 设置应用目的地前缀
        config.setApplicationDestinationPrefixes("/app");
    }
    
    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/chat")
            .setAllowedOrigins("*")
            .withSockJS();
    }
}
```

### 2. 消息处理器

```java
@Controller
public class ChatController {
    
    @MessageMapping("/chat")
    @SendToUser("/queue/messages")
    public void handleChatMessage(ChatRequest request, Principal principal) {
        String username = principal.getName();
        String conversationId = request.getConversationId();
        String userMessage = request.getMessage();
        
        // 1. 检索知识库
        List<Document> docs = searchService.hybridSearch(userMessage);
        
        // 2. 构建 Prompt
        List<Message> messages = promptService.buildPrompt(
            conversationId, userMessage, docs
        );
        
        // 3. 调用大模型（流式）
        deepSeekService.streamChat(messages)
            .subscribe(chunk -> {
                // 4. 推送给客户端
                messagingTemplate.convertAndSendToUser(
                    username, 
                    "/queue/messages", 
                    new ChatResponse("chunk", chunk, conversationId)
                );
            });
        
        // 5. 更新 Redis 历史
        conversationService.appendHistory(conversationId, userMessage, response);
    }
}
```

### 3. 异步处理

```java
@Async
public CompletableFuture<List<Document>> hybridSearch(String query) {
    // 并行执行 KNN 和 BM25
    CompletableFuture<List<Document>> knnFuture = 
        CompletableFuture.supplyAsync(() -> knnSearch(query));
    
    CompletableFuture<List<Document>> bm25Future = 
        CompletableFuture.supplyAsync(() -> bm25Search(query));
    
    return CompletableFuture.allOf(knnFuture, bm25Future)
        .thenApply(v -> mergeResults(knnFuture.join(), bm25Future.join()));
}
```

## 七、面试要点

### Q1：为什么选择 WebSocket 而不是 HTTP 轮询？

> [!tip] WebSocket vs SSE 的选型依据
> 如果只需要服务端→客户端的单向流式推送（如 ChatGPT），SSE 更简单。Baize 选 WebSocket 是因为需要双向通信：用户可以随时发送"停止生成"指令，这需要客户端→服务端的实时通道。

**A**：
1. **实时性**：WebSocket 双向通信，服务端可主动推送
2. **性能**：长连接复用，避免频繁建立 TCP 连接
3. **流式友好**：适合大模型流式返回场景

**缺点**：
- 连接管理复杂（需要心跳、重连机制）
- 负载均衡需要支持 WebSocket（如 Nginx sticky session）

### Q2：Redis 存储对话历史，如何控制内存？

**A**：
1. **TTL 过期**：会话 24 小时后自动清理
2. **轮数限制**：只保留最近 5 轮对话
3. **LRU 淘汰**：Redis 配置 `maxmemory-policy allkeys-lru`
4. **归档机制**：重要对话持久化到 MySQL

### Q3：如何处理 WebSocket 连接断开？

**A**：
1. **客户端重连**：指数退避重连（1s → 2s → 4s → 8s）
2. **会话恢复**：重连后通过 conversationId 恢复上下文
3. **心跳检测**：客户端每 30 秒发送 ping，服务端响应 pong
4. **超时清理**：服务端检测到连接空闲 5 分钟后主动关闭

### Q4：流式返回如何处理异常？

**A**：
1. **超时处理**：设置 30 秒超时，超时返回"生成超时"
2. **内容为空**：检测到空响应，返回"模型未生成内容"
3. **格式错误**：解析失败时，记录日志并返回友好提示
4. **降级策略**：DeepSeek 失败时，切换到备用模型（如 Qwen）
