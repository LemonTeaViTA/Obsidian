# 支付与充值

> 问题：用户扫码充值，微信回调可能重复触发，你怎么保证不会重复给余额加钱？整条充值链路从下单到到账是怎么走的，状态机怎么设计的？

充值模块负责充值包管理、订单创建、微信支付集成、支付回调与余额充值。支持多档充值包（体验包 10 元 / 标准包 50 元 / 超值包 100 元），支付方式当前为微信扫码（NATIVE）。核心难点不在"调微信 API"，而在**回调的幂等性**——这是本文的重点。

## 一、参与文件

| 文件 | 路径 | 职责 |
| --- | --- | --- |
| RechargeController | controller/RechargeController.java | 充值端点（创建订单 / 回调） |
| RechargeService | service/RechargeService.java | 订单管理、支付回调编排 |
| WxPayService | service/WxPayService.java | 微信支付集成（下单、签名、XML） |
| RechargePackage | model/RechargePackage.java | 充值包实体 |
| RechargeOrder | model/RechargeOrder.java | 订单实体（含状态字段） |
| WxPayConfig | config/WxPayConfig.java | 微信支付配置（appId / mchId / apiKey / notifyUrl） |

余额的实际加减落在 `UsageBalanceService.recharge()`，属于配额模块，详见 [[配额与限流]]。

## 二、整体链路

充值是一个典型的"客户端下单 → 第三方支付 → 异步回调到账"三段式流程。注意**下单**和**到账**是两条独立的请求链路：前者由用户发起、同步返回二维码；后者由微信服务器异步 POST 回来，用户其实是在前端轮询订单状态等结果。

```
       ┌──────────── 同步：下单链路 ────────────┐
用户 ──POST /recharge/create──► RechargeService.createOrder()
                                  │ 1. 查充值包
                                  │ 2. 建 RechargeOrder (PENDING)
                                  │ 3. 存 MySQL
                                  │ 4. WxPayService.createPayment() ──► 微信统一下单 API
                                  │                                      返回 code_url
                                  └─ 5. 返回 {orderId, qrCodeUrl} ──► 用户渲染二维码
用户扫码支付
       ┌──────────── 异步：回调链路 ─────────────┐
微信服务器 ──POST /recharge/wx-callback (XML)──► RechargeService.handleWxCallback()
                                  │ 1. 验证签名（失败返回 FAIL）
                                  │ 2. 解析 XML，取 out_trade_no / result_code
                                  │ 3. 查订单
                                  │ 4. 幂等判断：非 PENDING 直接返回 SUCCESS
                                  │ 5. 成功 → PAID + recharge 余额 + 日志
                                  │    失败 → FAILED
                                  └─ 6. 返回 SUCCESS 给微信（停止重发）
前端轮询订单状态，发现 PAID，跳转成功页
```

### 创建订单（下单）

`createOrder(userId, packageId)` 的关键步骤：先查充值包拿到金额和 tokens，再建一条 `PENDING` 订单并落库，**然后**才去调微信统一下单。订单先落库的意义在于：回调回来时一定能用 `out_trade_no` 找到这条记录，订单是回调处理的锚点。

```java
RechargeOrder order = new RechargeOrder();
order.setOrderId(UUID.randomUUID().toString());   // 即微信的 out_trade_no
order.setUserId(userId);
order.setPackageId(packageId);
order.setAmount(pkg.getAmount());
order.setTokens(pkg.getTokens());
order.setStatus(RechargeOrder.Status.PENDING);
order.setCreatedAt(LocalDateTime.now());
rechargeOrderRepository.save(order);              // 先落库，再调微信

WxPayService.PaymentResult result = wxPayService.createPayment(
    order.getOrderId(), pkg.getName(), pkg.getAmount());
return new CreateOrderResponse(order.getOrderId(), result.getQrCodeUrl());
```

### 微信统一下单（生成二维码）

`WxPayService.createPayment()` 拼参数 → 签名 → 转 XML → POST `https://api.mch.weixin.qq.com/pay/unifiedorder` → 从响应里取 `code_url`。`trade_type=NATIVE` 表示扫码支付，`code_url` 就是前端渲染成二维码的内容。

> [!tip] 金额单位陷阱
> 数据库里金额单位是"元"（`DECIMAL(10,2)`），微信支付 `total_fee` 单位是"分"且为整数。转换用 `amount.multiply(new BigDecimal(100)).intValue()`。用 `BigDecimal` 而不是 `double` 是为了避免浮点精度问题——金额计算永远不要用浮点。

## 三、幂等性：本模块最核心的设计

> [!warning] 重复回调必然发生，不是"可能"
> 微信支付的回调**保证至少一次、不保证恰好一次**。网络抖动、微信侧没在规定时间内收到 `SUCCESS` 响应，都会触发重发。如果回调处理没有幂等保护，同一笔订单会被处理多次，结果就是**用户付一次钱、余额加好几次**——直接的资损。

幂等的实现非常朴素但有效：**在加余额之前先检查订单状态，只有 `PENDING` 的订单才处理。**

```java
// handleWxCallback 中的幂等闸门
RechargeOrder order = rechargeOrderRepository.findByOrderId(orderId)
    .orElseThrow(() -> new CustomException("订单不存在"));

// 关键：已处理过的订单（PAID / FAILED）直接返回 SUCCESS，不再动余额
if (order.getStatus() != RechargeOrder.Status.PENDING) {
    return "SUCCESS";
}

if ("SUCCESS".equals(resultCode)) {
    order.setStatus(RechargeOrder.Status.PAID);
    order.setPaidAt(LocalDateTime.now());
    rechargeOrderRepository.save(order);
    usageBalanceService.recharge(order.getUserId(), order.getTokens(), "充值-" + orderId);  // 加余额
    logger.info("订单 {} 支付成功，用户 {} 充值 {} tokens", orderId, order.getUserId(), order.getTokens());
} else {
    order.setStatus(RechargeOrder.Status.FAILED);
    rechargeOrderRepository.save(order);
}
return "SUCCESS";
```

### 为什么"检查状态"就够了

订单状态在这里承担了**幂等键**的角色：第一次回调把 `PENDING` 推进到 `PAID`，之后所有重复回调进来都因为 `status != PENDING` 在第一道闸门被拦下，直接回 `SUCCESS` 让微信停止重发，余额逻辑根本不会被触达。状态本身就是"是否已处理"的标记位，不用额外维护一张去重表。

> [!warning] 状态检查 + 写余额必须在同一事务里
> 注意事项里点明了：**用数据库事务保证原子性**。"读订单状态 → 改状态 → 加余额"这三步要在一个事务内完成。否则在高并发下两个回调同时读到 `PENDING`，会双双通过闸门、双双加余额——这就是经典的检查-执行竞态（check-then-act race）。事务（配合行锁 / 状态条件更新）把这个窗口关掉。

### 状态先行 vs 余额先行的顺序

代码里是**先把订单置 `PAID` 并保存，再调 `recharge`**。这个顺序不是随意的：状态先落地，幂等闸门才能在后续回调里立刻生效。如果反过来先加余额再改状态，加完余额还没改状态时若发生重复回调或崩溃重试，又会重复加钱。状态推进作为"已处理"的依据，必须在产生副作用之前确立。

## 四、支付状态机

订单状态是整个模块的主线。`RechargeOrder.Status` 的流转：

```
                     ┌─────────────────┐
                     │     PENDING      │  下单成功，等待支付
                     └────────┬─────────┘
            回调 result_code   │   回调 result_code
              = SUCCESS        │     != SUCCESS
                     ┌─────────┴─────────┐
                     ▼                   ▼
              ┌────────────┐      ┌────────────┐
              │    PAID     │      │   FAILED    │
              │ 已到账(终态) │      │ 支付失败(终态)│
              └────────────┘      └────────────┘

       （规划中）PENDING 超时 30min ──► CANCELLED（定时任务）
```

| 状态 | 含义 | 触发条件 | 是否终态 |
| --- | --- | --- | --- |
| PENDING | 已下单，等待支付 | `createOrder()` 创建时 | 否 |
| PAID | 已支付、余额已到账 | 回调 `result_code = SUCCESS` | 是 |
| FAILED | 支付失败 | 回调 `result_code != SUCCESS` | 是 |
| CANCELLED | 超时未支付被取消 | 定时任务（规划场景，见下） | 是 |

只有 `PENDING` 是可被回调推进的"活"状态；`PAID` / `FAILED` 都是终态，再来回调一律被幂等闸门挡回。这也是为什么幂等判断写成 `status != PENDING` 而不是 `status == PAID`——`FAILED` 的订单同样不该被二次处理。

## 五、失败与重试处理

| 场景 | 处理方式 |
| --- | --- |
| 签名验证失败 | 直接返回 `FAIL`，不查订单、不动余额（见安全节） |
| 订单不存在 | 抛 `CustomException("订单不存在")` |
| 回调 `result_code != SUCCESS` | 订单置 `FAILED`（终态） |
| 重复回调 | 幂等闸门拦截，返回 `SUCCESS` |
| 用户一直不支付 | 订单停留 `PENDING`（规划：30 分钟超时自动 `CANCELLED`） |

### 微信侧的重试由"返回值"驱动

handleWxCallback 的返回值是和微信约定的重试信号：返回 `SUCCESS` 微信就认为通知已被消费、停止重发；返回 `FAIL`（或超时未响应）微信会按其策略重试。所以即便是被幂等闸门拦下的重复回调，也必须返回 `SUCCESS`——否则微信会一直重发这笔"其实早就处理完"的通知。

### 订单超时取消（规划场景）

`PENDING` 订单不会自己消失。常见改动场景里规划了一个 `@Scheduled` 定时任务：扫 `status=PENDING` 且 `createdAt < now - 30min` 的订单，置为 `CANCELLED`，避免无效订单长期占用、也防止用户拿很久以前的二维码付款后系统状态错乱。

## 六、安全：签名验证

> [!warning] 回调端点是公网暴露的，必须先验签
> `/recharge/wx-callback` 必须公网可访问（本地开发用 ngrok，生产配真实域名），这意味着任何人都能往这个地址 POST。`handleWxCallback` 的第一步就是 `verifySignature(xmlData)`，验签失败立即返回 `FAIL`，**在查订单和动余额之前**。少了这一步，攻击者可以伪造一条 `result_code=SUCCESS` 的回调，凭空给自己充值。

签名算法：`MD5(参数按字典序拼接 + apiKey)`。`apiKey` 是商户与微信之间的共享密钥，不出现在请求里，攻击者无法伪造出正确签名。验签和幂等是两道独立的防线——验签防伪造，幂等防重复，缺一不可。

## 七、设计权衡小结

- **订单先落库再调微信**：牺牲一点"无效订单"的存储，换来回调一定能找到锚点、状态机有据可依。
- **用订单状态当幂等键**：不额外建去重表，复用既有字段，简单且与状态机天然一致；代价是必须配合事务防竞态。
- **异步回调 + 前端轮询**：支付结果到账是异步的，前端轮询订单状态体验上有延迟，但这是第三方支付的固有模型，换来下单链路的快速返回。
- **同步下单失败 vs 异步到账失败分离**：下单失败用户立即看到（同步异常），到账失败走状态机（FAILED），两类失败的可观测性和处理路径清晰分开。
