# CC 的可观测性（成本、token、遥测）

> **一句话定位**：CC 怎么知道"自己花了多少钱、烧了多少 token、哪里出错了"。这套可观测性不只是给用户看账单——它是 CC 那些「token 经济学」决策的**数据来源**：正因为能精确测量，才能判断「截断到底省不省 token」这种问题。

---

## 一、先记一张地图

CC 的可观测性分三层：

| 层 | 追踪什么 | 给谁用 |
|---|---|---|
| **① 成本/token 账本** | 每个模型用了多少 token、花了多少钱、跑了多久、改了多少行代码 | 用户（`/cost` 命令）+ 自己 |
| **② 遥测事件** | "发生了什么"——每个关键动作/错误都打一个命名事件 | 开发方（理解海量用户的使用和故障） |
| **③ 指标计数器** | token 消耗等指标，按标准可观测性格式导出 | 监控系统 |

核心一句：**CC 把"花了多少、做了什么、哪出错"都记下来——既给用户看账，也给自己做优化决策的依据。**

---

## 二、① 成本/token 账本

CC 维护一个**会话级的账本**，逐项累计。用户敲 `/cost` 能看到：

- **总花费**（美元）
- **API 耗时** vs **墙钟耗时**（API 实际调用时间 vs 整个会话时间）
- **代码改动量**（加了多少行、删了多少行）
- **按模型分的用量**：每个用到的模型，分别统计了——

| 统计项 | 含义 |
|---|---|
| `inputTokens` | 输入 token（发给模型的） |
| `outputTokens` | 输出 token（模型生成的） |
| `cacheReadInputTokens` | **从缓存读的** input token（命中前缀缓存的部分） |
| `cacheCreationInputTokens` | **写入缓存的** input token（第一次建立缓存的部分） |
| `webSearchRequests` | 网页搜索次数 |
| `costUSD` | 这个模型花了多少钱 |

这个账本**跨会话保存**——关掉再开，能恢复上次的成本状态。

### 为什么把 cache_read 和 cache_creation 分开记（关键洞察）

注意上面那两个缓存相关的字段——**这正是 CC 能"测量前缀缓存有没有生效"的依据**（见 [[CC-系统提示拼装]]）。

- `cacheCreationInputTokens` 高 = 大量内容在「第一次写入缓存」——说明缓存经常 miss、在反复重建。
- `cacheReadInputTokens` 高 = 大量内容「从缓存读」——说明缓存命中得好。

所以「保前缀缓存」这件事不是凭感觉，是**可量化的**：把这两个数一比，就知道缓存策略好不好。前面讲的「系统提示要跨轮稳定」「破缓存要写理由」之所以能被严肃执行，正是因为**有这两个数字盯着**。

> 这是可观测性最重要的价值：**让"省 token / 保缓存"从口号变成可测量的指标。** 没有度量，优化就是瞎猜。

---

## 三、② 遥测事件：每个动作打一个"命名事件"

CC 在代码里**到处打事件**——每个关键动作、每个错误，都用一个有名字的事件记下来。比如（都是真实事件名）：

- `tengu_bash_security_check_triggered`：bash 安全检查被触发（这个出现了 42 次调用点，说明安全检查埋点很密）
- `tengu_tool_use_error`：工具执行出错
- `tengu_compact_failed`：上下文压缩失败
- `tengu_mcp_list_changed`：MCP 工具列表变了
- `tengu_cancel`：用户取消
- `tengu_git_operation`：git 操作

这些事件汇聚起来，让开发方能**在海量用户层面**回答："工具出错率多少？压缩失败频率？哪个安全检查最常触发？"——这正好对应了"调用次数、成功率、错误率"这类监控维度，只不过 CC 是面向**整个用户群**的产品级遥测，不是单个 agent 的业务看板。

### 这些事件怎么驱动优化（真实例子）

[[01-FileRead-读文件]] 里提过一个事：CC 曾经上线"大文件截断读前 N 行"的方案，**靠遥测数据发现"工具错误率降了、但 token 反而涨了"，于是回滚**。

这个决策**完全建立在遥测上**——没有"token 消耗"和"错误率"两个指标同时被记录，根本发现不了"优化了错误率却输了 token"这个反直觉的结果。**可观测性不是事后看，是优化的前提。**

---

## 四、③ 指标计数器：标准可观测性导出

除了事件，CC 还把 token 消耗这类**指标**通过标准的可观测性框架（OpenTelemetry 那一套）导出——token 计数器在每次记账时，带上「类型」标签（input / output / 缓存读 / 缓存写）发出去。这样这些数据能接进标准的监控系统，做聚合、看趋势、设告警。

简单说：**事件**回答"发生了什么"（离散的动作/错误），**指标**回答"量是多少"（连续的数值，可聚合）。两者配合，构成完整的可观测性。

---

## 五、把可观测性和前面的主线串起来

可观测性其实是**前面所有"经济学决策"的底座**：

- **token 经济学**（读文件抛错、搜索分页、命令落盘……）——靠 token 账本量化"到底省没省"。
- **前缀缓存经济学**（系统提示稳定、破缓存写理由）——靠 cache_read / cache_creation 两个数量化"缓存命中率"。
- **健壮性**（各种错误恢复）——靠遥测事件量化"哪类错误多发、恢复成功率多少"。

**一句话：前面讲的所有"该怎么做"的设计，背后都有一个"做得好不好"的度量在支撑。** CC 之所以能做出那些反直觉但正确的取舍（比如截断回滚），正是因为它什么都在测。

---

## 六、核心 takeaway

1. **三层可观测性**：成本/token 账本（给用户 + 自己）、遥测事件（"发生了什么"）、指标计数器（"量是多少"）。
2. **cache_read 和 cache_creation 分开记**——这是测量前缀缓存有没有生效的依据，让"保缓存"从口号变成可量化指标。
3. **遥测事件遍布代码**：每个关键动作/错误打一个命名事件，面向海量用户做产品级监控（错误率、失败频率等）。
4. **可观测性是优化的前提，不是事后摆设**：截断方案回滚就是靠"token 涨了"这个数据发现的——没有度量就没有正确的取舍。
5. **它是前面所有经济学决策的底座**：省 token、保缓存、健壮性，背后都有对应的度量在支撑。
