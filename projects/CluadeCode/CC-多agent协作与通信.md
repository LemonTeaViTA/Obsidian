# CC 的多 agent 协作与通信

> **一句话定位**：单个子 agent（[[03-Agent-子agent工具]]）解决的是"把一段脏活隔离出去、只回结论"。这篇讲更上一层——**多个 agent 怎么编队干活、它们之间怎么传消息**。核心两件事：协调者把活**并行**派给多个 worker；agent 之间靠**文件信箱**异步通信。

---

## 一、先记一张地图

| 要素 | 是什么 |
|---|---|
| **① 角色分工** | 一个"协调者"负责拆活、派活、汇总；多个"worker"负责干具体的活 |
| **② 并行异步** | worker 是异步的——派出去立即返回，结果稍后作为单独消息到达。多个独立 worker 同时跑 |
| **③ 上下文隔离** | 每个 worker 有自己独立的上下文，**看不到协调者的对话**，所以派活的指令必须自包含 |
| **④ 通信靠信箱** | agent 之间传消息，靠**各自的一个"收件箱"文件**——你往我的信箱写，我读我的信箱 |

核心一句：**协调者拆活并行派出去，worker 各自独立干、干完单独回报，agent 间靠文件信箱传话。**

---

## 二、① 角色分工：协调者 + worker

多 agent 协作的基本结构是**一个协调者带一群 worker**：

- **协调者**：不亲自干重活，而是**把大任务拆成小块、派给 worker、收集结果、汇总**。它的系统提示明确要求："**能自己直接答的就别派活**——别把你不用工具就能处理的事也甩给 worker。"
- **worker**：被派去干一件具体的活（研究某个问题、改某个模块、查某个东西），干完把结果回报。

关键纪律（协调者系统提示里写死的）：

- **"并行是你的超能力"**：worker 是异步的，**独立的活要并发派出去**，别串行。要研究一个问题就从多个角度同时铺开。一次消息里发多个派活调用 = 并行启动多个 worker。
- **派出去之后，简短告诉用户"我派了什么"就结束本轮**，**绝不预测或编造 worker 的结果**——结果会作为单独的消息稍后到达。

---

## 三、② 并行异步：派出去就返回，结果稍后到

这是和单个子 agent 最大的不同。单个子 agent 是**同步**的（派出去、等它跑完、拿到结论才继续）。而协调者派的 worker 是**异步**的：

> 派一个 worker → **立即返回一个任务 ID**（不等它跑完）→ 协调者可以接着派别的 worker / 干别的 → worker 跑完后，结果**作为一条单独的消息**到达协调者。

这样协调者���能**同时驱动好几个 worker**：一次派出 3 个去研究不同角度，它们并行跑，谁先完谁的结果先回来。这正是"并行是超能力"的落地——**异步 + 立即返回任务 ID**，让 fan-out（一散多）成为可能。

配套能力：
- 发现某个 worker 派错方向了，可以**中途停掉它**（用它的任务 ID）。
- 停掉的 worker 还能**用发消息的方式让它继续**（不一定要重新派一个）。

---

## 四、③ 上下文隔离：worker 看不到协调者的对话

每个 worker 有**自己独立的上下文**，**完全看不到协调者那边的对话历史**。这带来一条铁律：

> **派给 worker 的每一条指令，必须自包含——把 worker 需要知道的一切都写进去。**

协调者系统提示里专门强调了一个**反模式**：

- ❌ **别写"基于你的发现继续""根据研究结果……"**——这种话等于**把理解的责任甩给了 worker**。
- ✅ 正确做法：协调者**自己先把发现消化、综合成一个具体明确的指令**，再派下一个 worker。

为什么这么严？因为"理解和综合"是协调者的核心职责。如果它只会说"基于前面的研究做下去"，那它根本没真正理解，只是在 worker 之间传球。系统提示原话："**你永远不把'理解'这件事交给���一个 worker。**"

这其实是 [[03-Agent-子agent工具]] 那个"上下文隔离"思想的延续——隔离带来干净（worker 不被协调者的一堆历史干扰），但代价就是**沟通必须显式、自包含**。

---

## 五、④ 通信机制：文件信箱（核心）

agent 之间怎么传消息？答案朴素得出人意料——**靠文件**。

机制是这样：

- **每个 agent 有一个"收件箱"**，本质就是磁盘上的**一个文件**（在团队目录下，按 agent 名字命名）。
- **发消息** = 往**对方的收件箱文件**里写一条记录（记录里有"谁发的、内容、读没读"）。
- **收消息** = agent 读**自己收件箱**里的**未读消息**，把它们**作为附件注入到自己的对话里**（这样模型就"看到"了这条消息），然后**标记为已读**。

所以这是一套**异步、基于共享文件系统**的通信：
- 不是实时的（不是 A 直接喊 B，而是 A 把信放进 B 的信箱，B 下次查信箱才看到）。
- 通过"未读/已读"标记管理，避免同一条消息被重复处理。

**为什么用文件信箱、而不是直接内存传递？** 文件信箱的好处是**解耦**——发送方不用管接收方此刻在不在、在干什么，把信放进信箱就行；接收方按自己的节奏查收。这和"后台任务完成通知用队列"（[[CC-健壮性外壳]]）是同一个思想：**用一个中间存储解耦收发双方的时序**。

---

## 六、两套多 agent 模式的区别

CC 其实有两种"多 agent"，别混：

| | 单个子 agent（检索型） | 协调者 + worker 编队 |
|---|---|---|
| 关系 | 主 agent 临时派一个去查东西 | 协调者长期带一队 worker 干活 |
| 同步性 | 同步（等它回结论） | 异步（派出去立即返回，结果稍后到） |
| 数量 | 通常一个 | 多个并行 |
| 通信 | 只回传一次结论 | 可来回发消息（信箱）、可中途停/续 |
| 适用 | "去帮我查清 X" | "把这个大项目拆成几块，并行推进" |

[[03-Agent-子agent工具]] 讲的是前者，这篇讲的是后者。后者是前者的"规模化升级"——从"派一个、等结论"变成"派一队、并行、可通信"。

---

## 七、核心 takeaway

1. **协调者 + worker 分工**：协调者拆活/派活/汇总，worker 干具体活。能自己答的别派。
2. **并行异步是核心**：worker 派出去立即返回任务 ID，多个并发跑，结果作为单独消息稍后到——"并行是超能力"。
3. **worker 看不到协调者的对话**：派活指令必须自包含；**绝不能说"基于你的研究继续"**——那是把理解甩给 worker，协调者必须自己先综合。
4. **通信靠文件信箱**：每个 agent 一个收件箱文件，发=往对方信箱写、收=读自己未读并注入对话再标已读。异步、解耦。
5. **和单个子 agent 的区别**：子 agent 是"派一个、同步、等结论"；编队是"派一队、异步、可通信、可停续"。
