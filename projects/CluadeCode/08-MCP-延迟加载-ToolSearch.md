# CC 怎么按需加载 MCP 工具（ToolSearch）

> **一句话定位**：用户可能接几十个 MCP 服务、上百个工具。把这上百个工具的完整说明都塞进每轮请求，会白白烧掉几万 token。CC 的办法是**平时只让模型看到工具的"名字"，等它真要用某个时，再把那个工具的完整定义"展开"出来**。

---

## 一、先理解 MCP 和这个问题

**MCP 是什么**：一个标准协议，让 CC 能接入各种外部工具服务——比如一个 Slack 服务（发消息、读频道）、一个数据库服务、一个 Jira 服务。接上之后，这些外部工具就像 CC 自带工具一样能被模型调用。

**问题来了**：每个工具要让模型会用，就得给模型一份"说明书"——名字、干什么、有哪些参数（参数说明可能很长）。一个工具的完整说明可能几百 token。**接几十个服务、上百个工具，光这些说明书就好几万 token**——而且按那条贯穿全局的主线，**它们会逐轮重发**。可是模型这一个任务里，大概率只用得到其中一两个工具。

**这就是浪费**：为了"万一要用"，把上百本说明书一直摊在桌上、反复重发。

---

## 二、地图：CC 的解法是"先给名字、用时展开"

| 步骤 | 状态 | 说明 |
|---|---|---|
| **平时** | 工具只露"名字" | 几十上百个 MCP 工具，模型只看到名字清单，不占完整说明的 token |
| **模型想用某个** | 调"工具搜索" | 模型说"我要找和 slack 发消息相关的工具" |
| **展开** | 那个工具的完整说明出现 | 这一个工具的完整定义被补进上下文 |
| **之后** | 像自带工具一样调用 | 模型现在知道它的参数了，正常调用 |

核心思想一句话：**说明书不全摊开，要用哪本再翻哪本。**

---

## 三、这套机制怎么转

### 平时：延迟工具只露名字

CC 把 MCP 工具（以及个别内置的大工具）标记为**"延迟加载"**。被标记的工具，在发给模型的工具清单里**只出现名字，不带完整的参数说明**。所以哪怕接了一百个工具，这个清单也很短、很省 token。

模型这时的状态是：**知道有这么个工具、叫什么名，但不知道它的参数，所以还不能直接调。**

### 用时：搜索 → 展开

模型想用某个延迟工具时，先调一个特殊的**"工具搜索"工具**，描述一下它想要什么——可以按名字精确取（"给我这几个工具"）、按关键词搜（"查 notebook 相关的"）、或要求名字里含某个词。

搜索命中之后，**那些命中工具的完整定义就被"展开"补进模型的上下文**。从这一刻起，模型就知道这些工具的完整参数了，可以**像调用自带工具一样正常调用**它们。

### 一个关键事实：这套"展开"靠的是平台 API 能力

这里有个值得知道的底层事实：**这套机制不是纯粹的客户端逻辑，它依赖模型推理 API 本身的特殊能力**——

- 发工具清单时，能给某个工具打一个"先别加载完整说明"的标记，**API 那边**就只把名字给模型看。
- "工具搜索"返回的，其实是一种**"工具引用"**（就是个工具名的引用），而**API 自己负责把这个引用展开成完整的工具定义**塞进模型上下文。

换句话说，"展开"这个动作是 **API 平台帮你做的**，不是客户端自己拼的。这也带来一些限制：不是所有模型都支持这套（个别模型不支持就只能退回"全摊开"），第三方的 API 代理网关也常常不支持。

> 这是一个**很重要的认知**：CC 的某些能力是建立在"它自家的模型推理 API + 自家的 CLI"垂直整合之上的。换个不提供这种能力的 API（比如很多开放模型走的通用接口），这套机制就**没法照搬**——因为底层协议根本没有"先发名字、用时让 API 展开"这回事。对这类接口，模型只能调用"请求时就完整声明过的工具"。

### 三档开关

CC 给这套机制留了三档：
- **默认**：总是对 MCP 和大工具延迟加载。
- **自动**：只有当这些工具的说明书加起来超过一个阈值（比如上下文窗口的 10%）时才启用延迟——量不大就懒得折腾。
- **关闭**：全部摊开（退回传统方式）。

---

## 四、这是 token 经济学的"天花板"

读到这会发现，按需加载 MCP 工具，是那条贯穿全局的 token 经济学主线**做到了极致的一层**：

- 读文件：管的是"一个文件的内容"别全塞进来。
- 搜索/命令输出：管的是"一堆结果"别全塞进来。
- 子 agent / 网页摘要：管的是"一大堆原始材料"别全塞进来，只进结论。
- **按需加载工具：连"工具的说明书"本身都别全塞进来，要用哪个再展开哪个。**

前面几个管的是"工具产出的内容"，这一层管的是"工具自身的定义"——**省 token 省到了工具描述这一层**。这是被"海量 MCP 生态"（接几十上百个工具）逼出来的需求：工具一多，光说明书就能撑爆上下文。

---

## 五、核心 takeaway

1. **问题**：接太多 MCP 工具，光说明书就烧几万 token，还逐轮重发——可一个任务只用得到一两个。
2. **解法**：平时只露工具名字，模型要用哪个，调"工具搜索"把那个工具的完整定义展开出来，再正常调用。一句话——**说明书要用哪本翻哪本，别全摊开**。
3. **底层靠平台 API**："展开"是 API 帮做的（先发名字标记 + 用时展开工具引用），不是纯客户端逻辑——这意味着换个不提供此能力的通用 API 就没法照搬。
4. **token 经济学的天花板**：前面省的是"工具产出的内容"，这一层省到了"工具自身的定义"。是海量工具生态逼出来的优化。
