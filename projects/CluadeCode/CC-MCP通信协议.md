# CC 怎么和 MCP 工具通信（协议层）

> **一句话定位**：MCP（Model Context Protocol）是一个**标准协议**，让 CC 能接入各种外部工具服务（数据库、Slack、监控系统……）。这篇讲**协议层面 CC 和这些外部服务到底怎么对话**——握手、要工具清单、调工具、传输方式。（上层的「工具太多怎么按需加载」见 [[08-MCP-延迟加载-ToolSearch]]。）

---

## 一、先记一张地图

| 环节 | 在做什么 |
|---|---|
| **① 用标准协议，不自己造** | CC 直接用官方 MCP SDK，底层是 JSON-RPC。接入方只要遵守协议，谁都能接 |
| **② 握手 + 能力协商** | 连上时双方互报身份和能力（"我支持哪些功能"） |
| **③ 要工具清单** | 调 `tools/list`，拿回这个服务提供哪些工具 |
| **④ 调工具** | 调 `tools/call`，把参数发过去、拿结果回来 |
| **⑤ 传输方式可插拔** | 同一套逻辑，底下可以是子进程/HTTP/WebSocket 等多种通道 |

核心一句：**MCP 是一套标准的"外部工具接入协议"，CC 按协议握手、要清单、调用——和接哪种服务无关。**

---

## 二、① 关键前提：用标准协议，不自己造轮子

这是理解 MCP 最重要的一点：**CC 不自己定义"怎么和外部工具对话"，而是用一个公开的标准协议（MCP），并直接用它的官方 SDK。**

为什么这很关键？因为**"标准"意味着解耦**：
- 任何人按 MCP 协议写一个服务（一个 Slack 工具、一个数据库工具），**不用知道 CC 内部长什么样**，就能被 CC 接入。
- CC 也不用为每种外部服务写专门的对接代码——**所有 MCP 服务走同一套协议**。

底层用的是 **JSON-RPC**（一种基于 JSON 的远程调用格式）：每个操作是一个有 `method`（方法名）和 `params`（参数）的 JSON 消息。MCP 在 JSON-RPC 上定义了几个标准方法，最核心的两个是：
- `tools/list`：要这个服务的工具清单。
- `tools/call`：调用其中某个工具。

---

## 三、② 握手 + 能力协商

CC 连上一个 MCP 服务时，会**先互相报家门**：

- **CC 报自己**：我是 "claude-code"，版本号多少，我支持哪些能力（比如能不能让服务反过来问我问题）。
- **服务报自己**：我支持哪些能力（最关键的是「我有没有工具」）。

这一步叫**能力协商**——双方确认"对方支持什么"，之后才按支持的能力交互。比如 CC 会检查服务有没有声明「我有工具」，没有的话就不去要工具清单了。

---

## 四、③ 要工具清单（tools/list）

握手完，CC 调 `tools/list`，拿回这个服务提供的所有工具。拿到之后做几件事，把外部工具**转换成 CC 内部统一的工具格式**：

1. **加前缀防重名**：每个工具名被改成 `mcp__{服务名}__{工具名}`（比如 Slack 服务的 `send_message` 变成 `mcp__slack__send_message`）。为什么？因为可能接多个服务，**不同服务可能有同名工具**——加上服务名前缀，工具名空间就隔离开了，不会撞车。
2. **打标记**：标成「这是 MCP 工具」，后续权限检查、延迟加载都靠这个标记区分。
3. **清洗外部数据**：MCP 服务是**外部的、不完全可信的**，它返回的工具描述、名字等会做 unicode 清洗——防止外部数据里夹带异常字符注入到 CC 的上下文里。这是一条安全边界：**凡是外部来的数据，进 CC 之前先清洗。**
4. **可选取搜索提示**：如果服务在工具元信息里提供了「搜索关键词」，CC 会取来用于延迟加载时的搜索匹配。

转换完，这些外部工具就和 CC 自带工具**长得一样**了，模型调用时感觉不到区别。

---

## 五、④ 调工具（tools/call）

模型决定调某个 MCP 工具时，CC 发一个 `tools/call` 请求，带上：
- **工具名 + 参数**：要调哪个、参数是什么。
- **超时**：等多久没回就算超时。
- **取消信号**：用户中断时能掐断这次调用。
- **进度回调**：MCP 服务在长时间操作中，可以**反过来向 CC 汇报进度**（"已处理 30%"），CC 把进度显示给用户。

结果回来后，CC 把它转成标准的工具结果，接回对话——和自带工具的结果走同一条路。

---

## 六、⑤ 传输方式可插拔（同一套逻辑，多种通道）

MCP 的一个聪明设计是**把"协议"和"传输"分开**：协议（握手、tools/list、tools/call）是一套，但底层「消息怎么传过去」可以是多种通道：

| 传输方式 | 怎么连 | 典型场景 |
|---|---|---|
| **stdio** | 启动一个子进程，通过它的标准输入/输出收发消息 | 本地工具（最常见）——比如本地装的一个文件系统 MCP |
| **SSE / HTTP 流** | HTTP 长连接 | 远程服务 |
| **WebSocket** | WebSocket 连接 | 远程服务、IDE 集成 |
| **进程内** | 不开子进程，直接在 CC 进程内跑 | CC 自带的一些内置 MCP 服务 |

**关键**：不管底下是哪种通道，**上层的协议逻辑（握手、要清单、调工具）完全一样**。这就是「传输层抽象」——换通道不影响协议逻辑。比如 stdio 方式下，CC 会启动一个子进程、捕获它的错误输出（stderr）用于排查连接失败，但「调工具」这件事和走 HTTP 时一模一样。

---

## 七、健壮性：连接管理

接外部服务，连接出问题是常态，CC 有一套：
- **连接超时**：连不上不会无限等，超时报错。
- **断线重连**：连接掉了能检测到并尝试重连（个别传输方式下，底层只报错不报关闭，CC 会自己桥接这个缺口触发重连）。
- **会话过期检测**：服务那边会话过期了，CC 能识别并清掉缓存的连接。
- **认证**：支持 OAuth 等认证流程（接需要登录的服务时）。
- **超时/失败的调用**：`tools/call` 超时或失败，会作为错误结果返回给模型，而不是让调用永久挂起。

---

## 八、核心 takeaway

1. **MCP 是标准协议，CC 用官方 SDK 接入，不自己造**——标准化带来解耦：任何按协议写的服务都能接，CC 不用为每种服务写专门对接。
2. **底层是 JSON-RPC**，核心两个方法：`tools/list`（要清单）、`tools/call`（调工具）。
3. **握手先做能力协商**：双方互报身份和支持的能力。
4. **工具清单要转换**：加 `mcp__服务名__工具名` 前缀防重名、打 MCP 标记、**清洗外部数据**（安全边界）、转成 CC 统一格式。
5. **传输层可插拔**：stdio/HTTP/WebSocket/进程内，上层协议逻辑不变。
6. **调用带超时/取消/进度回调**，连接有重连/会话过期/认证管理——接外部服务，健壮性是刚需。
