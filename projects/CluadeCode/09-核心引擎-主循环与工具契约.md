# CC 的核心引擎：对话主循环 + 工具是什么

> **一句话定位**：这篇讲两件最底层的事——CC 一轮对话的**骨架**怎么转、以及 CC 里"**一个工具**"到底由哪些部分构成。骨架的"出错怎么救"那一圈兜底，单独在 [[CC-健壮性外壳]] 讲；这里只讲**正常情况下的主干**和**工具的构造**。

---

## 一、对话主循环：一句话能说完的骨架

CC 一轮对话（一个 turn）的核心循环，本质就是这么转：

> **把当前对话发给模型 → 模型要么给最终回答（结束），要么要求调用一些工具 → 那就执行这些工具、把结果接回对话 → 再发给模型 → 往复，直到模型不再调工具为止。**

就这么简单。展开成步骤：

| 步 | 做什么 |
|---|---|
| 1 | 准备好当前对话（必要时先压缩瘦身），发给模型 |
| 2 | 模型回应：**带不带工具调用？** |
| 3a | **带** → 执行这些工具 → 每个结果作为"工具结果"接回对话 → **回到第 1 步** |
| 3b | **不带** → 这就是最终回答 → 结束，返回给用户 |

**唯一的分岔点就是第 2 步**："模型这次回应里有没有要调工具"。有就执行+接回+再转一圈，没有就收工。这个"转圈直到模型不调工具"的模式，就是所谓 ReAct（推理-行动）循环。

> 真实的循环代码有一千多行，但**骨架就是上面这几十行**。剩下那一千多行,全是骨架外面"出岔子怎么自己救"的兜底——那些是 [[CC-健壮性外壳]] 的内容。这里要记住的是：**主干极简，复杂度在外壳。**

### 一个关键纪律：工具调用和结果必须配对

这条贯穿整个循环（也是健壮性外壳反复在守的底线）：模型每发起一个工具调用，对话里就**必须有一个配对的结果跟在后面**。少一个，下次请求就会被整个拒绝、对话卡死。所以"执行工具→把结果接回"这一步不是可有可无，是**协议刚需**。

---

## 二、工具是什么：一个标准化的"契约对象"

CC 里的每一个工具——读文件、搜索、执行命令、派子 agent……——都不是一个随便的函数，而是一个**实现了统一契约的标准对象**。主循环不关心具体是哪个工具，它只**按一套固定的生命周期，去调用这个对象的各个"钩子"**。

把一个工具拆开，它由这么几类部件构成：

| 部件类别 | 干什么 | 什么时候被调 |
|---|---|---|
| **自我介绍** | 名字、给模型看的说明、参数表 | 组装请求时（让模型知道有这工具、怎么用） |
| **执行前把关** | 校验参数合法、检查权限（放行/拒绝/问用户） | 模型决定调它之后、真正执行之前 |
| **执行** | 真正干活，可以中途报告进度 | 把关通过后 |
| **结果转换** | 把执行产出转成"发给模型的工具结果" | 执行完 |
| **界面渲染** | 在终端里怎么显示这次调用和结果 | 全程（给用户看，和给模型看的分开） |
| **元信息** | 是不是只读？能不能并发？结果多大要落盘？ | 调度时参考 |

下面挑几个**最值得理解的部件**讲。

---

## 三、值得理解的几个工具部件

### ① 执行前两道关：先校验、再问权限

模型决定调一个工具后，**不是立刻就执行**。先过两道：

1. **参数校验**：这次给的参数合法吗？（比如路径对不对、必填项有没有）不合法就直接退回错误，根本不执行。
2. **权限检查**：返回三种结果之一——**放行 / 拒绝 / 问用户**。比如"执行命令"这种危险工具，可能就需要弹出来问用户批不批准。

只有两道都过了，才进真正的执行。

### ② "给模型看的" 和 "给用户看的" 是两层

这是个容易忽略但很重要的设计。工具执行完产出一份原始数据，这份数据会走**两条不同的路**：

- **给用户看的**：在终端里渲染成好看的样子（带颜色、折叠、进度条），用的是原始数据。
- **给模型看的**：通过一个专门的"结果转换"步骤，变成发回对话的"工具结果"——这里可能加上系统提示、可能因为太大而**换成"预览+文件路径"的包装**、可能标记成错误。

**为什么要分两层？** 因为用户和模型要的东西不一样。用户要的是直观好看；模型要的是省 token、信息密度高。同一次工具执行，给用户渲染一个漂亮的 diff，给模型只发一句"文件已更新"——两层分开，各取所需。

### ③ 结果太大要落盘（还是那条 token 经济学）

每个工具都有一个"结果最大多大"的设定。**超过了，结果就被落到磁盘文件，模型只收到一个预览 + 文件路径**（想看全的自己去读那个文件）。这和读文件"太大抛错"、搜索"超限分页"、命令"超大输出落盘"是**同一套**——别让一大坨东西卡进昂贵的、逐轮重发的上下文。

有意思的是**读文件这个工具，把自己的这个上限设成了"无穷大"（即永不落盘）**。为什么？因为读文件的结果本来就是"文件内容"，如果再落盘，就变成"读 → 落成文件 → 又得读这个文件"的死循环了。而且读文件自己已经有分页、大小上限在管，不需要再落一道。**这个细节体现了：通用机制要允许个别工具按自己的情况豁免。**

### ④ 只读 / 能否并发：决定调度

每个工具都自报两个属性：**我是只读的吗？我能和别的工具同时跑吗？** 这两个属性决定了主循环怎么调度它们——只读、无副作用的工具可以**并行**跑（比如同时读三个文件）；会改东西的工具必须**串行**，避免互相踩（比如两个写同一文件的操作并行就乱了）。

## 三点五、Schema 设计与描述工程（让模型正确选择工具的核心）

这一节回答「工具如何让模型知道它的存在、知道该不该调它、知道怎么调它」——这是工具的描述工程，也是所有 agent 平台里最关键的 prompt 工程问题。

### 一个工具的完整「自我介绍」长什么样

每个工具暴露给模型的信息包含三个部分：

**① name（工具名）**
模型在 tool_call 里用这个名字调用工具，同时也是它判断该用哪个工具的第一层线索。CC 的工具名都是动词短语（`read_file`、`execute_command`、`search_code`），语义直接。

**② description（工具说明）**
模型在「该不该调这个工具」时主要依赖这段文本。这是最关键的一层。CC 的描述有几个设计规律：
- **正向说清用途**：「读取指定路径的文件内容，支持按行分页」。
- **主动排除歧义**：Bash 工具的说明里会出现「不要用 cat/head/tail，改用专门的读文件工具」——模型看到这些排除性指令，不容易把读文件的需求错误路由到 Bash 命令。
- **给上限/限制**：「默认 60 秒超时，不允许全盘扫描」——让模型对工具的能力边界有预期。

**③ parameters（参数表，JSON Schema 格式）**
每个参数都有三样东西：
- `type`：数据类型（string / number / boolean / array / object）
- `description`：参数级别的说明文本，告诉模型「这个参数填什么、注意什么」
- 是否 `required`：必填 vs 可选

### 参数描述文本的工程细节

以 Bash 工具的 `description` 参数为例，它的参数说明这样写：

> "Clear, concise description of what this command does in **active voice**. **Never use words like 'complex' or 'risk'** in the description - just describe what it does.
> For simple commands (git, npm, standard CLI tools), keep it **brief (5-10 words)**:
> - ls → "List files in current directory"
> ...
> For commands harder to parse at a glance (piped commands, obscure flags), add enough context..."

这里传递了几层信息给模型：
1. **强制风格**（主动语态、不用"复杂"/"风险"这类词）
2. **给出长度预期**（5-10 词）
3. **给出具体例子**（`ls` → "List files in..."）

模型读到这样的参数说明，能更准确地生成符合预期的参数值。这是「让模型准确调工具」的微观层面。

### strict 模式

工具可以开启 `strict: true`，效果是：API 层面强制要求模型**只能填参数表里定义的字段、类型必须严格匹配**，不能有任何「模型自由发挥」的空间。在需要精确控制参数结构的场景下（特别是有内部字段必须屏蔽的工具），这是一道硬保险。

### searchHint（ToolSearch 场景的专用字段）

当 CC 启用延迟加载（见 [[08-MCP-延迟加载-ToolSearch]]），工具不会一开始就把完整说明暴露给模型，只露名字。模型想用某个工具时，调 ToolSearch 搜索——此时靠的就是 `searchHint` 这个字段：3-10 个词的关键词短语（比如 `"execute shell commands"`），供关键词匹配。这是工具说明的「精简摘要版」，专门为搜索场景设计。

### toAutoClassifierInput（安全分类器通道）

安全分类器需要对工具调用的输入做快速判断（比如判断一条 Bash 命令是否高风险）。工具提供 `toAutoClassifierInput()` 方法，把输入转换成分类器能处理的格式——Bash 工具这里直接返回命令字符串，FileEdit 返回 `文件路径: 新旧内容`。

**这里有一个安全设计**：有些工具的参数里存在纯内部字段（比如「把 sed 命令预览后直接写盘」的内部标志）。这类字段会从模型可见的 schema 里**彻底剔除**——模型的工具定义里根本看不到这个字段，自然无法利用它拼装旁路安全检查的调用。

### 「模型选错工具」怎么防

CC 防止「模型选错工具」主要靠两个层面：

**a) description 里明确排他**：
在工具说明文本里主动写「**用我，不要用 X**」。典型例子是 Bash 工具的 prompt：
- 搜文件：用 Glob 工具（NOT `find` 或 `ls`）
- 搜内容：用 Grep 工具（NOT 命令行 `grep` 或 `rg`）
- 读文件：用 Read 工具（NOT `cat`/`head`/`tail`）
- 改文件：用 Edit 工具（NOT `sed`/`awk`）

这些「NOT」指令是在全局 prompt 里，**不仅在 Bash 自己的说明里**，而是在 system prompt 级别告诉模型「执行工具的优先级排序」。

**b) 名字 + 说明组合让工具边界清晰**：
每个工具的 name 和 description 组合之后，它们的使用场景应该**没有歧义重叠**。比如 Grep（搜内容）和 Glob（搜文件名）这俩做了明确分工，不会让模型纠结选哪个。MCP 工具延迟加载后通过 searchHint 做模糊匹配，也减少了相似工具并列出现时的混淆。

---



读到这会有个问题：为什么不让每个工具就是个简单函数，非要套这么一大套契约？

因为**主循环要统一调度几十种工具**。如果每个工具各搞各的，主循环就得为每个工具写特殊处理。而有了统一契约，**主循环只需要面对"一个抽象的工具对象"**——不管你是读文件还是派子 agent，我都按同一套流程：组装说明 → 校验 → 权限 → 执行 → 转换结果 → 渲染。新增一个工具，只要实现这套契约，主循环一行不用改。

代价是这套契约本身很庞大（几十个部件/钩子）。但换来的是**主循环的极致简洁和工具的即插即用**——这是一个典型的"把复杂性收进契约、换主流程清爽"的工程取舍。

---

## 五、核心 takeaway

1. **主循环骨架极简**：发给模型 → 有工具就执行接回再转 → 没工具就结束。复杂度全在外壳（[[CC-健壮性外壳]]），不在骨架。
2. **工具调用必须配对结果**——协议刚需，少一个对话就卡死。
3. **工具是统一契约对象**：主循环按固定生命周期（说明→校验→权限→执行→转换→渲染）调它的钩子，不关心具体是哪个工具。
4. **给模型看的 vs 给用户看的，两层分开**：用户要直观，模型要省 token，同一次执行各取所需。
5. **结果太大落盘、只读才并发**——还是那套贯穿全局的 token 经济学和安全调度，落到了工具契约这一层。
