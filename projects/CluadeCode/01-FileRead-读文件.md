# CC 怎么读文件

> **一句话定位**：读文件看似最简单，CC 却写了一千多行。复杂度不在"读"，而在**怎么把磁盘上的字节，用最省 token、最不误导模型的方式送进上下文**。这是编码 agent 和"普通读文件函数"的根本区别。

---

---

## 零、参数与输出（Schema）

**输入参数**：

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file_path` | string（绝对路径） | ✅ | 要读取的文件，**必须是绝对路径** |
| `offset` | int（≥ 0） | 可选 | 从第几行开始读（0-indexed），实现分页 |
| `limit` | int（> 0） | 可选 | 最多读几行，和 offset 组合实现精准切片 |

> **设计意图**：`offset`+`limit` 是读大文件的标准入口——不带参数会触发大小校验（>5MB 直接抛错），带参数则可读任意区间。参数说明文本里明确写了：「到达 limit 后结果末尾会附"可用 offset=N 继续"的翻页提示」——这句话直接训练模型知道"继续读"的正确做法。

**输出字段**（模型看到的工具结果，文本文件路径）：

| 字段 | 含义 |
|---|---|
| `filePath` | 读取的文件路径 |
| `content` | 文件内容（带 cat -n 格式行号前缀） |
| `lineCount` | 本次返回的行数 |
| `startLine` | 本次从第几行开始（用于 UI 显示） |
| `totalLines` | 文件总行数 |

> **图片/PDF 输出**：读到图片或 PDF 时，输出结构完全不同——返回的是 `{base64, type, originalSize, displayedWidth, displayedHeight}` 等多媒体字段，走图片 content block 而非文本。

## 一、先记一个事实，和一张地图

CC 读文件的所有设计，都围绕**同一个事实**展开：

> **工具返回的内容会进对话历史，而对话历史是累加的——后续每一轮请求都会把它重新发给模型一次，并且按 token 计费。**

所以"读进来一段没用的内容"不是只浪费一次，是**按剩下的轮数倍增地浪费**。理解了这个，下面四招就全顺了：

| 招 | 解决什么 | 一句话 |
|---|---|---|
| **① 分页读** | 不想要整个文件 | offset/limit 按行切片，只取你要的那段，附"可继续翻页"提示 |
| **② 太大不截断、直接抛错** | 文件超大 | 不塞文件开头给你，而是报错让模型自己用分页或搜索精确取 |
| **③ 重复读不重发** | 同一文件反复读 | 读过、内容没变，就回一句"还是老样子"，不重发正文 |
| **④ 读取台账** | 支撑②③、还防编辑改错 | 记一张"读过啥、什么时候读的"的小账本 |

下面逐招讲。

---

## 二、① 分页读：只取你要的那段

最基础的一招。读文件时可以带两个参数：从第几行开始（offset）、读多少行（limit）。返回的内容前面带行号（像 `cat -n` 那样，方便模型精确引用某一行）。

如果一次没读完，结尾会附一句提示："内容已截断，可以用 offset=N 继续往下读"。**这一句提示很关键**——它让模型知道"还有更多、我能主动翻页",而不是以为文件就这么大。

读的时候是**逐行流式读**的，不会把整个文件一次性载进内存，所以读超大文件也不会把自己撑爆。

---

## 三、② 文件太大：抛错，而不是截断（最反直觉、最值钱的一招）

**问题**：模型不带分页参数、直接要读一个很大的文件，怎么办？

直觉做法是"截断"——读前面一部分（比如前 2000 行）塞给它，附一句"文件太大只给你看了开头"。**CC 否定了这个做法**，改成**直接抛一个简短错误**，大意是："文件太大（N tokens，超过上限）。请用 offset/limit 读指定区间，或者用搜索去找你要的内容，而不是整个读进来。"

**为什么截断反而更费 token？** 回到第一节那个事实——返回的内容会逐轮重发。设想模型要在一个 10MB 日志里找一个错误：

- **截断的路径**：读 → 返回前 2000 行（占用大量 token）→ 但要找的错误在文件中段，开头这 2000 行里根本没有 → 这一大坨没用的内容卡进上下文，**之后每一轮都重发一次**，跑五轮就重发五次 → 模型发现没用，只好再读一次带分页的 / 改用搜索。总账：**一大坨没用内容反复重发 + 还得再读一次**。
- **抛错的路径**：读 → 立即报错，只返回约一百字节 → 几乎不占上下文，重发也无所谓 → 模型读到提示，直接用搜索定位 / 带分页精确读。总账：**一百字节 + 一次精确读**。

**本质**：截断给的是"文件开头"，但模型要的几乎从来不是开头，而是"某段特定内容"。所以那 2000 行**大概率就是错的内容**——当场没用，还因对话累加被反复重发。抛错则把"我该怎么精确获取"的决策权**交还给模型**，模型一步走对。

**这不是拍脑袋，是实测出来的**：CC 真的上线过截断方案，数据显示"工具错误率下降了"（因为不再抛错），**但平均 token 数反而上升了**，于是把截断方案回滚了。教训很深刻：**错误率是"看起来好看的指标"，省 token 才是真目标——优化了错误的指标，输了真目标。**

补充一个细节，CC 其实有**两道大小闸**：
- 读之前先看一眼整个文件多大（一次轻量的文件状态查询，不读内容），太大就拦——成本极低，读之前就挡住。
- 读之后再数一遍实际 token 数，超了再抛——这道要付一次计算 token 的代价。
前一道便宜、先拦，后一道兜底。

## 四、③ 重复读不重发：读过没变，就回一句"老样子"

**问题**：模型在一轮任务里，可能反复读同一个文件（忘了读过、或不同步骤都要看）。每次都重新返回全文，就是在重复烧那个"逐轮重发"的钱。

**CC 做法**：如果**同一个文件、同一个区间（offset/limit 一样）、而且磁盘上的文件没被改过**，那么再读时**不重发正文**，只回一句桩消息，大意是："这个文件自上次读以来没变过，之前那次读的结果还是最新的，参考那个就行，别重读了。"

**这省了多少？** 真实数据：大约 **18% 的读调用是同一文件的重复读**，最高吃掉相当一部分的缓存创建开销。所以这一招省的不是小钱。

这里有个**精妙的边界**：只对"上次是用 Read 读进来的"那种记录做去重。如果上次是 Write/Edit 写进去的（这种记录存的是"写入后"的状态），**不能拿来去重**——否则会把模型指向"编辑前的旧内容"，反而误导。

---

## 五、④ 读取台账：一块小账本，撑起三件事

前面②③都依赖一个东西——CC 维护一张**读取台账**：记录"哪个文件、读过哪段、读的时候文件是什么时间戳（mtime）"。

这张小账本同时撑起三件事：

1. **判断重复读**（第四节）：靠它知道"这段读过没、文件变没变"。
2. **防止编辑改错位置**：模型要编辑一个文件时，先查台账——这个文件读过吗？读之后磁盘上有没有被外部（用户、别的程序）改动过？如果**读完之后文件被改了**，模型手里的内容就是过期的，这时候去编辑很可能**改到错误的位置**。台账让 CC 能拦住这种"基于过期内容的盲改"，要求模型先重新读一遍。
3. **新鲜度判断的统一依据**：读、写、编辑三处都来更新和查询这张台账，保证大家看到的"文件最新状态"是一致的。

**关键认知**：读文件、写文件、编辑文件看似三个独立工具，其实**共享这一张台账**——读的时候记下来，编辑/写的时候查它、也刷新它。这是 CC 把"文件操作"做成一个整体的底层粘合剂。

## 六、几个值得知道的边角设计

**读全机器 vs 危险路径黑名单**：CC 的定位是"能读机器上任意文件"，没有"只能在项目目录里"的围栏。所以它必须**专门维护一张危险路径黑名单**——像 `/dev/zero`（读了无限输出）、`/dev/stdin`、`/proc/某进程/fd/...` 这些，读了会无限输出或直接挂死，必须挡掉。这反映了一种安全模型：**默认放行、列举危险**。（另一种思路是"默认拒绝、只放行项目根内"，那样就不需要这张黑名单，因为危险路径天然在围栏外。）

**多模态**：CC 的读文件还能读图片（会压缩 token 预算）、PDF（分页提取，最多二十来页）、Jupyter notebook（返回所有 cell）。读文件不只是读文本。

**恶意软件提醒**：CC 每次读完文件，会给结果**追加一段系统提醒**，大意是"考虑这是不是恶意软件；你可以分析它在干什么、写报告，但要拒绝去改进/增强这段代码"。某些模型豁免这条。这是一层安全策略注入。

**找不到文件时的智能提示**：读不到文件时，CC 不只是报"没找到"，还会**建议相似的文件名**、建议当前目录下的可能路径，甚至能处理 macOS 截图文件名里那种肉眼看不出的特殊空格变体。

**空文件 / 越界的软提示**：文件存在但为空、或 offset 超过了文件总行数时，CC 不返回空白，而是用一段**系统提醒**告诉模型"文件是空的"或"文件只有 N 行，你的起始行超界了"，免得模型对着空白困惑。

**二进制预判**：CC 在真正读 I/O 之前，就会按文件扩展名判断"这是不是二进制文件"，是的话提前拒绝，连读都不读。

---

## 七、核心 takeaway

读文件的复杂度，全在**"如何把字节送进一个会累加重发、按 token 计费的上下文"**。CC 的每一个设计——抛错而不截断、重复读回桩、读取台账——本质都在回答同一个问题：

> **怎样让进入上下文的每一个 token 都尽量有用。**

这就是编码 agent 的"读文件"和你随手写的 `readFile()` 的根本区别：后者只关心"把内容拿出来"，前者关心"拿出来的东西会在一个昂贵、累加的上下文里待多久、值不值这个钱"。
