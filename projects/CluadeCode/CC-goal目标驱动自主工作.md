# CC 的 goal：目标驱动的自主工作

> **一句话定位**：`/goal` 让你设一个「完成条件」，Claude 会**自己一轮一轮干下去、不把控制权还给你**，直到条件达成。每轮结束后由一个**独立的小模型当裁判**检查"达成没"。这是 CC「轻量目标驱动」的代表——不规划步骤，只验收结果。
> （需要 Claude Code v2.1.139+。本篇基于官方文档，不是源码还原。）

---

## 一、先记一张地图

| 要素 | 是什么 |
|---|---|
| **① 完成条件** | 你给一句"什么算做完"（如"所有测试通过且 lint 干净"），它本身就是给 Claude 的指令 |
| **② 自动续轮** | 每轮干完，不还控制权给你——条件没达成就自动开下一轮 |
| **③ 独立评估器** | 每轮后一个**新鲜的小模型**（默认 Haiku）检查条件，返回 是/否 + 一句理由 |
| **④ 自动收尾** | 条件达成→目标自动清除；没达成→把"理由"作为下一轮的指导继续干 |

核心一句：**你只说"什么算完成"，Claude 自己反复干，一个独立裁判每轮验收，达标自动停。**

---

## 二、它怎么转（一个完整循环）

```
你：/goal 所有 test/auth 测试通过且 lint 干净
  ↓ 设目标会"立即开一轮"，条件本身当指令（不用再单独发提示）
Claude 干第一轮（跑测试、改代码……）
  ↓ 一轮结束
评估器（小模型）：读对话记录 → 条件达成没？
  ├─ 否 → 返回一句理由（"还有 3 个测试失败"）→ 作为下一轮指导 → Claude 自动开下一轮
  └─ 是 → 目标自动清除，记一笔"已达成" → 控制权还给你
```

期间界面有个 `◎ /goal active` 指示器显示目标跑了多久。运行不带参数的 `/goal` 能看当前状态（条件、跑了几轮、花了多少 token、评估器最近的理由）。

---

## 三、三个最精妙的设计点

### ① 它不是 plan 引擎——极简，只验收不规划

`/goal` **没有任务分解、没有依赖图（DAG）**。它极简到只有两样：**一个完成条件 + 每轮判断达没达成**。

对比一下"目标分解→分步执行"那种重型 plan 引擎：那种要先把目标拆成任务、排依赖、按序执行、失败重规划。`/goal` 全不要——它**不替模型规划步骤，只给一个"什么算完成"，让模型自由推进、到点了有人验收**。

> 这正是「模型越强、越不需要僵硬规划」的体现。能力够强的模型自己会拆解、会调整，外部只需要给它一个**明确的终点**和一个**客观的验收**，不需要替它编排每一步。`/goal` 把"自主多回合推进"做成了轻量的、目标驱动的形态。

### ② 由"新鲜的小模型"验收，不是干活的模型自评

这是最关键的一点。判断"做完了没"的，**不是刚才干活的那个模型，而是一个没参与干活、只看结果的独立小模型**。

为什么重要？因为**干活的模型容易"自我感觉良好就收工"**——它倾向于认为自己做完了。换一个独立裁判来验收，就避开了这种自评偏差。官方原话：「完成由一个新鲜的模型而不是执行工作的模型决定」。

> 这呼应了 [[05-TodoWrite-vs-plan-DAG]] 里那个「验证助推」的思想——**你不能自封完成，要由独立的验证者裁决**。`/goal` 把这个思想做成了核心机制：每轮都有一个独立裁判判分。

### ③ 它是 Stop hook 的"会话级包装"——复用已有积木

`/goal` **没有另造一套机制**，而是把两个我们已经学过的积木拼起来：
- **Stop hook**（[[CC-用户事件钩子]]）：每轮结束时触发的钩子。
- **提示型钩子用小模型判断**：把"条件达成没"下放给便宜的小模型。

所以 `/goal` 本质是「一个会话范围的、基于提示的 Stop hook」——只在当前会话生效，你输一个条件它就临时挂上。这是 CC 一贯的风格：**用已有积木拼新功能，不重复造轮子**。

---

## 四、一个关键约束：评估器只能看"对话里呈现的内容"

评估器**不能自己跑命令、不能读文件**——它只是个"看对话记录判分"的裁判，不是"亲自下场查"的检察官。所以**条件必须写成"干活的模型能在对话里证明的东西"**：

- ✅ "所有 test/auth 测试通过"——有效。因为 Claude 会跑测试，**结果出现在对话里**供评估器读。
- ❌ 写一个需要评估器自己去验证、但它做不到的条件——没法判断。

好条件通常有三要素：
1. **可测量的终态**：测试结果、构建退出码、文件数、空队列。
2. **明确的证明方式**：比如"npm test 退出 0"、"git status 干净"。
3. **重要约束**：过程中不许动的东西，比如"不许改其他测试文件"。

条件最多 4000 字符。想限制时长可以在条件里加"或 20 轮后停"这种子句。

## 五、和另外两种"保持会话自己跑"的方式对比

CC 有三种让会话在没有你逐步提示时继续跑的方式：

| 方式 | 下一轮何时开始 | 谁决定停止 |
|---|---|---|
| **/goal** | 前一轮完成时 | **新鲜小模型**确认条件满足 |
| **/loop** | 时间间隔到了 | 你停它 / Claude 自觉完成 |
| **Stop hook** | 前一轮完成时 | 你自己的脚本或提示 |

区别：
- `/goal` 是**会话级快捷方式**（输个条件、仅当前会话有效），且用**独立评估器客观验收**。
- `/loop` 是**按时间间隔**重跑（不是按条件）。
- `Stop hook` 存在**配置文件里**、对其范围内每个会话都生效，验收逻辑你自己写。

还有个互补关系：**自动模式**（auto mode）消除"每个工具的批准提示"，`/goal` 消除"每个回合的提示"——两者叠加就是"全程无人值守地朝目标干"。

## 六、其他实用细节

- **每会话只能一个活跃目标**：再设一个会替换掉旧的。
- **`/goal clear`** 提前清除（stop/off/reset/none/cancel 都是别名）；`/clear` 开新对话也会清掉目标。
- **非交互式可用**：`claude -p "/goal ..."` 一次调用跑到完成；Ctrl+C 中断。
- **恢复会话**：会话结束时还活跃的目标，`--resume`/`--continue` 时会恢复（条件保留，但轮数/计时/token 基线重置）。
- **要求工作区受信任**：因为评估器是 hooks 系统的一部分（hooks 能跑任意逻辑，所以要信任）。`disableAllHooks` 时 `/goal` 不可用。
- **评估成本极低**：评估走小快模型，相比主回合的花费通常可忽略。

---

## 七、核心 takeaway

1. **`/goal` = 设一个完成条件，Claude 自动一轮轮干到达成**，不用你逐步提示。
2. **它不是 plan 引擎**：没有任务分解/DAG，极简到只有"条件 + 每轮验收"——体现"模型越强越不需要僵硬规划，只需明确终点+客观验收"。
3. **独立小模型当裁判**：完成由没参与干活的新鲜模型判断，避开"干活模型自我感觉良好就收工"的偏差。
4. **是 Stop hook 的会话级包装**：复用"每轮触发的钩子 + 小模型判断"两个已有积木，不重复造轮子。
5. **评估器只看对话呈现的内容**：所以条件要写成"模型能在对话里证明的东西"（跑测试、退出码、git 状态）。
6. **三种自主方式**：/goal（按条件验收）、/loop（按时间间隔）、Stop hook（你自定义）——互补，可叠加自动模式实现全程无人值守。
