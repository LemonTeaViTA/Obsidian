# CC 怎么派子 agent（上下文隔离检索）

> **一句话定位**：把"开放式、要翻几十个文件、来回搜很多轮"的脏活，当成**一次工具调用**整包下放给一个子 agent。子 agent 自己折腾完，**只把提炼后的结论回传**，中间翻过的几十个文件原文**根本不进主 agent 的上下文**。

---

## 一、先想清楚它解决什么痛点

主对话的上下文是**累加重发**的（见 [[01-FileRead-读文件]] 那条主线）。而"开放式检索"会产生**一大堆一次性的中间垃圾**。设想这个场景：

> 主 agent 要"在整个项目里找鉴权逻辑在哪" → 搜出 30 个文件 → 读了其中 12 个 → 发现 10 个不相关。

如果主 agent 自己干这件事，那 **12 个文件的完整内容全卡进了主对话**，之后每一轮都重发，既烧 token 又干扰主线推理——而最后有用的其实只有一句"鉴权在某文件第 42 行"。

子 agent 就是来解决这个的：

> 主 agent 说"去找鉴权逻辑在哪" → **派一个子 agent**去干 → 子 agent 用它**自己的、用完即弃的上下文**去搜去读，折腾完 → **只回主 agent 一句**："鉴权在某文件第 42 行，走 JWT，配置在另一个文件第 88 行"。

主 agent 的上下文只多了这一句话，干干净净。**几十个文件的翻找垃圾，全被挡在了主上下文之外。**

> 注意区分：这是**一个任务内部**的上下文隔离，和"开新对话窗口、靠记忆续上"是两回事（那是跨对话的隔离）。

---

## 二、地图：子 agent 的四条核心机制

CC 的子 agent 工具堆了很多模式，但**真正的核心只有四条**：

| 机制 | 解决什么 | 怎么做 |
|---|---|---|
| **① 上下文隔离** | 子 agent 不该看到主对话的一堆历史 | 子 agent 拿**全新的空白对话**，只有你给它的那条指令 |
| **② 只回传结论** | 中间垃圾不能流回主对话 | 子 agent 跑完，**只把最后一句结论回传**，完整过程不回传 |
| **③ 防递归** | 子 agent 不能再无限派孙 agent | 子 agent 看不到"派 agent"这个工具 |
| **④ 工具裁剪** | 检索 agent 不该改文件 | 只给它只读的搜/读工具，不给写/执行 |

逐条讲。

### ① 上下文隔离：给子 agent 一张白纸

派子 agent 时，子 agent 拿到的是**一份全新的、空白的对话历史**——里面只有一条消息：**你交给它的那个任务指令**。主 agent 的系统提示、主对话的全部历史、之前所有工具结果，**统统不传给它**。

这是"隔离"的核心：子 agent 不被主对话的一大堆上下文干扰，**从一张白纸开始**专注做这一件事。反过来，它在白纸上涂的那一堆（搜了什么、读了什么），也**不会沾染主对话**。

### ② 只回传结论：隔离省 token 的关键

子 agent 跑完之后，**只把它最后说的那句话（结论）回传给主 agent**。它中间翻了多少文件、搜了多少次——那些全留在它自己那张用完即弃的白纸上，**不回传**。

这才是省 token 的关键所在：如果把子 agent 的完整过程也回传，那和主 agent 自己干就没区别了。**正因为只回结论、不回过程，几十个文件的中间垃圾才真正被挡住。** 回传的结论也有长度上限兜底。

### ③ 防递归：子 agent 不能再派孙 agent

如果子 agent 还能再派子 agent，理论上会无限套娃下去。CC 的做法很干净：**子 agent 的工具清单里，根本没有"派 agent"这个工具**——它看不到，自然就调不了。（除此之外还有标记位等兜底，但"看不到"是主闸。）

### ④ 工具裁剪：检索 agent 只读不写

CC 内置的检索型子 agent，**只给它只读的工具**（读文件、搜内容、找文件名、跑只读命令），**不给写文件、改文件、执行有副作用命令的工具**——因为它的活就是"找东西、提炼结论"，不该去改动项目。

还有个省 token 的小动作：派检索子 agent 时，连主 agent 的项目说明文件、git 状态这些都从它的上下文里删掉——这一项基于海量实测，省下的 token 相当可观。

## 三、配套：什么时候该派、什么时候别派

**轮次上限**：子 agent 也会陷在循环里出不来，所以有最大轮数，跑飞了优雅退出。

**prompt 里的使用纪律**（这点很重要，决定了子 agent 不被滥用）：CC 明确告诉模型**什么时候别派子 agent**——

- 已经知道某个文件的具体路径 → **直接读**，别派。
- 要找某个类/函数的定义 → **直接搜**，别派。
- 只在两三个文件范围内找 → **直接读**，别派。
- **只有"开放式、要来回翻很多文件很多轮"才值得派子 agent**。

逻辑很清楚：派子 agent 本身有成本（它要跑一整个自己的循环）。如果一两步就能搞定的事也派，那是杀鸡用牛刀。子 agent 的价值在于**用一次调用，把一段本会产生大量中间垃圾的开放检索整个隔离出去**。

---

## 四、和"网页摘要"是同一个思想

读到这会发现，子 agent 和 [web_fetch 的 AI 摘要](07-WebFetch-网页抓取)本质是**同一招**：

> **把"读一大堆原始材料、提炼出结论"这种脏活下放出去，主模型只接干净的结论，不被原始材料淹没。**

区别只在下放的对象：
- web_fetch 下放给"一个小模型一次调用"（读一个长网页 → 浓缩）。
- 子 agent 下放给"一个独立 agent 多轮折腾"（翻几十个文件 → 提炼）。

两者都在回答那条贯穿全局的问题：**怎样让进入主对话的每个 token 都尽量有用**——原始材料不进来，只让结论进来。

---

## 五、核心 takeaway

1. **子 agent = 让模型自己决定何时"下放脏活、只收结论"**，把开放式检索的中间垃圾挡在主对话之外。
2. **四条核心机制**：全新空白对话（隔离）、只回传结论（省 token 的关键）、看不到"派 agent"工具（防递归）、只给只读工具（检索不该改文件）。
3. **只回结论、不回过程**——这是隔离能省 token 的真正原因；回了过程就和自己干没区别。
4. **prompt 教模型别滥用**：一两步能搞定的别派，只有开放式多轮检索才值得。
5. **和网页摘要同一思想**：脏活下放、主模型只接干净结论。
