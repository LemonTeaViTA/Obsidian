# CC 的 system prompt 是怎么拼出来的

> **一句话定位**：发给模型的"系统提示"不是一坨写死的文本，而是**一段段拼起来的**。而且拼的时候有个核心讲究——**绝大部分段要"跨轮稳定不变"，只有极少数允许每轮变**。为什么？为了命中平台的"前缀缓存"，省钱省延迟。这是和"省 token"并列的第二条经济学主线。

---

## 一、先理解"前缀缓存"——这是整篇的动机

每轮对话，发给模型的内容是：**系统提示 + 整个对话历史**。其中**系统提示永远在最前面**。

平台（模型 API）有个机制叫**前缀缓存**：如果你这次请求的**开头一大段**和上次**一模一样**，平台就能**复用上次的计算结果**，不用重新处理这一段——**又快又便宜**（缓存命中的部分计费极低）。

精确点说，机制是**缓存断点**：客户端在请求里打一个"缓存标记"，标记**之前的全部内容**（系统提示 + 工具定义 + 到标记为止的对话历史）算作**一个可缓存的前缀块**，平台缓存这一整块的计算结果。

但缓存有个死规矩：**它是"前缀"匹配——从头比，前面没变就命中、一旦遇到第一个不一样的地方，从那个点往后全失效**。由此推出两条：

- **在末尾追加**（正常对话每轮把新消息加在最后）→ 前面字节没变 → **前面全命中**，只算新追加的。这是正常对话能持续省钱的原因。
- **在中间插入**（比如改了系统提示、或重写了历史）→ 插入点之后的字节全错位 → **插入点之前命中、之后全部重算**。

**关键推论**：系统提示在最前面。它一旦有一个字每轮在变（比如塞个实时时间戳），就等于"在最前面动了刀"——**后面什么都白缓存了**。

所以 CC 拼系统提示时的最高纪律是：**让它尽量跨轮一字不变。**

> 顺带回答一个常见疑问："动态注入的内容（系统提醒、诊断、通知）会不会破坏缓存？" 不会——因为 CC 把动态内容**追加在对话末尾**，不是插进系统提示或历史中间。追加在末尾，前面字节没变，缓存照样命中，只有新加的那条要算。**CC 刻意只往末尾加、不往中间插，就是为了保护前缀缓存。**

## 一点五、先分清"两层缓存"（一个关键澄清）

很容易把两件不同的事揉在一起，先拆开：

| | 平台前缀缓存 | 客户端分段缓存 |
|---|---|---|
| 在哪 | **模型平台那边**（服务器） | **客户端这边**（CC 自己内存里） |
| 缓存什么 | 一段前缀的**计算结果** | 每个段**算出来的那段文本** |
| 谁的功劳 | **模型/平台的效果** | CC 客户端自己的优化 |
| 省什么 | 省"模型重新计算" | 省"客户端重新生成那段文本" |

**两层是不同的东西，但有协作关系**：

- **平台前缀缓存**是模型的能力。客户端在这件事上只干两件：打标记告诉平台"缓存到这"、**保持字节跨轮稳定**。真正缓存计算结果的是平台。
- **客户端分段缓存**是 CC 自己的优化（下面第三、四节讲的"每段算一次存住"）。它和模型无关。

**一个重要结论（容易想偏）**：对平台前缀缓存来说，**它根本不认识你的"段"**——它眼里就是一长串字节，纯粹"前面没变就命中"。所以**"分段"本身不给平台缓存任何位置上的好处**——只要前面字节不变、改的都在后面，前面就命中，跟你分不分段无关。

那真正帮平台缓存的是什么？是**排序**——把"绝不会变的"放最前、"可能会变的"放最后（就是"静态前、动态后"）。这样万一某个易变段变了，**坏掉的前缀最短**。这是"排序"的功劳，不是"分段"的功劳。

**那 CC 为什么还要分段？** 因为分段是**客户端的"治理结构"**，目的有两个，都和"平台缓存的位置"无关：
1. **省客户端自己的重算**：有些段算起来要查磁盘、跑命令（探测环境、git 状态）——算一次存住，省 I/O。
2. **冻结字节、防漂移**：如果每轮重新生成那段文本，可能因某个细节悄悄变一点点，导致前缀字节漂移、平台缓存 miss。"算一次就冻住"等于**给平台缓存上保险——保证这些字节绝不漂移**。

所以两层的关系是：**客户端分段缓存（冻结字节）→ 服务于 → 平台前缀缓存（能稳定命中）。** 客户端负责把字节冻得稳如泰山，平台负责缓存这些冻住的字节的计算结果。下面讲的"分段 + 标记 + 破缓存写理由"，本质都是这套"管住字节别乱漂"的治理机制。

## 二、地图：系统提示的两个设计要点

| 要点 | 是什么 |
|---|---|
| **① 分段拼装 + 优先级** | 系统提示由多个"段"按优先级拼成（身份、工具纪律、环境信息……） |
| **② 每段标记"可缓存"还是"必须每轮变"** | 绝大多数段算一次就缓存住、跨轮不变；极少数"必须实时"的段才允许每轮重算，且要写明理由 |

②是精华，但先讲①。

---

## 三、① 分段拼装：系统提示由哪些段组成

系统提示是一个**段的列表拼起来**的。大致包含这些内容（确定看到的）：

- **身份与语气**：你是谁、该用什么风格回答、各种行为纪律。
- **工具使用纪律**：什么时候用哪个工具、什么时候别用（比如"读文件别用 cat、用专门的读文件工具"——这些纪律就写在系统提示里）。
- **环境信息**：当前**工作目录**、**是不是 git 仓库**、**操作系统平台**、**你用的是哪个模型**（名字+ID）、**知识截止时间**等。
- **项目记忆**：项目特定的约定（比如项目根目录的说明文件内容）。
- 还有一些功能性的段（技能命令、特定模式的额外指令等）。

**拼装有优先级**（从高到低，命中一个就用它）：
1. 完全覆盖（如果指定了"用这段当系统提示"，就只用它）。
2. 协调者模式的专用提示（特定模式下）。
3. 某个 agent 自带的提示（如果当前是某个专门 agent）。
4. 用户自定义提示。
5. **默认提示**（最常见的情况）。
- 最后，如果有"追加提示"，拼在末尾。

普通对话走的是"默认提示"那条。

---

## 四、② 每段标记"可缓存 / 必须每轮变"（精华）

这是 CC 应对前缀缓存的核心机制。每个段在定义时，会被标成两类之一：

### 可缓存段（绝大多数段）

> **算一次，结果缓存住，之后每轮直接复用缓存，直到 `/clear` 或 `/compact` 才重算。**

身份、工具纪律、环境信息这些——它们**在一次会话里基本不变**（你的工作目录、操作系统、用的模型，一个会话里就是固定的）。所以算一次就缓存，**保证每轮拼出来的这些段逐字节相同** → 前缀缓存命中。

注意一个有意思的取舍：像"当前日期"这种**理论上会变**的信息，也被当成**可缓存**——因为一次会话通常就几小时，日期变了也无所谓，**为了缓存稳定，宁可让它"算一次就定住"**，不追求实时。这体现了设计的优先级：**缓存稳定 > 信息绝对实时**。

### 必须每轮重算的段（极少数，要写明理由）

> 有些信息**确实必须每轮反映最新状态**，这种段被特别标记成"每轮重算"。

但 CC 对这类段**极其克制**——定义它们要用一个**带"危险"字样的特殊方式，而且强制要求写一句"为什么必须破缓存"的理由**。因为每多一个这种段，就多一份"破坏前缀缓存"的风险。**这个"写理由"的硬要求，本质是给"破缓存"这件事设了一道审查关卡**——逼开发者想清楚"这真的值得牺牲缓存吗"。

---

## 五、缓存什么时候失效（清空重来）

可缓存段会一直用缓存，直到两个时刻才清空重算：

- **`/clear`**：用户主动清空对话、开始新的。
- **`/compact`**：上下文被压缩（[[CC-上下文压缩]]）。压缩本身就重写了对话内容，缓存反正要重建，顺带把系统提示的段缓存也清了。

平时（普通对话往复）这些段一直缓存着，跨轮稳定——这正是前缀缓存能持续命中的原因。

---

## 六、把它和别处串起来

前缀缓存这条线，其实在前面几篇反复露过脸，只是没点透：

- 工具定义**按名字排序**输出——为什么？因为工具清单也在请求的前缀里，**顺序每轮一变，前缀就变了，缓存失效**。排序保证它跨轮字节稳定。
- 模型切换备用模型时要**擦掉思考签名**——也和保持请求合法、不无谓触发重算有关。
- 系统提示**跨轮稳定**——就是这一篇。

所以 CC 有**两条并列的经济学主线**：
1. **省 token**（别让没用的内容进上下文、逐轮重发）——前面大部分篇章讲的。
2. **保前缀缓存命中**（别让请求开头的字节每轮变）——这一篇讲的。

两条都是在"对话会逐轮重发、按量计费"这个事实下，从不同角度省钱：一个省"发多少内容"，一个省"重算多少"。

---

## 七、核心 takeaway

1. **系统提示是分段拼的**，不是一坨死文本；拼装有优先级（覆盖 > 模式 > agent > 自定义 > 默认，末尾追加）。
2. **前缀缓存是核心动机**：系统提示在请求最前面，只要它逐字节跨轮不变，平台就能复用计算、省钱省延迟；一旦变了，从变的那点往后缓存全失效。
3. **每段标记可缓存 / 必须每轮变**：绝大多数可缓存（算一次定住，到 /clear 或 /compact 才重算）；极少数必须实时的才每轮重算，且**强制写明破缓存的理由**——给"破缓存"设审查关卡。
4. **宁可信息不那么实时，也要保缓存稳定**（比如日期算一次就定住）——优先级是"缓存稳定 > 绝对实时"。
5. **这是和"省 token"并列的第二条经济学主线**：省 token 管"发多少内容"，保缓存管"重算多少"。
