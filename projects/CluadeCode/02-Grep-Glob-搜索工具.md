# CC 怎么搜索（Grep / Glob）

> **一句话定位**：CC 的搜索不是"跑个 grep 给你"，而是一套**职责分明的三件套 + 一圈 token 经济学和工程容错**。核心仍是那条贯穿全局的主线——搜出来的结果也会进上下文、逐轮重发，所以必须给硬上限。

---

---

## 零、参数与输出（Schema）

**Grep 输入参数**（完整 12 个参数）：

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pattern` | string（regex） | ✅ | 正则表达式，走 ripgrep 语法（注意：Go 语言的 `interface{}` 要写成 `interface\{\}` 转义） |
| `path` | string | 可选 | 搜索路径，默认 cwd |
| `glob` | string | 可选 | 文件名过滤，等同 `rg --glob`（如 `*.ts,*.tsx`） |
| `output_mode` | enum | 可选 | `files_with_matches`（默认，只返回文件名列表）/ `content`（返回匹配行内容）/ `count`（每文件匹配数） |
| `context` / `-C` | int | 可选 | 匹配行前后各几行上下文，仅 `content` 模式有效（`-C` 是 `context` 的别名） |
| `-B` | int | 可选 | 匹配行之前几行，仅 `content` 模式 |
| `-A` | int | 可选 | 匹配行之后几行，仅 `content` 模式 |
| `-n` | boolean | 可选 | 显示行号（默认 true），仅 `content` 模式 |
| `-i` | boolean | 可选 | 忽略大小写 |
| `type` | string | 可选 | 文件类型过滤（`js`/`py`/`java`/`go`/`rust` 等），等同 `rg --type`，比 glob 更高效 |
| `head_limit` | int | 可选 | 最多返回多少条（默认 250），防止超大结果撑爆上下文 |
| `offset` | int | 可选 | 分页偏移——跳过前 N 条再取 head_limit，实现翻页 |
| `multiline` | boolean | 可选 | 跨行匹配（等同 `rg -U --multiline-dotall`），`.` 可匹配换行符 |

> **output_mode 的选择逻辑**：默认 `files_with_matches` 最省 token——只知道哪些文件里有匹配。需要看具体哪行时才切 `content`。模型应该从粗到细：先用 `files_with_matches` 确认范围，再对特定文件用 `content` 定位行号，最后用 read_file 带 offset 精读。

> **head_limit + offset 翻页**：只有真发生截断才会回 `appliedLimit` 字段，模型据此判断「还有更多，需要翻页」。

**Glob 输入参数**（只有 3 个）：

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pattern` | string | ✅ | glob 模式（如 `**/*.ts`、`src/**/*.{js,ts}`） |
| `path` | string | 可选 | 搜索根目录，默认 cwd |
| `max_results` | int | 可选 | 最多返回多少文件（默认约 100） |

## 一、先记一张地图：搜索是三件套，职责正交

CC 把"搜索"拆成三个独立工具，各管一件事，**互不替代、互相配合**：

| 工具 | 找什么 | 怎么用 |
|---|---|---|
| **Grep** | 文件**内容**（哪一行匹配某个正则） | 定位到"某文件第几行" |
| **Glob** | 文件**名/路径**（哪些文件名匹配某个模式） | 找出"有哪些文件" |
| **Agent（子 agent）** | 开放式、需要来回搜很多轮才能搞清的问题 | 把"反复搜+读"整包下放 |

它们怎么配合，是一条典型工作流：

> 先用 **Grep** 找到"错误在 `xxx.java` 第 42 行" → 再用**读文件**带上 `offset=42` 精读那一段的上下文。

**Grep 负责定位、读文件负责精读**，两个独立工具拼成工作流——不是"读文件依赖搜索"。而如果一个问题需要**反复搜很多轮**（搜了看、看了再换关键词搜），CC 的纪律是**别让主对话反复 grep，把它整包交给子 agent**去搞，只要结论回来。（子 agent 怎么回事，见 [[03-Agent-子agent工具]]。）

## 二、Grep：找内容

### 底层是 ripgrep，工具层只做"穿插"

Grep 底下跑的是 **ripgrep**（业界最快的搜索工具）子进程。CC **不自己造搜索轮子**，而是在 ripgrep 外面"穿插"上自己关心的东西：权限过滤、结果上限、分页、多种输出格式、路径省 token。

它能搜的花样不少：正则匹配、限定文件类型（只搜 js/py/java…）、限定某种文件名模式、忽略大小写、显示匹配行的前后几行上下文、跨行匹配等。

### 三种"我要什么粒度"的输出

- **只要文件名**（默认）：告诉我哪些文件里有匹配就行，不要正文。
- **要匹配的行**：连行号带内容一起给我。
- **要计数**：每个文件匹配了几处。

默认给"只要文件名"——因为这是最省 token 的粒度，模型拿到文件名后可以再决定要不要细看。

### 关键：结果上限（和读文件同一套 token 经济学）

Grep 的结果也会进对话、逐轮重发，所以**必须有硬上限**：默认最多返回约 250 条，整体结果有一个体积上限（约 20KB）。

精妙的一点：**只有真的因为超限被截断时**，才会附一个标记告诉模型"还有更多，你可以翻页继续看"。没截断就不啰嗦。这和读文件的"分页提示"是同一个思路——既给硬上限防止上下文膨胀，又留一个"还能往下取"的逃生口。

### 一个反直觉的排序：找文件名时"最新改的排前"

当 Grep 返回"哪些文件有匹配"的列表时，它会**按文件的最后修改时间降序排**——最近改过的文件排在最前面。逻辑是：**你正在处理的任务，相关文件往往就是最近动过的那些**，把它们排前面，模型第一眼看到的就是最可能相关的。

（这里有个 CC 自己的"不对称坑"：Grep 的文件列表是**最新优先**，但下面要讲的 Glob 默认却是**最旧优先**——同样是"按修改时间排"，两个工具方向相反。这是 CC 的真实行为，记住别想当然。）

### 工程容错（值得一看的细节）

- **超时保护**：默认搜 20 秒还没完就掐断；在文件 I/O 慢得多的环境（比如 WSL）放宽到 60 秒。
- **掐进程分两步**：先温和地请它退出，给几秒；还赖着不走（卡在阻塞 I/O 的搜索），就强杀。
- **遇到资源不足自动降速重试**：在线程受限的环境（Docker/CI），第一次因资源不够失败，会自动降到单线程再试一次。
- **超时但没结果时抛错，而不是返回"空"**：这点很重要——"搜索没跑完"和"真的没有匹配"是两码事。如果超时就静默返回空，模型会误以为"确实没有"，从而走错方向。所以 CC 宁可抛错，让模型知道"这次没搜完"。
- 默认**尊重 .gitignore**（不去搜那些本就该忽略的文件），并额外硬排版本控制目录（`.git` 等）。
- 超长的单行（比如压缩过的代码、base64）会被截断，免得一行脏数据污染整个结果。

### 一条 prompt 纪律

CC 明确告诉模型：**搜索永远用 Grep 工具，不要自己去命令行里敲 `grep` 或 `rg`**。原因有二：Grep 工具已经把权限和性能都优化好了；而且走工具能让用户看清、能审批。

## 三、Glob：找文件名

比 Grep 简单得多，就干一件事：**按文件名/路径模式，列出匹配的文件**。底下同样是 ripgrep（用它的"只列文件"模式）。

几个要点：

- **默认最多返回约 100 个文件**，超了就截断并提示"换个更具体的路径或模式吧"。
- 排序**默认是最旧优先**（升序）——和 Grep 的最新优先相反，这就是上面说的那个不对称坑。
- **默认不尊重 .gitignore**（和 Grep 相反！）。为什么？因为**找文件**的时候，模型常常**就是要看到** `node_modules` 这类被 gitignore 的目录里有什么。这是 CC 想清楚的取舍：搜内容时该躲开噪音目录，找文件名时反而常要看全。

---

## 四、为什么搜索要这么讲究：还是那条主线

读到这里会发现，搜索工具的设计逻辑和[[01-FileRead-读文件|读文件]]一模一样：

> **搜出来的结果会进上下文、按 token 计费、逐轮重发。**

所以 CC 给搜索上的那些"上限 + 分页 + 超时抛错"，和读文件的"抛错而非截断、分页提示"是**完全同源的 token 经济学**。区别只是：读文件管的是"一个文件的内容"，搜索管的是"一堆匹配结果"——但"别让没用的东西卡进昂贵的上下文反复重发"这个核心目标，是一致的。

---

## 五、核心 takeaway

1. **搜索是三件套，职责正交**：Grep 找内容、Glob 找文件名、子 agent 管开放式多轮搜索。开放搜索别在主对话里反复 grep，整包下放给子 agent。
2. **同样"按修改时间排"，Grep 最新优先、Glob 最旧优先**——CC 真实存在的不对称，别想当然。
3. **搜索结果和读文件同源**：都进上下文逐轮重发，所以都有"硬上限 + 分页逃生口"。
4. **超时要和"无匹配"分开**：超时没结果就抛错，绝不静默返回空——否则模型会把"没搜完"误当成"真没有"。
