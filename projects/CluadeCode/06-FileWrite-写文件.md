# CC 怎么写文件

> **一句话定位**：写文件的难点不在"把内容存盘"，而在**怎么不让一次整文件覆写，悄悄抹掉别人（用户、格式化工具）刚做的改动**。CC 的写文件，重头全在"写之前的把关"上。

---

---

## 零、参数与输出（Schema）

**输入参数**（仅 2 个，极简）：

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file_path` | string（绝对路径） | ✅ | 目标文件的绝对路径，文件不存在时自动创建（父目录也会自动建） |
| `content` | string | ✅ | 文件完整内容，整体覆写，**不做任何行尾/编码转换**（模型发什么写什么） |

> **为什么只有 2 个参数**：Write 是整体替换——路径 + 内容就是全部，没有"替换哪段"的概念。正是因为简单，才更危险（见主体第二节）。

**输出字段**（模型看到的工具结果）：

| 字段 | 含义 |
|---|---|
| `type` | `"create"`（新建文件）或 `"update"`（覆写已有文件） |
| `filePath` | 写入的文件路径 |
| `structuredPatch` | 若是覆写，包含 diff 结构（hunk 数组），显示改了什么 |
| `originalFile` | 覆写前的原始内容（若为新建则为 null） |

## 一、先记一张地图：写文件三件套，以及它最该防的事

读文件、编辑文件、写文件，是 CC 文件操作的"三件套"，**共享同一张读取台账**（见 [[01-FileRead-读文件]] 第五节）。写文件在这套里的角色和把关如下：

| 把关 | 防什么 | 怎么做 |
|---|---|---|
| **① 写前必须先读过** | 防"没看过文件内容就盲目整个覆写" | 文件已存在却没读过 → 拦，要你先读 |
| **② 读完之后文件被改了** | 防"基于过期内容覆写，抹掉中间的改动" | 读之后磁盘 mtime 变了 → 拦，要你重读 |
| **③ 临门再查一次** | 防"检查到写盘之间，文件又被改" | 真正写盘前再比一次 |
| **④ 不擅自改行尾/编码** | 防"好心改写反而损坏文件" | 模型发什么就写什么 |

核心就一句：**写文件 = 整个覆写，杀伤力最大，所以把关也最严。**

---

## 二、为什么写比编辑更需要把关（一个关键洞察）

这是理解 CC 写文件最重要的一点。先看一个对比：

- **编辑文件**：模型要提供"原文片段（old_string）"和"替换成什么"。如果模型不知道文件当前内容，它**写不出能匹配上的原文片段**，编辑就直接失败了。所以**"原文片段"本身就是一道内容校验**——它逼着模型必须真的了解文件现状，否则改不动。
- **写文件**：整个文件覆写，**不需要提供任何"原文片段"**，没有任何内容校验。模型只��给一段新内容，旧文件就被整个替换掉。

**结论**：写文件**没有编辑文件那道"原文片段"的安全网**。所以一个看着没把关的写操作，杀伤力比看着没把关的编辑大得多——编辑顶多改错一小段（而且大概率因为匹配不上而失败），写却能**一次性抹掉整个文件**。这就是为什么 CC 对写文件的"写前把关"比编辑更严。

具体会出什么事（如果不把关）：

- 模型读了某文件 → 用户在编辑器里改了它 → 模型按它读到的**旧内容**整个覆写 → **用户的改动被静默清掉**。
- 模型**压根没读过**某文件 → 直接覆写 → 整个文件被一段可能是模型凭空想象的内容替换 → **原文全没了**。

## 三、写前的三道闸（把关的核心）

### 第一道：没读过，不让写

模型要覆写一个**已经存在**的文件时，CC 先查读取台账：**这个文件读过吗？** 如果没读过（或者只用分页读过一小段、没看过全文），就**拦下来**，告诉模型"还没读过这个文件呢，先读了再写"。

为什么连"只读过一小段"也拦？因为你要**整个覆写**，却只看过文件的一部分——那没看到的部分就会被你这次覆写**无声地抹掉**。所以必须看过全文才放行。

**例外**：如果文件**不存在**（是新建），那就没有"先读"一说——本来就没东西可读、也没东西可抹，直接放行。所以"写前必须先读"这条**只约束覆写已存在的文件，不约束新建**。

### 第二道：读完之后被改了，不让写

就算读过了，CC 还要查：**你读完那一刻到现在，文件在磁盘上被改过吗？**（靠台账里记的修改时间和当前修改时间比对。）如果变了——说明你手里的内容已经过期，这时候覆写会**抹掉那个把文件改动了的人（用户、格式化工具、别的程序）刚做的事**。所以拦下来，让模型重新读一遍最新内容再写。

### 第三道：临门再查一次

前两道是在"准备写"的时候查的。但从"查完"到"真正写盘"这中间，理论上文件还可能被改。所以 CC 在**真正落盘的前一刻，再比一次**，确保"我以为的文件状态"和"磁盘上此刻的状态"还一致，不一致就中止。这是给前两道闸再加一层保险。

（这里还有个有意思的细节：单纯比"修改时间"在某些环境会误报——云同步、杀毒软件会碰一下文件让时间戳变了，但内容其实没变。所以这道临门检查在比时间戳之外，还会**回退去比一下内容本身**，避免无谓地拦截。）

## 四、不擅自改行尾和编码

一个容易忽略但 CC 踩过坑的点：**写文件时，模型发来什么内容，就原样写什么，不去"好心改写"。**

具体说行尾（换行符）：CC **不去保留旧文件的行尾风格、也不去采样仓库其它文件的风格**，而是**模型在内容里发的换行符就是它想要的**。为什么？因为"保留旧风格"听起来贴心，实际会**静默损坏文件**——比如用一种换行符去覆写另一种换行符的文件、或者被目录里的二进制文件污染了"风格采样"，结果给一个 Linux 上的脚本塞进了 Windows 换行符，脚本就跑不了了。

**原则**：写是"整个替换"，模型既然发了完整内容，就该完全照它的来，**任何自作主张的改写都是风险**。

## 五、其他把关与配套

- **写前自动建好父目录**：要写的路径父目录不存在，先建出来，免得写失败。
- **写前留备份**：支持撤销，写之前先把旧内容存一份。
- **写后刷新读取台账**：写成功后，把"这个文件现在是什么状态"更新进台账——这样模型紧接着再编辑它，不会误报"被人改过了"（因为改它的正是模型自己）。
- **通知编辑器**：写完通知 IDE，让 diff 视图、语言服务器及时更新。
- **安全守卫**：拦截往含密钥的团队记忆文件里写东西、跳过有凭证泄漏风险的特殊网络路径等。

## 六、prompt：克制地写

CC 的写文件 prompt 很短，但有几条硬纪律：

- **覆写已存在的文件前，必须先读过，否则工具会直接失败**（就是第三节第一道闸的明示）。
- **优先用编辑工具**——编辑只发"改动的那一小段"，更省 token、更不易出错；写文件**只用于新建文件或整体重写**。
- **绝不主动创建文档文件（README、`.md`）**，除非用户明确要求。
- 除非用户要，**不往文件里写 emoji**。

这几条的共同精神是**克制**：能用更小、更安全的编辑就别整个覆写；用户没要的东西（文档、emoji）就别擅自生产。

---

## 七、核心 takeaway

1. **写文件 = 整个覆写，杀伤力最大，所以把关最严**——三道闸（没读过/读后被改/临门再查）全是"写之前"的把关。
2. **写比编辑更需要把关**，因为写**没有编辑那道"原文片段"的安全网**——编辑改错顶多一小段且大概率失败，写却能一次抹掉整个文件。这是理解 CC 写文件设计的钥匙。
3. **不擅自改行尾/编码**——模型发什么写什么，"好心改写"反而损坏文件。
4. **三件套共享一张台账**：读的时候建账、写的时候查账又刷账。这张台账是 CC 把"读/编辑/写"粘成一个安全整体的底层基础。
5. **prompt 教模型克制**：优先编辑、别整个覆写，别擅自造文档和 emoji。
