# CC 用户事件钩子（Hooks）

> **一句话定位**：钩子让你能**把自己的逻辑挂到 CC 执行流程的某些关键时刻**上——比如"模型每次执行命令前，先跑我的安全检查""模型每次改完文件后，自动格式化"。它是用户**介入和约束 CC 行为**的口子，不用改 CC 的代码。

---

## 一、为什么需要它

CC 自己有一套行为逻辑（调工具、改文件、执行命令）。但**每个团队、每个项目的规矩不一样**：

- 有的团队要求"任何写文件操作都得先过一遍敏感信息扫描"。
- 有的项目要求"改完代码必须自动跑格式化和 lint"。
- 有的要求"模型绝对不准碰某些目录"。

这些规矩 CC 不可能内置（太个性化了）。所以 CC 留了一个口子：**让你在它执行流程的关键时刻，挂上你自己的逻辑**。这就是钩子。

**本质**：钩子是 CC 给用户的"**可编程的关卡**"——你在某个事件点设一道卡，CC 跑到那儿就会先问你的卡"放不放行"。

---

## 二、地图：钩子的三个要素

配一个钩子，就是回答三个问题：

| 要素 | 回答什么 | 例子 |
|---|---|---|
| **① 挂在哪个事件** | 在 CC 执行流程的哪个时刻触发 | "模型执行工具之前" |
| **② 触发时跑什么** | 触发了之后，执行什么逻辑 | "跑我的安全检查脚本" |
| **③ 跑完能干预什么** | 你的逻辑能不能拦截/修改 CC 的行为 | "检查不通过就拦下这次执行" |

下面逐个展开。

---

## 三、① 能挂在哪些事件（十个时刻）

CC 在执行流程的这些关键时刻，都预留了挂钩点：

| 事件 | 触发时刻 | 典型用途 |
|---|---|---|
| **执行工具前** | 模型决定调某工具、还没执行 | 安全检查、拦截危险操作、改参数 |
| **执行工具后** | 工具执行完、拿到结果 | 改完文件自动格式化/lint、记录审计 |
| **用户提交输入时** | 你刚敲完一条消息发出去 | 给输入附加上下文、检查输入 |
| **对话结束时（Stop）** | 模型这一轮要收尾了 | 自动 commit、收尾检查、阻止"草草结束" |
| **子 agent 启动/结束** | 派出/收回一个子 agent | 给子 agent 加约束、收集子 agent 的产出 |
| **会话开始/结束** | 整个 CC 会话启动/退出 | 初始化环境、清理、加载项目特定上下文 |
| **压缩前** | 对话要被压缩摘要之前 | 保存某些不想被压掉的信息 |
| **通知时** | CC 要给你发通知 | 转发到你自己的通知渠道 |

**最常用的是"执行工具前/后"这两个**——因为工具是 CC 真正"动手"的地方，把卡设在这里最有用。

---

## 四、② 触发时能跑什么（四种形态）

钩子被触发时，能跑的不只是 shell 命令，有四种形态：

1. **命令型**：跑一段 **shell 命令/脚本**。最常见——比如跑个格式化工具、跑个检查脚本。
2. **提示型**：跑一次**小模型判断**。比如"让一个便宜的小模型看看这次操作合不合规，给个 yes/no"。
3. **HTTP 型**：发一个 **HTTP 请求**。比如通知你公司的某个内部服务。
4. **验证 agent 型**：跑一个**专门的验证子 agent**。比如"派个 agent 去检查模型刚做的改动对不对"。

**注意提示型和验证型很有意思**：钩子不只能跑"死"的脚本，还能**调用 AI 来做判断**——把"这次操作该不该放行"这种需要理解的判断，交给一个小模型或子 agent。

钩子还能配成**后台运行**（不阻塞主流程）、或**一次性**（跑完就自动移除）。

---

## 五、③ 跑完能干预什么（这是钩子真正的力量）

钩子不只是"被动观察"，它能**主动干预 CC 的行为**。跑完之后，钩子可以返回几种"指令"：

| 钩子能返回 | 效果 |
|---|---|
| **拦截/拒绝** | 阻止这次操作。比如"执行工具前"钩子判定危险，直接拦下，工具根本不执行 |
| **修改输入** | 改掉模型给的参数再执行。比如把某个危险路径替换掉 |
| **注入上下文** | 往对话里加一段信息给模型看。比如"提醒模型：这个项目有特殊规范" |
| **附加系统消息** | 加一条提示 |
| **阻止收尾** | 在"对话结束"钩子里，可以说"还没完，继续干"，让模型别草草结束 |

**这才是钩子真正值钱的地方**：它不是日志，而是**一道能拦、能改、能补的活关卡**。比如：

- "执行命令前"钩子发现是 `rm -rf /`，**直接拦截**，模型这条命令根本跑不了。
- "执行工具前"钩子发现路径指向敏感目录，**改掉参数**指向安全位置。
- "对话结束"钩子发现"测试还没跑"，**阻止收尾**，逼模型先跑测试。

---

## 六、钩子到底怎么"挂"上去的（最关键的一节）

很容易误以为钩子是"模型动态生成的"或者"某种 CC 内部的设定"。**都不是。钩子是你（用户）预先写好、放在配置文件里的声明。模型全程不参与写钩子——它只是在运行时被钩子约束。**

### 第 1 步：你在配置文件里"声明"钩子

钩子写在一个**设置文件**里，是一段 **JSON 声明**，结构就是回答前面那三个问题：

```
"hooks": {
  "PreToolUse": [                 ← 挂在哪个事件（执行工具前）
    {
      "matcher": "Bash(git *)",   ← 什么情况触发（只在 git 命令时）
      "hooks": [
        {
          "type": "command",          ← 跑什么形态（shell 命令）
          "command": "./my-check.sh"  ← 具体跑哪个
        }
      ]
    }
  ]
}
```

这段 JSON 的意思就是："**执行工具前，如果是 git 命令，就跑我的 `my-check.sh` 脚本**"。

### 第 2 步：那个 "command" 就是一条 shell 命令

`"command": "./my-check.sh"` 是一条**普通的 shell 命令**，通常指向**你自己写的脚本文件**（bash、python 都行，能在 shell 里跑就行）。

所以"钩子用代码吗"的准确答案是：
- **配置本身**是 JSON 声明（不是代码）。
- 但 command 型钩子**指向的是你写的脚本**（那才是代码/脚本）。
- 这个脚本是**你写的**，不是模型写的。
- （提示型/验证 agent 型钩子，那个"跑什么"填的是一段给小模型的提示词——同样是**你预先配好的**，不是模型临时生成。）

### 第 3 步：CC 启动时读配置，把钩子"装"进去

CC 启动时会**读这个设置文件**，把里面声明的所有钩子加载进来，建立一张**"事件 → 钩子"的映射表**（哪个事件挂了哪些钩子、匹配规则是什么）。这就是"挂上去"的本质——不是什么神秘操作，就是**读配置、建映射表**。

### 第 4 步：运行到某事件，触发 + 执行

CC 跑到某个事件点（比如"要执行一条 Bash 命令了"）时：
1. 查表："这个事件有钩子吗？"
2. 有 → 查匹配规则："这条命令匹配 `Bash(git *)` 吗？"
3. 匹配 → CC **启动一个子进程，跑你那条 command**。

### 第 5 步：CC 和你的脚本怎么"对话"——靠标准输入/输出传 JSON

这是最精妙的一步。CC 和你的脚本之间，通过**标准输入/输出（stdin/stdout）交换 JSON**：

- **CC → 你的脚本（标准输入）**：CC 把"现在发生了什么"打包成 JSON，从标准输入喂给你的脚本。比如 `{"tool_name": "Bash", "tool_input": {"command": "git push"}}`——你的脚本读一下就知道"模型现在想跑 `git push`"。
- **你的脚本 → CC（标准输出 + 退出码）**：你的脚本判断完，通过标准输出返回 JSON（"拒绝这次操作"/"改成这个参数"），或者用退出码表态（比如退出码非 0 = 拦截）。

所以**你的脚本根本不需要懂 CC 内部**——它就是个普通脚本：**从标准输入读一段 JSON、做判断、往标准输出写结果**。CC 负责把这个结果翻译成"放行/拦截/改参数"。

### 串成一个完整例子

想要"模型每次 push 前必须先过我的检查"：

1. **你写个脚本** `check-push.sh`：从标准输入读 JSON，看是不是 push，是的话检查有没有敏感文件，有就往标准输出写"拒绝"。
2. **你在配置文件里声明**："PreToolUse 事件、匹配 `Bash(git push*)`、跑 `check-push.sh`"。
3. **CC 启动**，读到这个配置，记下来。
4. **模型某次想 `git push`** → CC 触发钩子 → 启动 `check-push.sh`、把 push 命令的 JSON 喂给它标准输入。
5. 脚本发现有敏感文件 → 往标准输出写"拒绝" → **CC 拦下这次 push，模型根本推不了**。

全程模型不知道你的脚本怎么写的，它只是**撞上了你设的关卡**。

## 七、一个精妙细节：钩子的"条件过滤"

如果每个钩子在每次事件都触发，会很浪费（比如你只想检查 `git` 命令，但每条命令都跑一遍你的脚本）。

所以钩子支持一个**条件过滤**（就是上面例子里的 `matcher`）：写一个匹配规则，**只有当操作匹配这个规则时，钩子才触发**。比如"只在执行 `git` 开头的命令时才跑我的检查"——其他命令直接跳过，不浪费。

这避免了"为不相关的操作白白启动钩子"的开销。

---

## 八、钩子和 CC 自带安全的关系

CC 自己已经有一套安全（权限确认、危险命令检测）。钩子是**在这之上让用户再加自己的关卡**：

- CC 自带的：通用的、CC 觉得该管的（比如执行命令要批准）。
- 用户钩子：**你团队/项目特有的规矩**，CC 不可能内置的那些。

两者叠加：一次工具调用，可能先过 CC 自带的权限检查，再过你配的"执行工具前"钩子。**钩子让安全策略从"CC 内置的固定几条"变成"用户可无限扩展的"。**

---

## 九、核心 takeaway

1. **钩子 = 用户给 CC 设的可编程关卡**：在执行流程的某个时刻挂上自己的逻辑，不用改 CC 代码。
2. **三要素**：挂在哪个事件（10 个时刻，最常用"执行工具前/后"）、触发跑什么（命令/小模型/HTTP/验证 agent 四种）、跑完干预什么（拦截/改输入/注入上下文）。
3. **钩子能调 AI 做判断**：提示型、验证 agent 型钩子，把"该不该放行"这种需要理解的判断交给小模型/子 agent。
4. **钩子真正的力量在"能干预"**：不是被动日志，是能拦、能改、能补的活关卡。
5. **条件过滤**避免为不相关操作白白触发。
6. **钩子是 CC 自带安全之上的用户扩展层**：把安全策略从"内置固定几条"变成"用户可无限扩展"。
