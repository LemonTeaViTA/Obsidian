# CC 对话循环的健壮性外壳

> **一句话定位**：CC 的对话循环骨架很简单，但真实世界会不停出岔子。这篇讲清楚——循环会从哪几个方向出岔子、每个方向 CC 怎么自己救回来。不涉及代码，只讲机制。

---

## 一、先记这张地图（全篇的骨架）

对话循环的**骨架**一句话能说完：

> 把当前对话发给模型 → 模型要么给最终回答（结束），要么要求调用工具 → 那就执行工具、把结果接回对话 → 再发给模型 → 往复，直到模型不再调工具。

这个骨架本身几十行就能写出来。但只有骨架它**极其脆弱**。CC 的功夫全在骨架**外面**那一圈兜底上。而这圈兜底，其实只回答一个问题：

> **循环跑起来，会从哪几个方向出岔子？每个方向怎么兜底？**

只有四个方向。**这张表就是全篇骨架，能复述出来就抓住了主干：**

| 方向（谁出问题） | 出什么岔子 | 统一动作 | 记忆钩子 |
|---|---|---|---|
| **① 喂进去的太多** | 上下文超长 | **瘦身重来** | 三级阶梯：本地排水 → 调模型压缩 → 放弃 |
| **② 吐出来的坏了** | 模型过载 / 输出被截断 | **换或加，重来** | 换备用模型 / 加额度 / 让它续写 |
| **③ 对话秩序乱了** | 用户中断 / 工具调用没配对结果 | **补全善后** | 守住"一个工具调用必配一个结果"的底线 |
| **④ 循环刹不住** | 转太多轮 / 烧光预算 / 死亡螺旋 | **装刹车** | 设上限 + "试过就不再试" |

下面四节，一节一个方向。

---

## 二、方向①：喂进去的太多——上下文超长怎么瘦身

**会发生什么**：对话越聊越长，加上工具塞回来的大量结果，整个上下文超过模型能吃下的最大长度，模型直接拒绝："prompt 太长"。这是最常见、最关键的一种岔子。

**贯穿的关键手法：错误"扣留"**。模型报"太长"时，CC **不会立刻把错误显示给你**，而是先"扣在手里"，自己偷偷去补救；只有所有补救都失败了，才把错误亮出来。所以你大多数时候根本看不到这个报错——它已经在背后被消化掉了。

补救是一个**三级阶梯**，先用最便宜、损失最小的，不行再升级，**每级只试一次**。

### 第一级——折叠排水（纯本地操作，不发模型，最便宜）

先讲清"折叠"，这是最容易误解的地方：**它不需要多一轮 LLM 调用，也不是在提示词里叫模型折叠，而是客户端程序自己在本地改写要发出去的消息列表。**

CC **每一轮请求发出去之前**，都顺手扫一遍那些"已经看过、价值榨干"的大块内容——读文件的完整结果、搜索的大段输出、后台命令通知、钩子摘要。对这些，程序**就地把冗长正文换成一行简短占位**（比如"读了 800 行的完整文件"换成"（该文件已读过，内容已折叠）"），换下来的原文**暂存一旁、需要时能还原**。这就是"提前折叠存下来"的真相——不是攒着等出事，是**平时每轮就在本地悄悄折叠**。

> 诚实标注：折叠"具体挑哪些内容、占位长什么样"是根据相关模块职责**推断**的（折叠模块内部实现没在可读源码里）。但"它是本地操作、不发 LLM"是**确定的**：做折叠/排水时根本没把提示词传进去、也不等网络返回；而第二级压缩则明确传了提示词。一对比就清楚。

"排水"就好理解了：真撞上太长，第一反应是把这些**已折叠、原文存在一旁的内容彻底清出去**腾空间。清掉的本就是榨干的边角料，**几乎不损失有用信息**。排完拿瘦身后的上下文**重新发一次请求**。零 LLM 调用、零额外往返，所以最便宜、优先用。

### 第二级——反应式压缩（唯一一级真正调用 LLM）

排水后**再发还是太长**，说明边角料不够省，升到第二级：**真请求一次模型**，让它把前面的大段对话**总结成一份结构化摘要**，再用摘要替换掉原始冗长历史，从根上压体积。

这一级的提示词有讲究（三级里**唯一有提示词的**，因为只有它要 LLM 干活）：
- 要求产出**固定结构的摘要**，覆盖约八个部分——用户明确诉求、关键技术概念、看过/改过的文件和代码片段、当前在做什么、下一步做什么等。
- 强调"下一步"要**附上最近对话的原话引用**，防压缩后任务跑偏。
- 开头压着一句重话：**"只准输出纯文本，绝对不要调任何工具"**——压缩这轮只给模型一次机会，手贱调工具这机会就废了。
- 模型先写"分析草稿"梳理思路、再写正式摘要；草稿块在进入上下文前被**剥掉**，不占地方。

压完同样**重新发请求**。（特例：如果太长是**图片/PDF 这类媒体**撑爆的，折叠排水帮不上忙，会**跳过第一级直接进压缩**，靠"剥掉媒体再重试"来救。）

### 第三级——放弃，亮错误

压缩之后**还是**太长，CC 才把那个一直扣在手里的错误显示给你，干净退出。这级没提示词，就是放弃 + 亮错。

### 关键："三级怎么知道上一级失败了"

**不靠抓异常，靠"给每轮盖个戳 + 一个'压过没'的标记"，跨轮判断。** 这三级不是一次串行试下来的，是**一级占一轮**：

1. 太长 → 折叠排水 → 盖戳「本轮是排水重试」→ 回循环顶**重发**。
2. **又**太长 → 看上一轮的戳是「排水重试」→ 知道排水没用 → **跳过第一级，直接压缩**。
3. 压缩前看「是否已压过」标记：没压过才压；压完标记设为真，盖戳「压缩重试」→ **重发**。
4. **还**太长 → 看「已压过」为真 → 知道压也试过了 → **亮错退出**。

所以"判断上一级失败"**不在恢复代码内部**，而在"下一轮还报不报太长"——又报了，就靠戳和标记决定升到哪级。这正是健壮性外壳的核心招式：**出岔子就带着新状态回循环顶重来，循环本身就是重试器**。

> 顺带区分一个易混点：除了上面这种"已经报错了才补救"，CC 还有一种**主动预防**——每次发请求前先估算上下文体积，逼近上限就**提前压缩**。它发生在"发请求之前"，压缩后**原地把要发的上下文换成短版本、不打断循环**，模型那一轮照常进行。所以：发请求前的叫"预防"，报错后的三级阶梯叫"补救"，一前一后配合。

## 三、方向②：吐出来的坏了——模型过载 / 输出截断

这个方向是"模型这一侧没给出能用的响应"，分两种岔子。

### 模型过载 → 换备用模型重来

模型背后服务器临时过载、限流，请求被拒。CC 不把错误甩给你，而是**自动切到预先配好的备用模型，把请求从头再发一遍**。讲究两点：
- **整个请求重来**，不接断点——换了模型，半截状态没意义。
- **换前要擦掉只对旧模型有效的痕迹**：模型内部思考带一种"签名"（旧模型盖的章），新模型不认、会因此报错，所以换前先清掉。
- 给你一行小提示"已切备用模型"，但不打断任务。

### 输出被截断 → 先加额度，再让它续写

模型回答有"最多输出多少"的上限，正写着被硬截断，回答就残缺。CC 的阶梯思路是"先扩容、再续写"：
1. **一次性扩容重试**：如果用的是偏小的默认额度，撞顶了就**把额度直接调大、同一请求重发一次**。这步很干净——不加任何"接着说"，纯加额度重来，每轮只用一次。
2. **多轮续写**：额度够大还截断（内容确实超长），就往对话里加一句"到上限了，从断的地方直接继续"，让模型**分多次续完**，有次数上限防止无限续。
3. **放弃**：续几次还没完，才把截断结果亮出来。

**这一节的统一动作 = "换或加，重来"**：过载就换模型，截断就加额度/续写，最后都回循环顶重发。

## 四、方向③：对话秩序乱了——中断 / 协议配对

这个方向守的是**对话格式的完整性**，这是一条不可触碰的底线。

**底线是什么**：模型 API 有条硬规矩——**每一个工具调用，后面必须紧跟一个配对的结果**。少一个，下次请求整个被拒，对话**彻底卡死、再也聊不下去**。

**什么时候会破坏它**：用户中断（模型已发起几个工具调用，还没执行就被打断）、或工具因报错/过载没产出结果——这些都会留下"孤立的工具调用"。

**CC 怎么做**：在每一个可能产生孤立调用的出口（中断、报错、模型切换），都**主动补上一个合成的占位结果**（内容大意"这个调用被中断了"），把配对补齐，再干净收尾。

**设计精神**：宁可填一条"被中断了"的占位，也绝不让对话变成模型拒收的残缺格式。**补全善后，是为了保证下一次还能正常接着聊。**

---

## 五、方向④：循环刹不住——轮数 / 预算 / 死亡螺旋

模型理论上可能陷入"调工具→看结果→再调工具→……"出不来，或任务大到烧光预算。循环必须有刹车：
- **最大轮数上限**：来回到一定次数还没收尾，强制停。
- **token 预算**：累计消耗到量就停。
- 每轮开头检查这些闸，超了就带"为什么停"的说明退出。

**还有一类更隐蔽的刹车——防死亡螺旋**。死亡螺旋指"越救越糟"的闭环，CC 在每个可能形成它的地方都设了硬闸。最典型的例子：上下文太长、最终放弃退出时，CC **故意不去触发"任务结束钩子"**。因为那些钩子会**往对话里再塞内容**，而问题恰恰是"内容太多"——再塞就又超长、又触发恢复、又失败……成了"错误→塞内容→更长→又错误"的无限循环。所以这种情况直接退出，不留口子。

**这一节的统一动作 = "装刹车"**：硬上限管住"转不停/烧不完"，"试过就不再试"管住"越救越糟"。

---

## 六、收束：四个方向共享的设计哲学

记住四方向四动作之后，再往上提炼一层——它们其实共享同一套思路：

1. **扣留 + 偷偷救**：失败先别急着告诉用户，CC 在背后试着自救；救成了你无感，救不成才亮错。大多数岔子就这样消化在你看不见的地方。
2. **逐级升级、每级只试一次**：处理太长（排水→压缩→放弃）、处理截断（扩容→续写→放弃）都是先用最便宜的、不行再换更狠的，且**每招只试一次**——绝不无限重试同一招（那是卡死的根源）。
3. **带新状态回循环顶重来**：几乎每个兜底成功后，都做同一个动作——构造"修正过的新状态"（瘦身的上下文、加大的额度），回循环开头重走一遍。**循环本身就是统一的重试器**，各种恢复只是"准备好新状态再交还给循环"。
4. **守住格式底线**：无论怎么出错、中断，都要保证工具调用与结果配对完整，否则对话彻底卡死。
5. **处处防死亡螺旋**：在每个可能"越救越糟"的地方，都设"试过就不再试"或"这种情况直接退出"的硬闸。

---

## 七、一句话总结

CC 的对话循环 = **一个几十行就能写完的简单骨架** + **一圈"从四个方向（喂太多 / 吐坏了 / 秩序乱 / 刹不住）兜底、且绝不卡死"的厚外壳**。

健壮性从来不是把骨架写复杂，而是**为每一种可预见的意外，都准备好一条"先自救、逐级升级、保住底线、防住死循环"的退路**。
