# 环境层详解

> 对应 [03-启动流程走读.md](./03-启动流程走读.md) 分层时序图里的 **环境层**。
> 环境层 = 服务启动最开始、在任何业务逻辑之前，把"这台进程运行在什么环境、用什么配置、构建命令怎么走"这些底座铺好。
> 入口：[main.py:3804 `setup_runtime_environment()`](../main.py#L3804)

---

## 一、环境层总览

```
                        ┌─────────────────────────────┐
   python main.py --env daily │  setup_runtime_environment() (main.py:3619) │
   ────────────────────►│                             │
                        │  ① 解析 --env 参数           │
                        │  ② apply_env_config(env)     │──► config.py: ENV_CONFIGS
                        │  ③ os.environ['ENV'] = env   │      写入几十个环境变量
                        │  ④ print_current_config()    │──► 打印校验
                        │  ⑤ mvn 命令劫持              │──► 生成 ~/logs/code-agent/mvn
                        │                             │      塞进 PATH 最前
                        └─────────────────────────────┘
                                     │
                    环境变量 + PATH 就绪，后续所有模块都读它
```

**一句话**：环境层不做业务，只干一件事——**把配置从 `config.py` 的字典搬进 `os.environ`，并劫持 mvn 命令**。之后 coscmd、langfuse、MCP、Redis 等所有模块都从 `os.environ` 读自己要的值。

## 二、配置从哪来？三个来源的优先级

环境变量最终值由三处叠加，优先级 **已有环境变量 > config.py 默认值 > 代码兜底**：

```
① 外部已设的环境变量（如 docker -e / export ANTHROPIC_API_KEY）
        │  apply_env_config 默认 override_existing=False
        │  ——已存在就【保留】，不覆盖
        ▼
② config.py 的 ENV_CONFIGS[env]     ← 主要来源
        │  按 --env 选 daily/pre/prod 那一套
        ▼
③ 各模块自己的 os.getenv(key, "默认值")  ← 最后兜底
```

关键代码 [config.py:130-140](../config.py#L130-L140)：

```python
for key, value in config.items():
    current_value = os.getenv(key)
    if current_value and not override_existing:
        continue                      # 已有就保留，不覆盖 ★
    if value:
        os.environ[key] = value       # 否则写入 config.py 的值
```

> **设计意图**：config.py 给一套合理默认，但允许部署时用外部环境变量临时覆盖（不用改代码）。这就是为什么 CLAUDE.md 里说"startup script 自动配置，也可通过环境变量覆盖"。

## 三、config.py 的 ENV_CONFIGS —— 环境层的"配置源头"

[config.py:15](../config.py#L15) 定义了三套环境配置，结构完全对称，只是值不同。每套配置里有哪些内容、供谁用：

| 配置项 | 作用 | 谁读它 |
|--------|------|--------|
| `MANAGEMENT_API_BASE_URL` | AI24 管理平台地址 | 拉 API Key、上报结果、Figma token |
| `REDIS_NODES` | Redis 集群节点 | 多机任务分发（Pub/Sub） |
| `AI24_MCP_URL` | AI24 MCP 服务地址 | create_claude_service 挂 MCP |
| `CONTEXT1_MCP_URL` | 中间件文档 MCP | 同上 |
| `UI_TEST_AUTOMATION_MCP_URL` | UI 自动化测试 MCP | 同上 |
| `TASK_URL` | 任务链接前缀 | 生成任务跳转链接 |
| `PREVIEW_HOST` | 前端预览服务地址 | PreviewService |
| `COS_PATH_PREFIX` | COS 备份路径前缀 | 云端备份分环境隔离 |
| `LANGFUSE_PUBLIC_KEY` / `SECRET_KEY` / `BASE_URL` | LLM 追踪凭证与地址 | init_langfuse |
| `LANGSMITH_OTEL_ENABLED` / `_ONLY` / `TRACING` | OpenTelemetry 追踪开关 | SDK 追踪 |
| `CLAUDE_CLI_PATH` | claude CLI 可执行文件路径 | SDK 找 CLI |
| `CLAUDE_CODE_ENABLE_TASKS` | 启用 Task 工具 | SDK 能力开关 |
| `CLAUDE_CODE_MAX_OUTPUT_TOKENS` | 最大输出 token（128000） | SDK 输出上限 |
| `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` | 实验性 agent teams | SDK 能力开关 |

**三环境差异**（看 URL 里的域名段）：

| | daily | pre | prod |
|--|-------|-----|------|
| 管理平台 | `ai24.daily.vdian.net` | `ai24.pre.vdian.net` | `ai24.vdian.net` |
| AI24 MCP | `.../ai24/sse` | `.../ai24-pre/sse` | `.../ai24-prod/sse` |
| Langfuse | `langfuse.daily.vdian.net` | `langfuse.vdian.net` | `langfuse.vdian.net` |

> ⚠️ 观察到的问题：
> 1. **prod 的 `COS_PATH_PREFIX` 写成了 `/code-agent/pre`**（[config.py:72](../config.py#L72)），疑似复制 pre 时忘改，会导致生产备份落到 pre 的路径。
> 2. **Langfuse / API Key 等密钥明文硬编码**在 config.py，有泄露风险，建议挪到环境变量或密钥管理。

## 四、config.py 的四个函数

### `load_env_config(env)` — [config.py:94](../config.py#L94)
校验 env 合法（不在 daily/pre/prod 就抛 `ValueError`），返回 `ENV_CONFIGS[env].copy()`。用 `.copy()` 避免调用方改到原字典。

### `apply_env_config(env, override_existing=False)` — [config.py:113](../config.py#L113)
把配置写进 `os.environ`（逻辑见第二节）。另外两个动作：
- **prod 强校验**：`REDIS_NODES` 必须有，否则 `raise RuntimeError`（生产不允许缺 Redis）
- **默认端口**：`PORT` 没设就补 `8080`

### `print_current_config()` — [config.py:184](../config.py#L184)
打印关键配置做启动校验。注意 API Key 只打印前 20 字符 + 长度（`api_key[:20]...`），**不泄露完整密钥**，这是好习惯。

### `get_ai24_mcp_name()` — [config.py:163](../config.py#L163)
按环境返回 MCP 服务名：daily→`ai24`、pre→`ai24-pre`、prod→`ai24-prod`。create_claude_service 挂 AI24 MCP 时用它决定服务名。

## 五、mvn 命令劫持 —— 环境层最巧妙的一招 ⭐️

> 🎯 **设计亮点**：这是整个环境层最精妙的设计！
> 
> **问题**：Claude 可能在一个任务中编译多个项目，每个项目需要不同的 JDK 版本（JDK 8/11），但 Claude 不会主动切换 `JAVA_HOME`，导致编译失败。
> 
> **解决方案**：创建一个"假 mvn"拦截所有 `mvn` 命令，自动读取当前目录的 `pom.xml` 判断 JDK 版本，动态设置 `JAVA_HOME`，再调用真正的 mvn。整个过程对 Claude 完全透明。

这是环境层唯一"有点魔法"的部分，分两步：**造假 mvn** + **改 PATH**。

### 第一步：setup_runtime_environment 造一个假 mvn
[main.py:3660-3679](../main.py#L3660-L3679)：

```python
mvn_wrapper_dir = os.path.expanduser("~/logs/code-agent")
new_mvn_wrapper = os.path.join(mvn_wrapper_dir, 'mvn')

# 写一个 bash 脚本，内容是转发到 new_mvn.py
with open(new_mvn_wrapper, 'w') as f:
    f.write('#!/bin/bash\n')
    f.write(f'exec python3 "{script_dir}/new_mvn.py" "$@"\n')
os.chmod(new_mvn_wrapper, 0o755)                       # 加执行权限

# 把这个目录塞到 PATH 最前面 ← 关键！
os.environ['PATH'] = f"{mvn_wrapper_dir}:{os.environ.get('PATH', '')}"
```

**原理**：Shell 按 PATH 顺序找命令，第一个匹配即用。把假 mvn 目录放最前，Claude 执行 `mvn xxx` 时**先命中这个假的**，转发给 `new_mvn.py`。

**PATH 劫持示意**：
```bash
# 原来的 PATH
PATH=/usr/local/bin:/usr/bin:/bin

# 修改后的 PATH（假 mvn 在最前面）
PATH=/home/www/logs/code-agent:/usr/local/bin:/usr/bin:/bin
     ↑
     假 mvn 在这里，Shell 优先找到它

# Claude 执行 mvn 时：
$ mvn clean install
# Shell 查找顺序：
# 1. /home/www/logs/code-agent/mvn  ← 找到了！执行这个
# 2. /usr/local/bin/mvn             ← 没机会执行
# 3. /usr/bin/mvn                   ← 没机会执行
```

注释说"仅影响当前进程及子进程"——因为改的是本进程的 `os.environ`，Claude 的 Bash 工具是子进程，会继承这个 PATH。

### 第二步：new_mvn.py 干真活 —— 自动选 JDK 版本
[new_mvn.py](../new_mvn.py)（全文 60 行）：

```python
JDK8_HOME  = "/opt/vdian/install/jdk1.8.0_202"
JDK11_HOME = "/opt/vdian/install/vdian-jdk11-11.0.18"
MVN_PATH   = "/usr/bin/mvn"

def parse_jdk_version():
    """解析当前目录的 pom.xml，判断需要哪个 JDK"""
    if not os.path.exists("pom.xml"):  # ← 读取当前目录！
        return "8"
    
    with open("pom.xml", "r") as f:
        content = f.read()
    
    # 按优先级匹配 maven.compiler.source / java.version / source
    patterns = [
        r"<maven\.compiler\.source>([^<]+)</maven\.compiler\.source>",
        r"<java\.version>([^<]+)</java\.version>",
        r"<source>([^<]+)</source>"
    ]
    
    for pattern in patterns:
        match = re.search(pattern, content)
        if match:
            version = match.group(1).strip()
            if version == "11" or version.startswith("11."):
                return "11"
            return "8"
    
    return "8"  # 默认 JDK 8

def main():
    version = parse_jdk_version()
    java_home = JDK11_HOME if version == "11" else JDK8_HOME
    
    print(f"[new_mvn] Using JDK {version} ({java_home})")
    
    os.environ["JAVA_HOME"] = java_home        # 改 JAVA_HOME
    os.environ["MAVEN_SKIP_RC"] = "true"       # 跳过 mavenrc，防被覆盖
    
    # 用真实 mvn 替换当前进程（execvpe 继承改好的环境变量）
    cmd = [MVN_PATH] + sys.argv[1:]
    os.execvpe(MVN_PATH, cmd, os.environ)
```

**做的事**：
1. **读取当前目录的 `pom.xml`** 判断需要 JDK 8 还是 11
2. **设置对应的 `JAVA_HOME`**
3. **用真正的 `/usr/bin/mvn` 替换当前进程**

**关键设计点**：

| 设计 | 代码 | 作用 |
|------|------|------|
| **读当前目录** | `os.path.exists("pom.xml")` | 适应 Claude 切换目录 |
| **进程替换** | `os.execvpe()` | 不创建子进程，直接替换 |
| **环境变量传递** | `os.execvpe(..., os.environ)` | 把修改后的 JAVA_HOME 传给真 mvn |

> **为什么用 `os.execvpe` 而不是 `subprocess.run`？**
> 
> ```python
> # subprocess.run 会创建子进程（多一层）
> subprocess.run(["/usr/bin/mvn", "clean", "install"])
> # 进程树：python main.py → new_mvn.py → mvn (三层)
> 
> # os.execvpe 直接替换当前进程（更高效）
> os.execvpe("/usr/bin/mvn", cmd, os.environ)
> # 进程树：python main.py → mvn (两层，new_mvn.py 被替换掉了)
> ```

> **解决的痛点**：不同项目要不同 JDK，Claude 不可能每次手动 `export JAVA_HOME`。用假 mvn 拦截，**自动按 pom.xml 选对 JDK**，对 Claude 完全透明——它以为在正常跑 mvn，其实中间被换了 JDK 环境。

### 完整调用链

```
Claude 执行  mvn clean install
        │  PATH 命中 ~/logs/code-agent/mvn (假的 bash 脚本)
        ▼
  exec python3 new_mvn.py clean install
        │  读 pom.xml → 判定 JDK 8/11 → 设 JAVA_HOME
        ▼
  os.execvpe /usr/bin/mvn clean install   (真 mvn，带正确 JAVA_HOME)
```

`os.execvpe` 是关键：它**用新进程替换当前进程**（不是 fork 子进程），所以 new_mvn.py 改的 `JAVA_HOME` 会被真 mvn 继承，且不留多余进程。

## 六、setup_runtime_environment() 完整代码走读

[main.py:3619-3681](../main.py#L3619-L3681)

```python
def setup_runtime_environment():
    """解析命令行参数并应用环境配置"""
    
    # 1. 创建参数解析器
    parser = argparse.ArgumentParser(
        description='DevSecOps Multi-Agent Platform',
        formatter_class=argparse.RawDescriptionHelpFormatter,
        epilog="""
示例:
  python main.py                     # 使用默认环境 (daily)
  python main.py --env pre           # 使用预发环境
  python main.py --env prod          # 使用生产环境
        """
    )
    
    # 2. 添加 --env 参数
    parser.add_argument(
        '--env',
        type=str,
        default='daily',                          # 默认 daily
        choices=['daily', 'pre', 'prod'],         # 只允许这三个值
        help='指定运行环境 (默认: daily)'
    )
    
    # 3. 解析命令行参数
    args = parser.parse_args()
    
    # 4. 加载并应用环境配置
    try:
        apply_env_config(args.env)                # 设置环境变量
        os.environ['ENV'] = args.env              # 保存环境标识
        print_current_config()                    # 打印配置校验
    except Exception as e:
        logger.error(f"环境配置加载失败: {str(e)}", exc_info=True)
        sys.exit(1)                               # 配置失败直接退出
    
    # 5. 设置 mvn 命令路由
    script_dir = os.path.dirname(os.path.abspath(__file__))
    mvn_wrapper_dir = os.path.expanduser("~/logs/code-agent")
    os.makedirs(mvn_wrapper_dir, exist_ok=True)
    
    new_mvn_wrapper = os.path.join(mvn_wrapper_dir, 'mvn')
    
    # 创建 mvn wrapper 脚本
    with open(new_mvn_wrapper, 'w') as f:
        f.write('#!/bin/bash\n')
        f.write(f'exec python3 "{os.path.join(script_dir, "new_mvn.py")}" "$@"\n')
    
    # 添加执行权限
    os.chmod(new_mvn_wrapper, 0o755)
    os.chmod(os.path.join(script_dir, 'new_mvn.py'), 0o755)
    
    # 将 mvn wrapper 目录添加到 PATH 最前面
    os.environ['PATH'] = f"{mvn_wrapper_dir}:{os.environ.get('PATH', '')}"
    logger.info(f"[MVN Router] mvn 命令已路由到 new_mvn.py (仅影响当前进程及子进程)")
    
    return args
```

## 八、小结：环境层做了什么

| 步骤 | 输入 | 输出 | 服务对象 |
|------|------|------|----------|
| 解析 `--env` | 命令行参数 | env 字符串 | 决定用哪套配置 |
| `apply_env_config` | ENV_CONFIGS[env] | 几十个 `os.environ` 变量 | coscmd/langfuse/MCP/Redis 全部 |
| mvn 劫持 | pom.xml（运行时） | 改写的 PATH + 假 mvn | Claude 的构建命令 |

**环境层的本质**：它是所有其他层的"地基"——把散落在 config.py 的配置集中搬进环境变量，并悄悄接管 mvn。后面每一层（coscmd 读桶配置、langfuse 读追踪地址、create_claude_service 读 MCP 地址）都是站在这个地基上从 `os.environ` 取值。
