1. 核心问题

当前真正需要思考的，不是怎么统计 Agent 搜索了多少次知识库，也不是怎么单独给 Langfuse Trace 打分，而是知识库虽然已经接入 Code Agent，却还没有真正进入 Agent 的监督和优化闭环。现在系统会把 knowledge、knowledge-service 和 app-knowledge-v2 同步到执行机器，Agent 也可以搜索和读取这些资料，但是我们很难稳定回答 Agent 当时需要什么知识、为什么使用某个搜索词或工具、为什么选择某份资料、资料是否足够可信，以及最终方案和代码究竟受到哪些知识的影响。换句话说，当前系统解决了知识文件能不能被使用的问题，却还没有解决知识在任务中是否有效、Agent 是否正确使用以及知识应该如何持续改进的问题。

2. 当前知识库到底由什么组成

当前需要把“知识内容”“Catalog”“TechDocs”和“Agent 的查找过程”分开理解。

`knowledge` 仓库里的 `shared/`、`prd-review/` 和 `domains/` 是 Agent 可以搜索和阅读的实际知识内容。其中既有通用规则和提示词，也有 PRD 审核规则、领域知识和应用级知识。`catalog/*.yaml` 是 Backstage 使用的结构化目录，按照 Domain → System → Component → API / Resource 描述业务领域、系统、应用、接口和资源之间的关系。`catalog/domains-techdocs/` 则是用于 Backstage 页面展示的领域文档。

这三层内容虽然放在同一个仓库里，但作用不同：Markdown 解决“具体知识写了什么”，Catalog 解决“这些领域、应用和资源是什么关系”，TechDocs 解决“怎样在 Backstage 页面展示”。它们都不等于 Agent 已经具备了自动检索能力。

从当前 Code Agent 实现来看，知识库同步只是把 Git 仓库 clone 或 pull 到执行机器，并没有看到向量数据库、Embedding 或 RAG 召回流程。Agent 如何找到资料，仍然主要取决于提示词、任务上下文、目录索引，以及模型主动使用文件搜索和读取工具的过程。因此，Catalog 已经让知识结构更清楚，但不能直接证明 Agent 一定会找到或使用正确的知识。

这也决定了监测重点：不能只统计 Catalog 有多少实体、TechDocs 有多少页面，还要记录 Agent 实际搜索了什么、读了哪个文件、采用了哪些内容，以及这些内容怎样影响最终结论。

3. 当前记录与决策信息的缺口

AI24 会保存用户输入、阶段命令、Agent 返回的消息和任务状态，Code Agent 会记录模型消息、工具调用、工具结果和最终执行结果，Langfuse 也会记录模型调用对应的 Trace。这些记录能够帮助我们看到用户说了什么、Agent 做了什么、调用了哪个工具、工具返回了什么以及任务最后是否完成，但是它们更像一条行为链，而不是一条完整的决策链。比如，我们看到 Agent 搜索某个业务状态，只能确定它执行了搜索，却不一定知道它是为了验证 PRD、寻找字段定义、排查文档冲突还是补充代码上下文；我们看到它读取了多个文件，也无法直接确认它认为哪份资料最可信、为什么放弃其他资料以及最后是否真的使用了知识库。因此，对话记录并不是完全没有价值，只是它通常保留了行动和结果，没有稳定保留连接这些行动的决策依据。

4. 关于 thinking 的判断

thinking 缺失很可能是我们无法解释 Agent 工具选择和知识选择的重要原因。我们目前怀疑模型路由没有把完整 thinking 继续向下传递，或者在响应转换中进行了过滤，但这个判断还需要沿实际调用链验证，不能直接写成已经确定的事实。从 Code Agent 源码来看，它已经定义并处理 ThinkingBlock，普通消息渲染器可以记录 thinking，事件渲染器可以把 thinking 和后续工具调用关联起来，收到的 SDK 消息也会被序列化后传入 Langfuse。因此，如果实际任务里完全看不到 thinking，需要依次确认模型是否生成、模型接口是否返回、路由是否过滤、SDK 是否解析、Code Agent 是否收到、消息上报是否保留以及 AI24 是否最终落库。更准确的结论不是 Code Agent 一定删除了 thinking，而是当前整条链路没有保证决策依据能够稳定地产生、传递、保存和使用，只要其中一层丢失，我们最后看到的就只剩工具行为和最终结果。

5. 原始 thinking 与知识决策记录

保存原始 thinking 会对调查问题有帮助，但它不应该成为整个方案的唯一基础。不同模型和路由对 thinking 的支持方式并不一致，有些只返回摘要，有些不返回，有些会因为安全、隐私、成本或者产品策略进行隐藏，而且原始 thinking 本身可能很长、很散并包含多次自我修正。即使完整保存下来，如果系统没有从中提取出知识需求、查询目的、候选资料、采用理由、未解决问题和最终影响，知识库仍然无法形成有效的优化闭环。因此，我们真正需要稳定保存的是一份简短、结构化、可复核的知识决策记录，它应当说明 Agent 当前缺少什么知识、为什么查询、尝试了哪些关键词和来源、采用了哪些资料、为什么相信这些资料、哪些结论由这些资料支撑、还存在哪些不确定性，以及发现问题后选择继续执行、读取代码验证、询问用户还是上报知识问题。原始 thinking 能够获得时可以作为补充证据，但知识监督不能完全依赖它。

6. 知识库监督和优化闭环

完整的闭环应该从一次具体的知识需求开始。Agent 在查询前留下简短的查询目的，查询过程中记录关键词、候选资料和结果，查询后说明采用了什么知识以及选择原因，最终将重要方案、业务结论和代码约束关联到实际知识来源。如果 Agent 发现资料难找、内容缺失、描述模糊、多个文档冲突或者知识已经过期，系统应当把这些问题聚合到具体业务域、目录和文件，而不是让它们只出现在一次任务的对话里。知识负责人完成修改后，还需要使用相似任务重新验证 Agent 是否更快找到资料、是否减少错误推断以及最终结果是否更加可靠。只有形成知识需求、知识查询、知识使用、问题反馈、内容优化和效果验证这一整条链路，知识库才从被动文件目录变成了真正受监督的 Agent 知识系统。

7. Langfuse 的位置

Langfuse 不是知识库监督闭环本身，它不会自动判断某份文档为什么被选择、内容是否过期，也不知道应该由哪个负责人修改。它当前最大的价值，是在系统还没有稳定保存知识决策记录时，帮助我们从模型消息、工具调用、工具结果、执行顺序、耗时和最终回复中迂回还原 Agent 的行为。我们可以借助 Langfuse 看它搜索了什么、读了什么、什么时候改变方向以及最后得出了什么结论，但如果模型路由已经过滤 thinking，那么 Langfuse 看到的同样只是不完整的行为记录。因此，Langfuse 应当被当作现阶段的问题调查和旁证工具，通过它识别当前缺少哪些决策信息，再反过来推动系统主动保存这些信息，而不是长期依赖人工从 Trace 中猜测 Agent 的想法。

8. 现阶段怎么分析和推进

现阶段不需要马上分析大量任务或者设计复杂评分，可以先选择一条具有代表性的真实任务，把 AI24 对话记录、Code Agent 消息日志、工具调用、知识文件、业务代码和 Langfuse Trace 按时间顺序放在一起，先还原能够看到的行为，再标出无法解释的地方，例如为什么突然搜索某个词、为什么放弃某份资料、为什么从知识库转向代码以及为什么最终采用某种实现。这些无法解释的地方就是当前缺失的决策信息。与此同时，应当选择一次明确会产生工具调用的测试任务，沿模型、路由、SDK、Code Agent、Langfuse 和 AI24 落库逐层检查 ThinkingBlock 在哪里开始消失。完成几条真实任务的分析后，我们才能确定哪些知识决策信息普遍缺失，并进一步设计统一的记录字段、问题上报方式和知识优化流程。

9. 当前结论

当前问题的重点不是工程指标不足，而是知识库与 Agent 工程之间缺少监督关系。现有对话和工具记录可以告诉我们 Agent 做了什么，却不能总是解释它为什么这样做；thinking 缺失可能是其中一个重要原因，但仍需确认具体丢失层级。Langfuse 可以帮助我们迂回观察和调查，却不能替代系统主动记录知识决策。最终目标也不是无限制地保存 Agent 的全部内部文字，而是能够稳定回答 Agent 需要什么知识、为什么这样查、为什么相信某份资料、知识如何影响最终任务、知识本身存在哪些问题以及下一步应该如何优化。做到这些之后，知识库才能从一个提供文件的基础设施，变成一个能够被监督、反馈和持续改进的 Agent 能力组成部分。
