# 阶段异常仍上报完成问题记录

> 记录学习 Code Agent 查询执行、阶段完成通知和 AI24 自动推进流程时发现的问题。本文只记录现状与建议，不代表问题已经修复。

## 一、问题结论

当前 `/task/query` 执行过程中，如果发生非用户主动中断的异常，Code Agent 会同时做两件相互矛盾的事：

1. 向用户上报“查询任务失败”和异常信息。
2. 调用 AI24 的 `sessionComplete` 接口，上报当前 `completedCommand` 对应的 Stage 已完成。

AI24 的 `sessionComplete` 当前只接收 `taskId` 和 `completedCommand`，没有接收成功、失败或错误原因。因此 AI24 无法通过这个回调区分“执行成功结束”和“发生异常后结束”，可能错误更新 `lastCompletedCommand`，并在 `autoExecute=true` 时继续执行下一阶段。

## 二、需要准确区分的范围

这个问题不是“主任务不管是否异常都会通过”，准确说法是：

- 受影响的是具体节点任务内部的当前 Stage，不是编排主任务本身直接通过。
- 用户主动中断会被 `was_interrupted` 识别，并跳过 `sessionComplete`。
- 非用户中断的执行异常仍会调用 `sessionComplete`。
- `sessionComplete` 不会直接把整个 `requirement_flow` 标记为 `DONE`，但可能错误推进节点任务内部的 Stage。
- 异常不只来自 Claude SDK，也可能来自 Code Agent 查询流程中的元数据、项目路径、UI 配置或未被内部捕获的代码异常。

## 三、当前实际流程

### 3.1 正常完成

```text
Claude 正常执行结束
    ↓
上报 SessionStatus.IDLE
    ↓
调用 sessionComplete(taskId, completedCommand)
    ↓
AI24 更新 lastCompletedCommand
    ↓
autoExecute=true 且存在 nextCommand
    → 自动执行下一阶段
```

### 3.2 用户主动中断

```text
用户调用 /task/interrupt
    ↓
was_interrupted=true
    ↓
Claude 查询被中断
    ↓
跳过 sessionComplete
    ↓
不自动进入下一阶段
```

### 3.3 非用户中断异常

```text
查询流程抛出异常
    ↓
上报 SessionStatus.IDLE
    ↓
was_interrupted=false
    ↓
仍调用 sessionComplete(taskId, completedCommand)
    ↓
异常继续向外抛出
    ↓
外层向用户上报“查询任务失败”
```

因此同一个任务可能同时出现：

```text
用户页面：Proposal 执行失败
AI24 阶段记录：Proposal 已完成
自动流程：开始执行 Apply
```

### 3.4 异常后自动进入下一 Stage 的准确条件

发生异常后，并不是任何情况下都一定进入下一 Stage。当前代码需要依次满足：

1. `was_interrupted=false`，即不是用户主动中断。
2. Code Agent 调用了 `complete_stage(taskId, completedCommand)`。
3. `complete_stage` 的 HTTP 回调成功到达 AI24。
4. 当前任务配置了 `autoExecute=true`。
5. AI24 根据工作流 Stage 列表找到了非空的 `nextCommand`。

满足以上条件后，AI24 会调用 `/task/query` 尝试执行下一 Stage。这里是“尝试启动”，下一次 `/task/query` 仍可能因为网络、状态或 Code Agent 异常而启动失败。

需要特别区分：

```text
autoExecute
    → 控制当前任务内部是否自动执行下一 Stage

AUTO_APPROVE_ON_BATCH_CREATE
    → 控制审批事项是否自动通过
```

异常后是否进入下一 Stage 使用的是 `autoExecute`，与自动审批开关无关。

另外，当前 `sessionComplete` 不检查以下内容：

- Claude 最终文字说“成功”还是“失败”。
- Proposal、Apply 等阶段是否生成了预期产物。
- 本轮是否得到业务结论。
- 普通工具调用是否曾经失败。

只要异常路径发送的完成回调成功到达 AI24，AI24 就会按照 `completedCommand`、`autoExecute` 和 `nextCommand` 处理。

## 四、哪些情况可能进入异常路径

这里的异常不等于普通工具失败。

普通的编译或测试失败通常以 `ToolResultBlock.is_error=true` 返回给 Agent，Agent仍有机会分析错误、修改代码并重新执行。这种失败属于 Agent 工作过程的一部分，不应该立即把整个 Stage 标记为失败。

会进入外层异常路径的情况可能包括：

- Claude 模型接口连接失败或超时。
- Claude CLI/SDK 进程异常退出。
- 鉴权失败、模型配置错误或服务不可用。
- `client.receive_response()` 消息流异常断开。
- 任务元数据缺失或项目路径无效。
- Figma、MasterGo 等必要配置缺失而主动抛出异常。
- Hook、消息处理或 Code Agent 自身未被内部捕获的 Python 异常。

这些异常本身并非完全不可见：Code Agent 会记录错误日志，也会向用户上报失败消息。真正的黑盒问题是系统没有统一、可信的阶段执行结果，AI24 只知道会话结束，却不知道阶段是否成功。

## 五、根本原因

当前流程混淆了两个概念：

```text
会话已经结束
≠
阶段执行成功
```

`SessionStatus.IDLE` 只应该表达 Agent 当前不再执行；`sessionComplete` 则应表达当前业务 Stage 已经成功完成。异常发生后可以上报 `IDLE`，但不应该同时无条件上报 Stage 完成。

另一个问题是完成接口缺少结果字段：

```text
当前：sessionComplete(taskId, completedCommand)

缺少：resultStatus、errorType、errorMessage、retryable
```

## 六、建议的状态模型

建议把阶段结果明确分为：

| 结果 | 含义 | 是否更新 lastCompletedCommand | 是否允许自动进入下一阶段 |
|------|------|-----------------------------|-------------------------|
| `SUCCESS` | 阶段产物和必要校验均完成 | 是 | 是 |
| `FAILED` | 系统、配置或执行异常导致阶段未完成 | 否 | 否 |
| `INTERRUPTED` | 用户主动停止 | 否 | 否 |

建议接口至少携带：

```json
{
  "taskId": "T100",
  "completedCommand": "/openspec:proposal",
  "resultStatus": "FAILED",
  "errorType": "MODEL_TIMEOUT",
  "errorMessage": "Claude SDK connection timeout",
  "retryable": true
}
```

也可以进一步拆成两个接口或两个事件：

```text
sessionEnded
    → 表示本轮会话已经停止，负责更新 IDLE

stageCompleted
    → 只在 Stage 业务成功后调用，负责推进工作流
```

## 七、失败后的处理建议

失败后不应该全部采用同一种策略，建议根据错误类型处理：

### 7.1 可重试错误

例如网络超时、模型服务临时不可用和部分 5xx 错误：

```text
Stage 失败
    ↓
保留当前 Stage
    ↓
自动重试有限次数
    ↓
仍失败则等待人工处理
```

### 7.2 不可直接重试错误

例如鉴权失败、模型名称错误、项目路径无效、缺少 Figma 配置和必要输入缺失：

```text
Stage 失败
    ↓
记录明确错误原因
    ↓
等待修复配置或补充输入
    ↓
人工触发重试
```

### 7.3 用户主动中断

```text
Stage 保持未完成
    ↓
不上报 FAILED
    ↓
记录 INTERRUPTED
    ↓
等待用户继续、重试或取消
```

## 八、怎样判断真正成功

仅收到 Claude SDK 的结束消息还不一定代表业务成功。建议至少同时满足：

- 查询流程没有抛出未处理异常。
- 任务没有被用户中断。
- SDK 最终结果不是错误结果。
- 当前 Stage 的强制门禁已经通过。
- Proposal、TDD 等有明确产物要求的阶段，必要文件和状态符合要求。

工具执行过程中出现过失败不应直接判定 Stage 失败；如果 Agent 后续完成修复、通过校验并正常结束，仍可以上报 `SUCCESS`。

## 九、最低验收标准

- Claude SDK 网络超时时，不调用成功语义的 `sessionComplete`。
- 查询流程抛出配置或路径异常时，不更新 `lastCompletedCommand`。
- 失败后不会因为 `autoExecute=true` 自动进入下一阶段。
- 用户主动中断时记录 `INTERRUPTED`，不记录 `SUCCESS` 或 `FAILED`。
- 普通工具失败后 Agent 成功修复并正常结束，可以正确记录 `SUCCESS`。
- 正常成功的 Stage 只上报一次完成，重复回调不会重复触发下一阶段。
- 页面展示、AI24 阶段状态和编排状态表达一致，不再同时出现“执行失败”和“阶段已完成”。

## 十、当前结论

当前代码能够看到异常日志和失败消息，因此问题不完全是 Claude SDK 黑盒；真正缺失的是“会话结束”和“阶段成功”的语义分离。非用户中断异常仍上报阶段完成，可能导致自动流程在前一阶段没有产物的情况下继续执行，应该作为工作流可靠性问题单独处理。
