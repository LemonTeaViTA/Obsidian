# Agent 必读文档约束改进记录

> 记录学习 Code Agent 提示词和 Hook 流程时发现的问题。本文只记录现状与建议，不代表功能已经实现。

## 一、发现的问题

当前系统提示词会要求 Agent 在执行任务时读取 PRD，并告诉 Agent PRD 的本地路径。正常情况下，Agent 会按照提示词使用 `Read` 工具读取文件。

但“提示词要求必须读取”目前仍属于软约束，系统没有明确验证：

- Agent 是否真的读取了 PRD。
- Agent 是否读取了正确任务对应的 PRD。
- 读取失败后是否进行了重试。
- Agent 是否在修改代码之前完成了阅读。
- PRD 更新后，Agent 是否重新读取了新版本。

因此当前只能根据工具日志或会话记录事后判断，不能在执行过程中强制保证。

## 二、风险

如果 Agent 没有读取 PRD 就开始修改代码，可能出现：

- 只根据用户的一句话理解需求，遗漏完整背景。
- 忽略业务边界、异常场景和验收要求。
- 使用了上一轮对话中的旧需求信息。
- 方案和代码实现正确，但解决的不是 PRD 中的真实问题。

即使工具记录显示 Agent 调用过 `Read`，也只能证明它打开过文件，不能完全证明它理解并使用了内容。因此门禁只能先解决“是否读取”，更高层的“是否理解”还需要方案引用、需求摘要或审核机制配合。

## 三、检查时机

最合适的强制检查点是第一次修改代码或项目文件之前。

原因：

- 文件阅读的先后顺序不重要，只要在行动前完成即可。
- 不需要打断 Agent 正常的搜索、分析和目录浏览。
- 一旦开始 `Write`、`Edit` 或执行有写入效果的 Bash 命令，就代表 Agent 已经开始实施方案，此时必须确认必要上下文已经读取。

建议流程：

```text
/task/query 开始
    ↓
生成本阶段的必读文件列表
    ↓
Agent 自由搜索和阅读
    ↓
记录已经成功读取的文件
    ↓
Agent 第一次尝试修改项目
    ↓
检查必读文件是否全部读取
    ├── 已读取 → 放行修改
    └── 未读取 → 拒绝本次修改
                 提示缺少哪些文件
                 要求读取后重试
```

## 四、避免 Hook 数量失控

不建议为 PRD、CLAUDE.md、审批文档和每一种知识文件分别创建一个 Hook。这样会导致 Hook 数量越来越多，规则重复、执行顺序复杂，也难以排查究竟是哪一个 Hook 拦截了操作。

更合适的方式是实现一个通用的 `RequiredContextGateHook`，通过配置决定当前任务和当前阶段必须读取哪些文件：

```text
RequiredContextGateHook
    ├── required_files：本阶段必读文件
    ├── read_state：已经成功读取的文件
    ├── trigger_tools：会触发检查的修改类工具
    └── policy：阻止、警告或放行
```

例如：

```json
{
  "required_files": [
    "prd.md",
    "openspec/changes/{task_id}/design.md"
  ],
  "check_before": [
    "Write",
    "Edit",
    "MultiEdit",
    "NotebookEdit",
    "BashWrite"
  ],
  "policy": "block"
}
```

一套 Hook 可以服务不同任务，不需要每增加一个文件就增加一个新 Hook。

## 五、哪些文件应该强制阅读

不能把所有知识库文件都加入必读列表，否则 Agent 会为了通过门禁读取大量与任务无关的内容，浪费时间和上下文。

建议分为三类：

| 类型 | 示例 | 建议策略 |
|------|------|---------|
| 强制必读 | 当前任务 PRD | 修改前必须读取 |
| 阶段必读 | 上阶段设计文档、审批产物、当前 TDD Manifest | 根据阶段动态加入 |
| 按需阅读 | 通用知识库、领域知识、应用知识 | 由 Agent 搜索，不做全量门禁 |

`CLAUDE.md` 通常由 Claude Code 按项目配置自动加载，可以优先验证加载链路，不一定需要再增加一次文件读取门禁。

## 六、实现时需要注意

1. **读取状态按任务保存**：不能让一个任务读取 PRD 后，错误地放行另一个任务。
2. **校验规范化路径**：防止读取同名但错误目录下的 `prd.md` 后通过门禁。
3. **记录文件版本**：可以保存文件哈希或修改时间；PRD 发生变化后，旧的读取状态应失效。
4. **识别真正的修改操作**：`Write`、`Edit` 容易识别，Bash 命令需要判断是否会写文件，避免把 `ls`、`rg` 等只读命令误拦截。
5. **处理读取失败**：只有工具成功返回后才能标记为已读，文件不存在或读取报错不能放行。
6. **支持不同强度**：强依赖 PRD 的任务使用阻止模式，普通自由问答可以只告警或不启用。
7. **保留可观测记录**：日志中应说明缺少哪个文件、拦截了哪个工具，以及后来何时满足条件。

## 七、最低验收标准

- Agent 未读取当前任务 PRD 时，第一次修改操作会被拦截。
- 提示信息能够明确告诉 Agent 需要读取的文件路径。
- Agent 成功读取正确文件后，再次执行修改可以通过。
- 只读搜索命令不会被误拦截。
- PRD 更新后，原来的已读状态自动失效。
- 不需要为每一种必读文件创建独立 Hook。
- 普通知识库文件不会被错误要求全量读取。

## 八、当前结论

当前系统主要依靠提示词要求 Agent 阅读 PRD，通常能够工作，但缺少工程上的强制证明。建议未来使用一个可配置的通用必读上下文门禁，在第一次修改项目之前检查必要文件是否已经读取，同时控制必读范围，避免 Hook 和无关阅读无限增加。
