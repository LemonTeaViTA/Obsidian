一、调研背景

随着前端、后端和客户端系统模板逐步完善，模板中定义的执行步骤、产物、状态和完成条件，与 AI24、Code Agent、OpenSpec 以及外部构建和测试平台之间可能出现差异。

本次调研关注的不是提示词写作质量，而是系统模板能否在当前软件工厂中按预期执行。调研重点回答四个问题：模板能否被工作流正确选中和组装，模板要求的产物能否被后续阶段找到，模板定义的完成条件是否与软件工厂门禁一致，外部工具和平台协议是否与模板中的调用方式一致。

本报告面向 Leader、模板维护者、软件工厂研发和业务研发同学。正文只呈现主要结论和影响，具体代码路径和核对依据见配套的《系统模板与软件工厂一致性调研证据表》。

二、调研范围

| 领域 | 模板数量 | 主要阶段 |
|---|---:|---|
| 前端 | 7 | Proposal、技术方案、测试规范、编码、Apply、视觉验证、工作总结 |
| 后端 | 5 | Proposal、测试用例、测试脚本、Apply、Build |

三个“前端（社区）”模板目前只有名称、版本和时间，没有提示词正文，因此未纳入内容一致性分析。

模板版本和时间以平台列表中模板名称对应的记录为准，不使用提示词正文中后来出现的版本文字作为平台版本依据。

本地归档文本中有三处 Unicode 替换字符，也出现在本次对话收到的文本中。它们不影响本报告的主要结论，但在取得平台原始导出前，不能据此声明归档正文与平台正文逐字一致。

四、总体结论

本次调研认为，三套系统模板的业务目标和阶段划分总体清楚，质量要求也比较完整，但模板与软件工厂之间尚未形成统一、可验证的执行协议。

主要差异集中在以下六个方面。

第一，模板装配机制没有被模板准确表达。

软件工厂将 Stage 和 Convention 分开获取，Convention 需要显式引用。部分前端模板使用普通文件名引用规范，不会触发当前 Convention 获取机制；部分客户端模板使用与 Stage 同名的 `@/openspec:*` 引用，当前 Agent 会按 Convention 查询。若线上没有额外配置同名 Convention，就无法按模板预期加载。系统模板存在并不代表工作流运行时一定加载了它。

第二，阶段产物的目录、文件名和传递方式不统一。

前端部分模板使用 `changes/<change-id>`，软件工厂使用 `openspec/changes/<taskId>`。后端部分阶段从任务根目录读取上游文档，但上游实际写入 OpenSpec change 目录。客户端新增了多个结果文件，这些文件没有对应的通用文档类型和跨任务恢复通道。

第三，模板完成条件与软件工厂门禁不是同一套标准。

模板通常要求完整行为覆盖、真实测试、全部任务完成和质量审计，但当前部分门禁只检查文件是否存在或状态字段是否满足。部分门禁达到有限重试次数后会放行，执行异常也可能继续上报阶段完成。

第四，TDD 状态和测试文件保护规则存在直接冲突。🔄

前端模板允许多个 case 共用测试文件并逐个追加测试，当前测试文件锁会在共享文件中任一 case 进入 RED 后冻结整个文件。前端模板使用 `READY_FOR_PR` 作为完成状态，当前 Stop 门禁的直接通过条件使用 `GREEN`。后端 manifest 字段又与当前 Hook 读取的字段不一致，导致部分保护机制不能按模板预期生效。

> 🔄 **需要重新验证**：AI24 已将 `TddApprovalFeedbackService` 重构为通用 `ApprovalFeedbackService`，manifest 字段协议可能已修复。详见[关键功能变化详解](./关键功能变化详解-20260812.md#一tdd-审批流程重构)

第五，外部工具协议存在版本漂移。🔄

前端视觉流程和客户端 UI 自动化模板使用的 MCP 工具名，与当前 Code Agent 固定提示或现有设计文档中的工具名不一致。客户端打包模板要求 `zeus_app` 和专用交付脚本，但当前 Code Agent 配置的是 `zeus`、`zeus-ci`，也没有找到该交付脚本的注入逻辑。客户端模板创建时间晚于当前 Code Agent 和 AI24 代码基线，表现出模板已经先于软件工厂代码演进。

> 🔄 **部分已改进**：Code Agent 已对接 Figma 官方 MCP 并升级 Web 视觉验证至 V3。新工具包括 `web_validation_build_assets` 和 `web_validation_submit_assets`。但 UI Test Automation 和 Zeus 的工具列表仍需线上确认。详见[关键功能变化详解](./关键功能变化详解-20260812.md#二web-视觉验证工具重构)

第六，部分质量结论缺少可执行证据。

前端视觉流程关闭平台视觉对比，却要求给出精确像素差异率。Android Apply 阶段禁止执行 Gradle 测试，后续打包模板又没有明确要求执行这些测试。后端 Build 阶段声明零警告和全量 GREEN，但实际命令没有完整执行这些判定。

五、前端模板调研结论

前端模板在需求行为、组件设计、测试层级、真实实现和交付审计方面形成了较完整的方法，但在软件工厂中存在以下主要问题。

1. Proposal 输出目录与软件工厂目录不一致，可能导致门禁、文档上传和 Apply 找不到规划产物。

2. Proposal 引用的验收标准、技术方案和测试规范没有使用当前 Convention 引用格式。其中验收标准对应模板也未在本次七个模板中找到。

3. Proposal 要求六份规划产物，当前门禁只检查其中四份是否存在，也不校验内容完整性。

4. “编码”和“Apply”两个模板都覆盖完整 RED、GREEN、REFACTOR、全量验证和总结，阶段职责明显重叠。若两者都配置为工作流 Stage，会重复执行和重复提交；若其中一个是 Convention，需要明确其引用关系。

5. 共享测试文件规则与当前测试文件锁相反。模板允许后续 case 继续向共享文件追加测试，当前 Hook 会在首个 case 进入 RED 后锁住整个文件。

6. manifest 外层状态协议不一致。模板最终设置 `READY_FOR_PR`，当前 Stop 门禁直接完成条件使用 `GREEN`，同一轮执行中可能出现重复拦截后再放行。

7. 视觉验证使用的 UI Test Automation 和 Figma 工具名与当前工厂声明存在差异，远程 MCP 的实际工具列表仍需线上确认。

8. 模板要求精确视觉差异率，但提交给 UI Test 平台的配置关闭了平台视觉对比，当前仓库也没有找到独立像素差异计算闭环。

9. 工作总结输出在 `docs/work-summary`，文档自动上传只识别 OpenSpec change 目录中的 `summary.md`。除非另行主动上传，总结无法通过当前自动上传规则进入 AI24 文档记录。

综合判断：前端方法体系较完整，但模板装配、目录、TDD Hook 和视觉工具协议尚未对齐，不应仅根据模板内容判断工作流已经具备完整 TDD 和视觉验收能力。

六、后端模板调研结论

后端流媒体模板强调线程、内存、媒体质量、反哨兵和真实 RED，方向明确，但阶段之间存在较大的协议断层。

1. Proposal 一方面声明唯一产物只有 `design.md` 和 `test_design.md`，另一方面又引用基础 TDD Proposal 的 tasks 和 manifest 步骤。当前 Proposal 门禁要求四份文件，模板自身的阶段边界与工厂门禁不一致。

2. Proposal 规划了集成测试、媒体质量测试和并发边界，但测试用例阶段明确排除这三类内容。本次模板集合中没有找到承接这些测试的后续阶段，因此规划覆盖没有形成交付闭环。

3. 测试用例阶段从任务根目录读取上游设计，实际 Proposal 产物位于 OpenSpec change 目录。文件缺失时模板允许跳过，可能在缺少技术方案的情况下继续生成用例。

4. 测试脚本生成的 manifest 字段使用 `file`，当前 TDD Hook 使用 `test_file`。测试文件锁因此无法根据该 manifest 正确定位测试文件。

5. 测试脚本把链接期 `undefined reference` 定义为唯一合法 RED。这只适用于新增未实现符号，不适用于修改已有行为时常见的运行期断言失败。

6. 测试脚本通过管道截取构建输出后读取退出码，在未启用 pipefail 的情况下得到的是 `tail` 的退出码，不能可靠取得编译命令退出状态。

7. Apply 从任务根目录读取 manifest，与测试脚本实际写入位置不一致；多个阶段的工作目录约定也不统一。

8. Build 只检查 manifest 中没有 RED，没有检查 PENDING 或未知状态；通过数量又可以被仓库中无关的既有测试满足。

9. Build 声明零警告，但只统计 warning 数量，没有把 warning 大于零作为失败条件。代码增量比例使用仓库最早提交作为基线，也不能准确表示本次变更。

10. 后端多个阶段使用 `-j$(nproc)`，与 Code Agent 固定系统提示中“C++ 编译必须使用固定核心数、不能占满机器资源”的约束冲突。

11. Build 的无 RED 检查使用 `grep -c ... || echo 0`。在没有 RED 的正常场景中会得到两个 `0`，后续数值判断报错，可能使预期成功的 Gate A1 反而失败。

12. 测试脚本把 manifest 外层状态设为 `RED`，Apply 只要求把 case 改为 `GREEN`，没有同步更新外层状态。启用当前 TDD Stop Gate 时，即使所有 case 已通过，仍可能因外层状态为 `RED` 被重复拦截。

综合判断：后端模板有较强的领域约束，但当前五个阶段没有形成一致的输入路径、manifest 协议和测试覆盖闭环，部分 Shell Gate 本身也不能按文字说明工作。

七、客户端模板调研结论

客户端模板对 Android 开发、Zeus 打包和 UI 自动化的流程描述很细，但这套模板明显依赖一批当前代码基线尚未提供的新能力。

1. 模板大量使用 `{{CHANGE_ID}}`、`{{EXECUTION_ROOT}}`、`{{ANDROID_APP_DELIVERY_SCRIPT}}` 等占位符。当前模板获取链路只返回模板正文并追加 Git URL，没有找到通用占位符替换机制。部分简单变量可以由模型理解，交付脚本路径和版本则无法自行推导。

2. Android 打包模板只允许使用 `zeus_app` MCP，当前 Code Agent 配置的是 `zeus` 和 `zeus-ci`，没有 `zeus_app` server。模板要求的 Android 专用交付脚本在 Code Agent 和 AI24 代码中也没有找到注入实现。

3. Android Apply 模板要求阶段结束上报状态 310，并明确禁止提前上报 500；当前 AI24 对 `/openspec:apply` 下发的完成 Hook 会在结束时无条件补报 500。若客户端 Apply 使用该命令，会产生状态语义冲突。

4. Android Apply 禁止执行任何 Gradle 测试，只记录预期 RED 和 GREEN；后续打包模板只验证 Zeus APK 构建，没有明确验证 Apply 阶段记录的单元测试和组件测试。测试可能从设计、编码直接进入交付，但缺少真实执行证据。

5. Android Apply 对 UI 自动化 Mock 的默认值同时要求“默认开启”和“默认关闭”，完成标准也要求默认开启。该规则会直接影响 Release 安全边界和 UI 自动化可用性。

6. `pack_result_info.json` 默认不提交、不推送，也没有对应文档上传类型。如果 UI 自动化阶段不在同一工作区继续运行，打包结果无法通过当前通用文档协议恢复。

7. Android 和 iOS UI 自动化模板要求 `ui_task_batch_create`、`ui_task_execute`、`ui_task_detail`。当前 Code Agent 设计文档仍声明 `ui_test_submit` 和 `ui_test_status`，远程平台是否已经升级到新工具名需要线上确认。

8. UI 自动化模板使用 `@/openspec:proposal`、`@/openspec:apply` 等与 Stage 同名的上下文引用。当前 Code Agent 会把所有 `@` 引用按 Convention 查询；如果线上没有额外配置这些同名 Convention，就无法取得对应 Stage 内容。

9. Android UI 自动化模板的参数表示例写成了 iOS 平台，并使用与表格固定值不同的 App 参数，存在直接的示例误导。

10. UI 自动化发现业务代码问题后，模板要求提交修复并直接重新创建 UI 任务，没有明确重新执行打包。新的业务代码可能仍然使用旧 APK 进行验证。脚本修复也没有明确要求带 author 提交并推送，远程平台可能看不到本地修复。

11. iOS UI 自动化依赖 `pack_result_info.json`，但本次客户端模板中没有 iOS 开发和 iOS 打包模板，iOS 链路无法仅依靠当前四个模板独立闭环。

综合判断：客户端模板对目标流程的描述很具体，但模板版本晚于当前软件工厂代码，部分工具、脚本和变量注入能力尚未在当前仓库落地。客户端结论还需要结合目标 App 仓库、Zeus 实际工具列表和 UI 自动化平台协议复核。

八、可能造成的影响

这些差异可能产生以下结果：

1. 系统模板已经创建，但当前工作流仍引用旧模板或根本没有加载对应 Convention。

2. 上游阶段已经生成文件，下游阶段因目录、文件名或跨任务传递不一致而无法读取。

3. 测试、任务或文档尚未完整，门禁仍然放行并推进下一阶段。

4. 模板要求的测试看似有 RED 和 GREEN 记录，但实际测试没有运行或没有被当前 Gate 验证。

5. 若运行时工具列表未提供模板引用的 MCP 工具，执行会在中途停止。其中客户端打包模板要求的 `zeus_app` 未出现在当前 Code Agent 配置中；前端视觉和客户端 UI 自动化工具仍需线上核对。

6. 修复已经提交，但没有重新打包或推送，自动化测试继续验证旧代码或旧安装包。

7. 失败或阻塞状态被工作流完成上报覆盖，Leader 和使用者看到的任务状态与真实交付状态不一致。

九、需要线上继续确认的信息

以下信息无法从当前代码仓库直接确认：

1. 三套工作流当前的 workflowNo、workflowTemplateId、版本和更新时间。

2. 每个 Stage 的 command、templateId，以及每个 Convention 的 command、templateId。

3. 前端工作流是否命中 TDD_WORKFLOW_NOS 和 GET_TEMPLATE_LATEST_WORKFLOW_NOS。

4. 前端任务实际使用的 flowType、uiMcpType，以及 Figma、MasterGo 和 UI Test Automation 的运行时工具列表。

5. 客户端任务是否存在模板正文之外的占位符替换和 Android 交付脚本注入机制。

6. Zeus 实际 MCP server 名称、Job 759 和 Job 438 的字段协议。

7. UI 自动化平台当前是否提供新版本的三个批量任务工具。

8. Android、iOS 和流媒体目标仓库的实际目录、构建脚本、测试目标和分支策略。

9. 当前生产环境部署的 AI24 和 Code Agent Commit 是否与本次本地基线一致。

十、最终判断

三套系统模板已经形成较完整的业务方法和质量要求，但还没有与软件工厂代码形成统一、可机器判定的协议。当前最需要关注的不是继续增加提示词长度，而是确认模板装配、产物目录、manifest、阶段状态、文档传递和 MCP 工具契约是否一致。

在完成线上工作流绑定和运行时工具核对前，本报告不判断三套工作流已经在线上发生故障，也不判断模板完全不可用。可以确认的是，按当前代码基线直接执行这些模板，会在多个阶段遇到确定的协议差异；其中客户端模板还依赖当前代码基线尚未发现的新增能力。

详细问题、模板位置和代码路径见《系统模板与软件工厂一致性调研证据表》。
