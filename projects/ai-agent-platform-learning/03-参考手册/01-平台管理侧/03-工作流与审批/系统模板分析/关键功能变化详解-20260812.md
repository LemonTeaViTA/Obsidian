# 软件工厂关键功能变化详解（2026-08-12）

> 本文档详细说明 AI24 和 Code Agent 在 2026-07-19 至 2026-08-12 期间的重要功能变化

---

## 一、TDD 审批流程重构

### 1.1 变化概述

**时间线**：2026-08-11 至 2026-08-12  
**影响范围**：所有涉及审批的工作流（前端、后端、客户端）

### 1.2 核心变化

#### 服务重构

**之前**：
```java
TddApprovalFeedbackService  // 仅支持 TDD 审批
```

**现在**：
```java
ApprovalFeedbackService  // 通用审批服务
├── TDD 测试审批
├── 技术方案审批
├── 测试清单审批
├── 领域划分审批
└── PM 审批
```

**关键改进**：
- 使用 `EnumSet` 管理审批类型，替代硬编码判断
- 统一的审批反馈接口
- 支持动态扩展新的审批类型

#### 新增审批接口

| 接口 | 用途 | 典型场景 |
|---|---|---|
| `addApprovalItem()` | 动态补充遗漏的审批项 | 审批过程中发现新问题 |
| `upsertApprovalItem()` | 创建或重新提交审批项 | 技术方案、测试清单等标准审批 |
| `getPmConfirmItems()` | 获取 PM 确认项 | 领域划分驳回后的 PM 二次确认 |
| `confirmByPm()` | PM 确认并流转给产品 | PM 审核驳回内容后提交 |
| `rejectDomainDivideBatchToProduct()` | 一键驳回至产品 | 技术 PM 终止领域划分批次 |

### 1.3 领域划分审批增强

#### 新增字段

```java
// 支持标记删除审批项
{
  "deleteItem": true,  // 新增字段
  "confirmItem": "xxx",
  "itemOwner": "xxx"
}
```

**用途**：在审批过程中标记某些项为"待删除"，而不是直接物理删除

#### 驳回流程优化

**之前**：驳回后直接发送给 code-agent

**现在**：驳回 → PM 确认 → 产品（带驳回原因）→ code-agent

```
┌─────────────┐
│ 领域划分审批 │
└──────┬──────┘
       │ REJECT
       ▼
┌─────────────┐
│  PM 二次确认 │  ← 新增环节
└──────┬──────┘
       │ confirmByPm()
       ▼
┌─────────────┐
│  通知产品    │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ Code Agent  │
└─────────────┘
```

### 1.5 对系统模板的影响

#### 需要重新验证的点

1. **manifest 字段协议**
   - 原调研报告指出后端测试脚本使用 `file` 字段，而 Hook 读取 `test_file`

3. **多人审批**
   - 新增了多人审批候选人和实际审批人回写
   - **建议**：检查前端技术方案模板是否支持多人审批场景

## 二、Web 视觉验证工具重构

### 2.1 变化概述

**时间线**：2026-07-21 至 2026-08-04  
**影响范围**：前端工作流的视觉验证阶段

### 2.2 Figma 官方 MCP 对接

#### MCP 路由策略

| ui_mcp_type | 服务地址 | 认证方式 | 核心工具 |
|---|---|---|---|
| `figma` (新方案) | `https://mcp.figma.com/mcp` | OAuth 2.0 | `get_code`, `get_screenshot`, `get_variable_defs` |
| `figma_pat` (原方案) | `http://127.0.0.1:{port}/message` | PAT | `get_figma_file`, `search_nodes`, `export_images` |
| `mastergo` (保持不变) | stdio MCP | - | MasterGo 专有工具 |

#### 官方 MCP 优势

1. **设计转代码能力**
   - `get_code` 工具可直接生成 React + Tailwind 代码
   - 支持从 Figma 设计稿生成可用的组件代码

2. **无需本地服务**
   - 直接连接 Figma 云端 MCP
   - 简化部署，无需维护本地 MCP 进程

3. **官方维护**
   - 工具能力由 Figma 官方持续更新
   - 更好的稳定性和兼容性

### 2.3 节点级验证流程 V3

#### 核心原则

```
PRD 视觉改动 = PRD ∩ Figma Frame ∩ 真实 DOM
```

**严格约束**：
1. 只使用初始化 Figma nodeId 自身或后代 Frame
2. 不得从图层名、组件名猜测 class
3. 不得绕过 UI Test Automation MCP 直调 Runtime
4. 每个 run 绑定已推送的不可变 commit

#### 工作流程

```
┌──────────────────────────────────────────────────────┐
│ 1. 确认阶段和必要输入                                 │
│    - taskId, PRD, repoUrl, branch, Figma URL        │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 2. 阅读 PRD，产出"PRD 视觉改动清单"                   │
│    - 组件、状态、路由、viewport、功能路径             │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 3. 在 Figma 初始化 nodeId 子树内定位最小 Frame       │
│    - 使用 get_metadata 获取层级                       │
│    - 使用 get_design_context 理解布局                │
│    - 使用 get_screenshot 确认候选                    │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 4. 按 PRD 和 Figma 完成开发                          │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 5. selector preflight（在真实 DOM 中验证）           │
│    - validationHints 中的每个 locator               │
│    - readySelector                                  │
│    - stateSetup.preActions 中的全部 selector        │
│    - functionalScenarios 中的全部 selector          │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 6. web_validation_build_assets                       │
│    - 构建稀疏资产（不传完整节点 JSON）                │
│    - 返回短 assetRef                                 │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 7. web_validation_submit_assets                      │
│    - 提交 assetRef（不是直接调用 ui_web_validation）│
│    - 绑定不可变 commitId                             │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 8. 持续 status 查询到终态                            │
│    - 使用 UI Test Automation MCP                    │
└────────────────┬─────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────┐
│ 9. 按 Gate、failureType 修复或转人工                │
│    - 源码修复：新 commit + 新 run                    │
│    - 配置修复：同 commit + 新 run                    │
└──────────────────────────────────────────────────────┘
```

#### 关键工具

| 工具 | 用途 | 参数 |
|---|---|---|
| `mcp__figma__get_metadata` | 获取 Frame 层级和几何信息 | `fileKey`, `nodeId` |
| `mcp__figma__get_design_context` | 获取布局、样式、组件信息 | `fileKey`, `nodeId` |
| `mcp__figma__get_screenshot` | 核对构图和选定范围 | `fileKey`, `nodeId`, `contentsOnly=true` |
| `mcp__web-validation-tools__web_validation_build_assets` | 构建节点资产 | 完整的 target 描述 |
| `mcp__web-validation-tools__web_validation_submit_assets` | 提交验证任务 | `assetRef`, `commitId` |

### 2.4 assetRef 机制

#### 之前的问题

- 模型需要处理完整的 Figma 节点 JSON（可能几十 KB）
- 重复传输大对象，浪费 token
- 容易在传输过程中修改或删改设计数据

#### 现在的方案

```
┌────────────────────────────────────────────────────┐
│ 1. Agent 调用 web_validation_build_assets          │
│    传入：target 描述（PRD、Frame、selector 等）      │
└──────────────────┬─────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────┐
│ 2. MCP Server 构建完整资产                          │
│    - DesignSpec (Figma 设计数据)                   │
│    - MappingManifest (设计到代码映射)              │
│    - visualTargets (验证目标列表)                  │
└──────────────────┬─────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────┐
│ 3. 服务端存储完整资产，返回短 assetRef             │
│    返回：{ "assetRef": "abc123xyz", "summary": ... }│
└──────────────────┬─────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────┐
│ 4. Agent 只需传递 assetRef                          │
│    web_validation_submit_assets(assetRef, commitId)│
└────────────────────────────────────────────────────┘
```

**优势**：
- Agent 不需要处理大对象
- 避免设计数据在传输中被修改
- 服务端可以对资产进行版本管理

### 2.5 对系统模板的影响

#### 前端模板需要适配的点

1. **视觉验证工具名**
   - 原模板可能使用旧的工具名
   - **需要确认**：是否更新为 `web_validation_build_assets` 和 `web_validation_submit_assets`

2. **Figma 读取方式**
   - 不再需要传递 `figmaVersion`
   - 使用 `get_design_context` 替代完整的 `get_figma_file`
   - **需要确认**：前端视觉验证阶段的提示词是否更新

3. **视觉差异计算**
   - 原调研报告指出"关闭平台视觉对比，却要求精确像素差异率"
   - **需要确认**：V3 流程如何处理视觉差异计算

4. **独立阶段配置**
   - V3 要求 `/web-validation-node` 独立阶段
   - **需要确认**：前端工作流是否已配置该独立阶段

## 四、其他重要更新

### 4.1 MCP 服务增强

#### 新增 MCP Server

1. **backstage MCP**
   - 查询架构元数据
   - 获取服务配置信息

2. **neo4j-query-remote MCP**
   - 远程查询 Neo4j 拓扑图
   - 支持 SSE (Server-Sent Events)

3. **code-agent-web-validation-tools MCP**
   - 独立的 Web 验证工具服务
   - 与 Figma MCP 分离

#### 配置增强

```json
{
  "mcpServers": {
    "backstage": {
      "url": "${BACKSTAGE_MCP_URL}",
      "alwaysLoad": true  // 新增参数
    },
    "neo4j-query-remote": {
      "url": "${NEO4J_QUERY_REMOTE_MCP_URL}",
      "alwaysLoad": false
    }
  }
}
```

**alwaysLoad 参数**：
- `true`：启动时立即加载 MCP Server
- `false`：按需加载（首次调用时加载）

### 4.2 Code Agent 系统提示词更新

#### Git Commit Author Hook 增强

**之前**：提醒使用 MCP 获取 author

**现在**：**强制要求**通过 MCP 获取 author 并 push

```
如果 commit 缺少 author 信息：
1. 必须调用 MCP 工具获取 author
2. 重新 commit 并 push
3. 不得使用默认 author 或跳过此步骤
```
