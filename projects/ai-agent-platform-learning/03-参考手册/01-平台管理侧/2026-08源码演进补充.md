# 2026-08 源码演进补充

> [!tip] 速览
> 2026-07-23 之后，ai24 的主要变化不是“又加几个 Controller”，而是把审批、工作台、产物和拓扑都推进成可独立演进的领域能力。旧文中的任务主链仍有参考价值，但审批数据模型和系统边界必须按本文理解。

## 一、审批模型从父表字段走向角色明细

### 1.1 当前数据职责

| 数据 | 当前职责 |
|------|----------|
| `approval_item` | 审批事项、批次、业务内容与整体状态 |
| `approval_item_approver` | 某审批项下某角色的候选审批人和当前状态 |
| `confirmer` / `tester` | 从明细投影出的候选人 CSV，兼容既有查询和 DTO |
| `developerConfirmStatus` / `testerConfirmStatus` | 返回给前端的角色级状态投影，不写回父表 `extend` |

明细表的关键字段是：

```text
approval_item_id + approval_type + approver + approval_status
```

其中 `approval_type` 只支持 `DEVELOPER` 和 `TESTER`，角色状态为：

- `PENDING`：待审批
- `APPROVED`：已通过
- `REJECTED`：已拒绝
- `NOT_REQUIRED`：该角色无需审批，仅用于对外投影

### 1.2 ANY_ONE 的真实语义

同一角色可以有多个候选人，但它不是多人会签：

1. 查询父审批项并持有批次锁。
2. 在该角色的 `PENDING` 明细中确认当前 SSO 用户。
3. 把获胜行更新为终态。
4. 删除同角色其他候选行。
5. 终态角色只保留实际操作人的一行。

因此“任意一人决定该角色”仍成立，但实际操作人不再依赖一个单独的 `actual_confirmer` 字段；明细终态行和其 `extend.actualOperator` 提供可追踪证据。

### 1.3 两个角色与整体状态

开发和测试是两个独立角色。`APPROVED` 或 `NOT_REQUIRED` 都算角色已满足；整体审批是否完成，要由两个角色状态和事项策略共同判断。前端显示两个角色状态徽标，不能只看父项的一个 `confirmStatus` 就推断谁已经处理。

相关源码：

- `ai24-core/.../approval/ApprovalApproverDomainService.java`
- `ai24-core/.../approval/ApprovalRoleStatusProjection.java`
- `ai24-persist/.../ApprovalItemApproverDO.java`
- `ai24-persist/.../ApprovalRoleStatusEnum.java`

## 二、审批写入增加批次与差量语义

### 2.1 主接口

| 接口 | 用途 |
|------|------|
| `POST /api/approvalItem/batchCreate` | 当前批次为空时首次创建审批项 |
| `POST /api/approvalItem/update` | 兼容旧调用方，更新单个未通过审批项 |
| `POST /api/approvalItem/reconcile` | 预览或原子应用审批批次差量 |
| `POST /api/approvalItem/approve` | 通过或拒绝一个角色，状态由请求体表达 |
| `GET /api/approvalItem/query` | 查询任务审批项聚合详情 |
| `POST /api/approvalItem/updateConfirmer` | 修改开发、测试审批人或跟进人 |

`approve` 没有单独的 reject endpoint；传 `confirmStatus=APPROVED` 或 `REJECTED`。线上操作人由服务端 SSO 注入，请求体中的 operator 不能作为可信身份。

### 2.2 reconcile 为什么存在

整批重建简单，但会丢失“哪些项没变、哪些项已审批”的语义。`reconcile` 请求包含：

- `dryRun`：只计算变化，不落库
- `expectedBatchToken`：防止预览后批次被别人修改
- `decisions`：对每个逻辑项声明创建、更新、删除或保留
- `allowDeleteApproved`：删除已通过项时必须显式确认

响应把 `created`、`updated`、`deleted`、`unchanged`、`conflicts` 分开返回，并携带新的 `batchToken`。这比“把变化项再次 batchCreate”安全，因为批量接口具有整批覆盖语义。

### 2.3 存储迁移已经收口

最新 `master` 删除了 `ApprovalApproverStorageMode*`、`ApprovalApproverMigration*` 和迁移 Controller，不再维护父表、双写、明细表三种运行模式。当前业务查询、工作台和角色状态统一以 `approval_item_approver` 为事实源；这些删除表示迁移期兼容路径结束，不表示角色明细模型被撤回。

### 2.4 APP_SPLIT 增加领域技术方案

应用拆分的普通审批项新增 `domainTechnicalDesignContent`，持久化到 `approval_item.domain_design`。约束不是“有就展示”：

- 首次创建和 reconcile 的目标项必须带非空 Markdown。
- 单项兼容更新只有在数据库已有非空方案时才可省略。
- PM 项和其他事件类型禁止携带该字段。
- 契约与领域技术方案都进入 reconcile 的 `sourceRefs` / `sourceDigest`，但只有领域技术方案正文进入普通项 target。

## 三、个人工作台成为首页读模型

### 3.1 接口

```text
GET /api/workbench
  ?approvalStatus=PENDING|PROCESSED
  &requirementStatus=RUNNING|DONE
  &pageNum=1
  &pageSize=20
```

服务端从 SSO 获取当前用户名，未登录返回业务码 `401`。返回值一次聚合：

- `pendingApprovals`：待我审批或已处理任务
- `participatingRequirements`：我参与的需求及当前阶段
- `approvalTotal` / `requirementTotal`：两类列表各自的分页总数

当前流程阶段投影为 `PRD_AUDIT`、`APP_SPLIT`、`APP_DEVELOP`。这是一张面向首页的读模型，不应让前端分别拼多套任务和审批接口。

相关源码：`PersonalWorkbenchController`、`PersonalWorkbenchService`、`PersonalWorkbenchVO`。

## 四、产物从单份内容演进为版本链

### 4.1 版本历史接口

```text
GET /api/taskInfo/artifact/history/{artifactId}
```

响应包含当前版本、当前内容和历史版本数组。前端据此提供时间线、展开、下载，以及旧契约 / 新契约 / diff 三种视图。

这里要区分“接口与组件存在”和“页面可达”：旧契约 / 新契约 / diff 已由 `TaskArtifactsViewer` 接入任务详情；历史查询 hook 与抽屉已经实现，但组合它们的 `NodeArtifactsViewer` 尚未被任何路由或页面引用。

### 4.2 拉取语义

任务可以在 `prevStageArtifacts` 中引用前一阶段产物及指定版本。未指定历史版本时读取当前内容；指定 `artifactPullVersion` 时读取对应历史版本。用户还可以通过 `/api/taskInfo/dismissArtifactPull` 忽略一次产物同步提示。

## 五、工作流可选择始终跟随最新模板

`alwaysUseLatestTemplate` 存在于工作流 `extend`，创建、版本更新、列表和详情 DTO 都已透出。开启后，历史任务解析阶段和 convention 时也使用该工作流当前最新模板，而不是永远固定在任务创建时的模板版本。

这项能力的风险是可复现性下降，因此学习时要区分：

- 关闭：任务绑定历史模板，容易复现。
- 开启：统一吃最新修复，但历史任务行为可能随模板升级变化。

## 六、项目筛选从名称收敛到 DEP ID

需求流水、敏捷看板和批量任务看板使用统一选择结构：

```json
[
  {"projectId":"1105","subprojectId":"7278,7279"},
  {"projectId":"183"}
]
```

同一项内 `projectId` 与 `subprojectId` 是 AND，不同项目项之间是 OR；只选项目时省略 `subprojectId`。服务端会规范化空格和重复子项目 ID，并拒绝非 DEP 数字 ID，不能把非法选择静默降级成“查询全部”。前端的 `ProjectTreeSelector` 将项目树勾选结果转换为 `selectProjects`，不再把项目名或路径当稳定查询键。

需求元数据同时增加 `projectId` / `subprojectId` 及缺失数据回填入口。这里要把“显示名称”与“查询身份”分开：名称可以变化，过滤和关联使用 DEP ID。

## 七、拓扑在 master 中只有流式写入

### 7.1 写入路径

```text
VSS / MQ 资源、关系、页面事件
  -> Topology*Consumer
  -> TopologyExtractedEventHandler
  -> TopologyGraphWriter / Neo4jTopologyGraphWriter
  -> Neo4j
```

写入侧负责规范化 ID、事件顺序、幂等 / 冲突处理和必要的 Redis 观察数据。它不是 CodeGraph 的 `.codegraph/codegraph.db`；前者是业务微服务拓扑，后者是本地源码符号图，二者不要混淆。

### 7.2 查询路径尚未合入 master

`dingshouqin/topology-readonly-master-20260803` 开发分支曾实现查询 provider：从 Neo4j 读取完整图，校验后构建 JVM 内不可变快照和索引；刷新失败时继续服务上一份有效快照。该分支及提交仍保留，但不是 `master` 的祖先。

该开发分支的接口位于 `/api/v1/topology`：

- `/health`、`/overview`、`/search`
- `/applications/{applicationKey}` 及其 `/topology`、`/resources`
- `/application-path/query`
- `/resources/{resourceId}/context`、`/neighbors`
- `/resource-path/query`
- `/resource-subgraph/query`、`/resource-subgraph/continue`

当前 `master` 搜索不到 `TopologyController`、快照 provider 或 `/api/v1/topology` 路由，因此不能把上面这些接口写成已经发布的主干能力。主干目前只应描述为“事件增量写 Neo4j”。

### 7.3 当前前端边界

`ai-program-factory` 当前 `master` 的 `/ms-board` 路由只是加载外部治理看板的 iframe，没有内置拓扑画布和查询状态机。外部看板可能有自己的后端，不能据此反推 `ai24/master` 已提供拓扑查询 API。
