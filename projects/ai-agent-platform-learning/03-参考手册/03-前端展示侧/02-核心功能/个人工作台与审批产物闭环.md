# 个人工作台与审批产物闭环

> [!tip] 速览
> 当前首页不再只是任务创建入口，而是“我现在该处理什么”的工作台：待我审批、我参与的需求和新建任务聚合在同一页。任务详情进一步展示角色级审批状态、产物版本与 diff，工作流管理则允许选择是否始终跟随最新模板。

## 一、首页结构已经变化

`src/routes/home.tsx` 当前组合四个模块：

```text
HomeScreen
  |- AIFactoryHeader
  |- PendingApprovalsCard
  |- ParticipatingRequirementsCard
  `- CreateTaskModal
```

旧文把首页描述成 `SimpleTaskForm` 主导的创建页并不完整。`simple-task-form.tsx` 仍是任务创建核心表单，但现在通过右上角“新建任务”打开的 modal 承载；首页主体是个人工作台。

## 二、个人工作台查询

### 2.1 前端调用

```text
GET /api/workbench
  approvalStatus=PENDING|PROCESSED
  requirementStatus=RUNNING|DONE
  pageNum / pageSize
```

`usePersonalWorkbench` 使用 TanStack Query，query key 包含筛选参数，`staleTime` 为 30 秒。审批完成后不能等待长期缓存自然失效，应主动 invalidate 对应查询。

### 2.2 两类卡片

| 卡片 | Tab | 点击行为 |
|------|-----|----------|
| 待我审批 | `PENDING` / `PROCESSED` | 新窗口打开 `#/conversations/{taskId}` |
| 参与中的需求 | `RUNNING` / `DONE` | 有编排任务时打开 `#/orchestration/{orchestrationTaskId}` |

参与需求还展示当前阶段：`PRD_AUDIT`、`APP_SPLIT`、`APP_DEVELOP`。两张卡片各自维护分页状态，服务端分别返回 `approvalTotal` 和 `requirementTotal`。

## 三、审批 UI 读取角色级状态

### 3.1 状态类型

```typescript
type ApprovalRoleStatus =
  | "PENDING"
  | "APPROVED"
  | "REJECTED"
  | "NOT_REQUIRED"
  | "UNKNOWN";
```

后端对开发和测试分别返回状态与描述。`ApprovalRoleStatusBadge` 使用图标、颜色、tooltip 和 `aria-label` 呈现；未知值必须归一化为 `UNKNOWN`，不能误显示为待审批。

### 3.2 审批接口

前端调用 `POST /api/approvalItem/approve`，同一接口通过 `confirmStatus` 表达通过或拒绝：

```typescript
{
  taskId,
  id,
  confirmStatus: "APPROVED" | "REJECTED",
  rejectReason,
  selectedAppList
}
```

操作成功后，`useApproveItem` 同时失效 `approvalItems` 和 `pmReviewItems`。发生特定业务冲突时还会失效 `domainDivideContent`，重新拉取后端事实，避免 UI 继续使用陈旧审批批次。

## 四、产物展示形成版本闭环

### 4.1 三种阅读视图

`ArtifactsPanel` 对有新内容的产物提供：

- 旧契约：任务原先引用的内容
- 新契约：上游当前最新内容
- 对比：基于行的新增 / 删除 diff

用户也可以下载当前选中视图。这样“上游产物发生变化”不再只是一个通知，而是可解释、可比较的状态。

### 4.2 历史版本

`useArtifactHistory` 调用：

```text
GET /api/taskInfo/artifact/history/{artifactId}
```

`ArtifactHistoryDrawer` 按版本时间线展示内容，默认展开当前版本，并支持按版本下载。查询只在 `artifactId` 有值时启用，5 分钟内视为新鲜数据。

## 五、工作流“始终使用最新模板”

工作流表单新增 `alwaysUseLatestTemplate`：

> 开启后，历史任务也会按工作流当前最新版本解析阶段和规范模板。

前端只是采集和展示这个策略，真正的解析发生在 ai24。该开关不能被理解成普通 UI 偏好，它改变历史任务的可复现性；修改时需要同时核对创建、编辑、详情回显和后端解析逻辑。

## 六、实时通信是多协议兼容，不是一条固定 WebSocket

当前仓库同时保留 V0、V1 和 Custom Agent Provider。对 Custom Agent / V3 路径：

- 接收：`CustomAgentWebSocketProvider` 使用 GMS SDK，业务 ID 为 `ai24`，默认连接 `VITE_GMS_WS_URL`。
- 订阅：当前选中的主任务或子任务 ID 参与 GMS userId / 消息过滤。
- 发送：`use-send-message.ts` 通过 HTTP `/api/task/query` 发送，GMS 主要承担下行消息。

所以旧文里的“浏览器直连 `wss://ai24/ws/report` 并双向发送”不是当前 Custom Agent 主路径。阅读 WebSocket 文档时要先确认对话版本，再判断使用 Socket.IO、原生 WebSocket 还是 GMS。

## 七、拓扑页面的仓库边界

当前 `master` 的 `/ms-board` 路由实现是：

```text
iframe -> https://ms-board.daily.vdian.net/
```

仓库中没有上一版内置的拓扑画布、force layout 和 topology query state。ai24 的 `/api/v1/topology/*` 仍是后端能力，但当前前端 master 通过外部治理看板承载页面。后续若重新内置拓扑工作台，应把它当成一次新的前端集成，而不是默认已有功能。
