# 任务初始化流程详解（POST /task/perform）

> 本文按 `code-agent master@c7d1ed37` 核对。初始化负责准备任务环境，不执行用户后续提交的开发指令。

**触发**：AI24 创建需要实际执行的任务后调用；来源可以是允许通过的手工创建，也可以是自动流程中的节点任务  
**目的**：保存初始化参数、获取 DEP/PRD、克隆代码、准备 CLAUDE.md/OpenSpec  
**特点**：HTTP 接口同步完成知识库更新和参数登记后，启动后台线程并返回 202

> 被 AI24 入口规则拒绝的手工创建请求不会到达 code-agent；编排主任务本身也不执行，只有实际节点任务会调用 `/task/perform`。

---

## 一、入口请求

```json
{
  "taskId": "task_123",
  "depUrl": "http://dep.vdian.net/#/taskDetail?id=12345",
  "flowType": "backend",
  "templateId": "default",
  "realTemplateId": "workflow-template-id",
  "userName": "张三",
  "model": "claude-opus-4-8"
}
```

当前实际工作的主路径是 `depUrl` 模式：接口从 `depUrl` 解析 `dep_id`，再让后台初始化流程读取 DEP 数据。源码注释还提到旧的 `gitUrl` 模式，但当前 `post()` 中没有对应的完整处理分支，学习时应以 `depUrl` 模式为准。

---

## 二、HTTP 线程做什么

### 1. 同步三套知识库

```python
clone_knowledge_repo_if_absent()
pull_knowledge_repo()

clone_knowledge_service_repo_if_absent()
pull_knowledge_service_repo()

clone_app_knowledge_v2_repo_if_absent()
pull_app_knowledge_v2_repo()
```

三套仓库分别是：

| 本地目录 | 远端仓库 | 分支配置 |
|---|---|---|
| `/home/www/logs/knowledge` | `trade/knowledge.git` | `KNOWLEDGE_REPO_BRANCH`，默认 `main` |
| `/home/www/logs/knowledge-service` | `trade/knowledge-service.git` | `KNOWLEDGE_SERVICE_REPO_BRANCH`，默认 `main` |
| `/home/www/logs/app-knowledge-v2` | `flutter-shop/app-knowledge-v2.git` | `APP_KNOWLEDGE_V2_REPO_BRANCH`，默认 `main` |

需要注意：

- 分支从管理平台配置动态获取，获取失败时回退到各自的默认 `main`。
- 每次 `/task/perform` 都会按 `clone（目录不存在时）→ fetch → checkout → pull` 尝试同步。
- 知识库同步失败只记日志，不阻断任务初始化。
- `KnowledgeRepoScheduler` 虽然定义了每小时同步能力，但当前 `main.py` 只创建实例，没有调用 `start()`；从当前主分支能确认的主动同步点是 `/task/perform`。

### 2. 解析并保存初始化参数

```python
dep_id = parse_dep_id_from_url(dep_url)

meta_container.update(
    task_id=task_id,
    dep_id=dep_id,
    dep_url=dep_url,
    flow_type=flow_type,
    project_path=PathManager.ensure_task_dir_exists(task_id=task_id),
    template_id=template_id,
    real_template_id=real_template_id,
    user_name=user_name,
    model=model,
    # 还会保存 enableDocumentAutoUpload、enableTdd、isApply、
    # dependentGitUrls、caseSetId、appId、domain 等任务上下文
)
```

这里的 `MetaContainer` 不是本地 JSON 文件，也不是直接写 COS，而是通过 AI24 的 `agentTaskData` 接口读写云端任务元数据。

此时：

- `project_path` 已经是任务基础目录，不是空值。
- `git_url`、`branch`、`prd_path` 还要等 DEP 初始化后补充。

### 3. 上报机器和版本

```python
meta_container.report_task(task_id)
```

它会通过云端任务数据接口登记：

- 当前机器 IP（`container_ip`）
- 当前任务版本号（`task_version`）

版本号不一定永远是 1：首次登记为 1；远端已有版本但本机没有本地版本文件时，会使用远端版本加 1。

### 4. 清理旧会话并登记状态

```python
TaskSessionMapper.remove_task_to_session_only(task_id)

status_holder.update_stage(
    task_id=task_id,
    stage=TaskStage.RECEIVED,
    task_type=TaskType.INIT
)
```

这里更新的是 code-agent 自己的 `TaskStatusHolder`，不是向 AI24 上报初始化完成状态。

### 5. 启动后台线程并返回 202

```python
thread = threading.Thread(
    target=run_init_task_via_claude,
    args=(task_id,)
)
thread.daemon = True
thread.start()

return {
    "success": True,
    "message": "项目初始化已启动（通过ClaudeCode调用init_project MCP接口），正在后台执行",
    "mode": "dep_url_via_claude",
    "task_id": task_id,
    "dep_id": dep_id
}, 202
```

返回文案还保留了旧的“`init_project MCP`”说法，但当前真实实现已经是 Claude 调用 `init-project` Skill。

## 三、后台线程做什么

### 1. 在初始化期间开启任务环境备份

`run_init_task_via_claude()` 先为任务目录启动备份监听。初始化结束时，无论成功还是失败，都会等待最后一次同步并停止监听。

因此准确说法是：

- 初始化期间监听文件变化并备份到 COS。
- 初始化结束后本次监听会停止，不是从此永久运行。
- 后续 `/task/query` 执行时会按查询流程再次启动相应监听。

### 2. 上报进行中消息

```python
await MessageReporter.report_session_status(
    task_id=task_id,
    session_status=SessionStatus.IN_PROGRESS
)

await MessageReporter.report_system_message(
    task_id=task_id,
    report_content="任务初始化中，请稍后..."
)
```

### 3. 给 Claude 的真实初始化提示词

```text
你好，我需要初始化一个项目。
当前任务ID(task_id)是：task_123.
请调用 init-project 这个 SKILLs 来完成项目初始化
```

这个提示词很短。具体步骤不写在入口提示词里，而是集中维护在 `.claude/skills/init-project/SKILL.md` 中。

### 4. 调用 Claude SDK

```python
await service.query(
    task_id=task_id,
    keep_session=True,
    skip_check=True,
    system_prompt="",
    prompt=prompt,
    cwd=task_base_dir,
    model=task_metadata.model,
    hooks=init_hooks
)
```

这里有三个容易记错的点：

- 外层初始化查询实际是 `keep_session=True`，不是 `False`。
- 系统提示词是空字符串。
- `skip_check=True` 是旧调用链遗留的兼容传参；当前主查询路径不执行 Token 检查，因此它不再改变 compact 行为。
- 查询结束后会删除 `task_id → session_id` 映射，因此初始化会话不会直接作为后续开发会话继续使用。

`InitStatusCheckHook` 会在模型准备结束时检查 AI24 的任务状态是否已经到 100；未达到时最多提示模型重试若干次。Apply 任务、状态查询失败或 Hook 自身异常会放行，避免无限阻塞。

### 5. `init-project` Skill 执行固定脚本

Skill 要求模型运行：

```bash
/home/www/conda/envs/code-agent/bin/python \
  ~/.claude/skills/init-project/scripts/project_initialization.py task_123
```

脚本按固定顺序执行两部分：

```text
project_initialization.py
├── dep_initialization(task_id)
│   ├── 从 MetaContainer 读取 dep_id、flow_type、template_id 等
│   ├── 调 DEP 获取需求详情、仓库、分支和上级需求信息
│   ├── 获取并保存 PRD，必要时处理技术方案/设计稿信息
│   └── 更新 MetaContainer：git_url、branch、prd_path、UI 信息等
└── environment_initialization(task_id)
    ├── 克隆主仓库，frontend_logic 可继续克隆依赖仓库
    ├── Apply 模式可获取 proposal 文档
    ├── 检查/生成 CLAUDE.md，初始化 OpenSpec
    ├── 更新 MetaContainer：base_branch、最终 project_path
    └── 非 Apply 模式向 AI24 上报 status=100
```

这不是一个名为 `init_project` 的 MCP 工具调用，而是“短提示词 → Claude 选择 Skill → Skill 运行 Python 脚本”的链路。

### 6. 收尾

正常结束时会：

- 清理初始化会话映射。
- 上报会话状态 `IDLE`。
- 通知 AI24 `/init` 阶段完成。

`finally` 中还会：

- 清理 `TaskStatusHolder`。
- 保存任务环境和会话状态。
- 等待最后一次备份同步后停止初始化监听。

## 四、初始化完成后的数据

典型 Linux 目录如下：

```text
/home/www/logs/code-agent/tmp/projects/task_123/
├── prd.md
└── project-name/
    ├── CLAUDE.md
    ├── openspec/
    └── ...项目代码
```

`PathManager` 兼容旧目录；如果仓库内原来的 `tmp/projects/{task_id}` 已存在，会优先使用旧路径。macOS 本地默认在 `~/logs/code-agent/tmp/projects/{task_id}`。

云端主要有两类数据：

1. AI24 `agentTaskData` 接口保存任务元数据、机器 IP、任务版本等结构化数据。
2. COS 保存初始化过程中监听到的任务目录和会话环境备份，供跨机器恢复使用。

---

## 五、关键点总结

1. `/task/perform` 先同步三套知识库，再启动后台初始化线程。
2. 当前主分支的初始化入口是 `init-project` Skill，不是旧的 `init_project MCP`。
3. 外层 SDK 调用是 `keep_session=True`，完成后主动清理会话映射。
4. MetaContainer 通过 AI24 云端接口保存元数据，不等于直接写 COS。
5. status=100 由环境初始化脚本上报；Apply 模式会跳过。
6. 文件备份监听只覆盖本次初始化生命周期，结束时会停止。
