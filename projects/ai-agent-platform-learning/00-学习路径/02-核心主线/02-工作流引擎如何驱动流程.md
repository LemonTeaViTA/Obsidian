## 一句话总结

**工作流引擎通过数据库配置（spec_workflow → spec_stage → spec_convention）驱动任务执行，每个阶段遵循"执行→上报→审批→推进"的固定模式。**

---

## 💡 为什么需要工作流引擎？

### 问题：不同需求类型流程不同

```
大需求：
  PRD审核 → 领域划分 → 应用拆分 → TDD开发

普通任务：
  Proposal → Apply → Build

简单需求：
  只需要 Apply
```

**如果硬编码**：
```java
if (需求类型 == "大需求") {
    // 走领域划分流程
} else if (需求类型 == "普通任务") {
    // 走TDD流程
}
// 每增加一种流程就要改代码 ❌
```

---

## 🏗️ 工作流引擎的设计方案

### 核心思想：配置驱动

```
代码固定：执行机制（怎么执行）
数据库配置：流程定义（执行什么）

→ 新增流程 = 添加数据库配置
→ 修改流程 = 修改数据库记录
→ 不需要改代码 ✅
```

## 📊 三层数据结构

### 第1层：spec_workflow（工作流）

```sql
CREATE TABLE spec_workflow (
    id BIGINT PRIMARY KEY,
    workflow_no VARCHAR(50),           -- 工作流编号（如：10001）
    workflow_name VARCHAR(200),        -- 工作流名称
    workflow_template_id VARCHAR(100), -- 模板ID
    flow_type VARCHAR(50),            -- 类型（backend/frontend）
    status INT                         -- 状态
);
```

**示例数据**：
```sql
INSERT INTO spec_workflow VALUES (
    1, '10001', '后端TDD开发流程', 'template_backend_tdd', 'backend', 1
);
```

---

### 第2层：spec_stage（阶段）

```sql
CREATE TABLE spec_stage (
    id BIGINT PRIMARY KEY,
    workflow_no VARCHAR(50),      -- 关联工作流
    stage_no VARCHAR(50),         -- 阶段编号
    stage_name VARCHAR(200),      -- 阶段名称（Proposal/Apply）
    stage_order INT,              -- 执行顺序
    stage_type VARCHAR(50)        -- 阶段类型
);
```

**示例数据**：


## 🔄 执行流程

### 流程1：任务创建时选择工作流

```
用户在前端选择：
  - 工作流：后端TDD开发流程（10001）
  ↓
ai24 查询 spec_workflow
  ↓
找到 workflow_no = '10001'
  ↓
查询该工作流的所有阶段（spec_stage）
  ↓
得到阶段列表：Proposal → Apply → Build
```

**代码实现**：
```java
// TaskWorkflowQueryService.java
List<SpecStageDO> stages = specStageManager.listByWorkflowNo(workflowNo);
// 返回：[Proposal, Apply, Build]
```

---

### 流程2：执行当前阶段

```
code-agent 查询当前阶段的约定
  ↓ GET /api/task/notify/getTemplate
返回当前阶段的 Prompt
  ↓
code-agent 执行
  ↓
完成后上报产物
```

**代码实现**：
```java
// SpecStageService.java
public String getCurrentStagePrompt(String taskId) {
    // 1. 查询任务当前阶段
    TaskInfoDO task = taskInfoManager.getById(taskId);
    String currentStage = task.getCurrentStage(); // "stage_proposal"
    
    // 2. 查询该阶段的约定
    List<SpecConventionDO> conventions = 
        specConventionManager.listByStageNo(currentStage);
    
    // 3. 拼接 Prompt
    return buildPrompt(conventions);
}
```

---

### 流程3：阶段完成后推进

```
阶段完成 → 审批通过
  ↓
更新 task_info.current_stage
  ↓ 
从 "stage_proposal" → "stage_apply"
  ↓
下次执行时，读取新阶段的配置
```

**代码实现**：
```java
// TaskInfoService.java
public void advanceToNextStage(String taskId) {
    // 1. 获取当前阶段
    TaskInfoDO task = taskInfoManager.getById(taskId);
    String currentStage = task.getCurrentStage();
    
    // 2. 查询下一阶段
    SpecStageDO nextStage = specStageManager.getNextStage(
        task.getWorkflowNo(), currentStage
    );
    
    // 3. 更新任务阶段
    task.setCurrentStage(nextStage.getStageNo());
    taskInfoManager.updateById(task);
}
```

## 🎯 核心设计模式：策略模式

### 审批策略接口

```java
public interface ApprovalEventStrategy {
    /**
     * 支持的事件类型
     */
    String supportEventType();
    
    /**
     * 所有审批通过时触发
     */
    void onAllApproved(String taskId, List<ApprovalItemDO> approvedItems);
    
    /**
     * 存在拒绝时触发
     */
    void onSomeRejected(String taskId, List<ApprovalItemDO> rejectedItems);
}
```

---

### 具体策略实现

```java
// 领域划分审批策略
@Component
public class DomainDivideApprovalStrategy extends AbstractApprovalStrategy {
    
    @Override
    public String supportEventType() {
        return "DOMAIN_DIVIDE"; // 支持领域划分事件
    }
    
    @Override
    protected void onAllApprovedLegacy(String taskId, 
                                       List<ApprovalItemDO> approvedItems) {
        // 领域划分通过后：创建应用拆分任务
        for (ApprovalItemDO item : approvedItems) {
            String newTaskId = taskInfoService.createTask(
                "应用拆分-" + item.getItemOwner(),
                buildInput(taskId, item),
                ...
            );
        }
    }
    
    @Override
    public void onSomeRejected(String taskId,
                               List<ApprovalItemDO> rejectedItems) {
        // 拒绝后：调用 code-agent 重新执行
        String feedback = collectRejectReasons(rejectedItems);
        codeAgentService.query(taskId, feedback);
    }
}
```

### 策略注册和调用

```java
@Service
public class ApprovalItemServiceImpl {
    
    // 所有策略自动注入
    @Autowired
    private List<ApprovalEventStrategy> strategies;
    
    // 策略映射表
    private Map<String, ApprovalEventStrategy> strategyMap;
    
    @PostConstruct
    public void init() {
        // 构建策略映射
        strategyMap = strategies.stream().collect(
            Collectors.toMap(
                ApprovalEventStrategy::supportEventType,
                s -> s
            )
        );
    }
    
    public void approve(Long approvalItemId, String approver) {
        // 1. 更新审批状态
        ApprovalItemDO item = approvalItemManager.getById(approvalItemId);
        item.setConfirmStatus(APPROVED);
        item.setActualConfirmer(approver);
        approvalItemManager.updateById(item);
        
        // 2. 检查该任务下该事件类型的所有审批是否都通过
        if (allApproved(item.getTaskId(), item.getEventType())) {
            // 3. 查找对应策略
            ApprovalEventStrategy strategy = 
                strategyMap.get(item.getEventType());
            
            // 4. 触发策略
            if (strategy != null) {
                strategy.onAllApproved(
                    item.getTaskId(),
                    getApprovedItems(item.getTaskId(), item.getEventType())
                );
            }
        }
    }
}
```

## 🔀 编排任务判断（新增）

### 问题：老任务 vs 编排任务

```
老任务：
  - task_flow 表不存在记录
  - 审批通过后，策略直接创建下一阶段任务

编排任务：
  - task_flow.node_no 不为空
  - 审批通过后，由编排层统一驱动
  - 策略不创建任务（避免重复）
```

---

### 抽象基类处理

```java
@Slf4j
public abstract class AbstractApprovalStrategy implements ApprovalEventStrategy {
    
    @Autowired
    private TaskFlowManager taskFlowManager;
    
    @Override
    public final void onAllApproved(String taskId, 
                                     List<ApprovalItemDO> approvedItems) {
        // 1. 查询是否为编排任务
        TaskFlowDO taskFlow = taskFlowManager.getByTaskId(taskId);
        
        if (taskFlow != null && taskFlow.getNodeNo() != null) {
            // 编排任务：跳过，由编排层驱动
            log.info("编排任务，跳过审批后置处理，taskId={}", taskId);
            return;
        }
        
        // 2. 老任务：走子类实现的原逻辑
        log.info("老任务，走原审批后置处理逻辑，taskId={}", taskId);
        onAllApprovedLegacy(taskId, approvedItems);
    }
    
    /**
     * 子类实现：老任务的审批后置处理
     */
    protected abstract void onAllApprovedLegacy(
        String taskId, 
        List<ApprovalItemDO> approvedItems
    );
}
```

## 📈 完整执行示例

### 场景：后端TDD开发流程

```
工作流配置：
  workflow_no: 10001
  stages:
    1. Proposal（设计）
    2. Apply（开发）
    3. Build（构建）

执行流程：

Step 1: 创建任务
  - 选择工作流 10001
  - current_stage = "stage_proposal"
  - 下发 code-agent

Step 2: Proposal 阶段
  - code-agent 查询 Proposal 的 Prompt
  - 执行设计测试用例
  - 上报产物（test_design.md）
  - 创建审批项（PENDING）

Step 3: 审批 Proposal
  - 产品审批：通过 ✅
  - 触发 ProposalApprovalStrategy.onAllApproved()
  - 更新 current_stage = "stage_apply"

Step 4: Apply 阶段
  - code-agent 查询 Apply 的 Prompt
  - 执行 TDD 开发
  - 上报产物（代码 + 测试）
  - 创建审批项（PENDING）

Step 5: 审批 Apply
  - 技术负责人审批：通过 ✅
  - 触发 ApplyApprovalStrategy.onAllApproved()
  - 更新 current_stage = "stage_build"

Step 6: Build 阶段
  - code-agent 查询 Build 的 Prompt
  - 执行编译和测试
  - 上报产物（构建日志）
  - 任务完成
```

## 💎 设计亮点（面试可讲）

### 亮点1：配置驱动，扩展性强
```
新增流程 = 插入数据库记录
不需要改代码，上线即生效
```

### 亮点2：策略模式解耦
```
每种事件类型一个策略
新增事件 = 新增策略类
符合开闭原则
```

### 亮点3：版本化管理
```
workflow_template_id 支持版本
白名单工作流自动使用最新版
存量任务兼容老版本
```

### 亮点4：编排任务兼容
```
通过 task_flow.node_no 判断
编排任务跳过策略后置处理
避免重复创建
```

## 🔗 相关概念

### 工作流 vs 编排

```
工作流（spec_workflow）：
  - 单个任务内部的阶段流程
  - Proposal → Apply → Build
  
编排（orchestration）：
  - 需求级别的多任务串联
  - PRD审核 → 领域划分 → 应用拆分 → 多个开发任务并行
  - 涉及 requirement_flow、orchestration_node
```

## 🤔 常见问题

**Q1：阶段顺序可以动态调整吗？**
A：可以。修改 spec_stage.stage_order 即可，但要确保逻辑一致性。

**Q2：审批拒绝后如何重试？**
A：调用 /task/query 接口，传递拒绝原因，code-agent 根据反馈重新执行。

**Q3：如何添加新的工作流？**
A：
1. 插入 spec_workflow 记录
2. 插入 spec_stage 记录（定义阶段）
3. 插入 spec_convention 记录（定义 Prompt）
4. 如需自定义审批逻辑，添加新的 Strategy
