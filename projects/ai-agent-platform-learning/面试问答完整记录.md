## 1. 项目介绍

### Q1：用2分钟介绍一下这个项目

**回答**：

我们的 AI Agent 平台项目主要用于内部的代码开发，支持前端、后端、客户端等多个领域。

**核心流程**：
1. 在 DEP 系统上提交需求
2. 平台抓取需求，选择模型和测试人员创建任务
3. PRD 需求审核，确保边界和测试明确
4. 领域拆分，将需求拆分成多个领域分别开发
5. 定义领域边界和契约
6. PM 审核通过后进入实际代码开发
7. 各个阶段拉取对应的工作流和提示词
8. Agent 执行开发，包括重试、上报等
9. 多重 Hook 进行审核
10. 开发完成上报

**技术架构**：
- 前端：React + TypeScript
- 后端：Spring Boot + MyBatis + Redis + MQ
- Agent侧：Python + Flask + Claude SDK

**三个系统协作**：
- ai24 负责任务管理和工作流配置
- code-agent 负责执行任务
- 前端负责任务创建和进度展示

## 2. 工作流引擎

### Q2：工作流是怎么实现的？是硬编码还是可配置的？

**回答**：

我们的工作流是**可配置的**，存储在数据库中，通过数据库驱动实现灵活的流程定义。

**数据结构**（三层表）：
```
spec_workflow（工作流配置）
  ↓
spec_stage（阶段配置）
  ↓
spec_convention（约束规范）
```

**核心设计**：
- 配置存储在数据库
- 执行中的任务使用创建时的工作流版本
- 不能动态修改正在执行的任务
- 新增流程 = 添加数据库配置，不需要改代码

**策略模式**：
- 每种审批类型一个策略类（如 DomainDivideApprovalStrategy）
- 审批通过触发对应策略的 onAllApproved()
- 符合开闭原则，易扩展

## 3. 编排任务与并行开发

### Q3：领域拆分后如何并行开发？如何解决并发冲突？

**回答**：

我们使用 **FAN_OUT 机制**实现并行开发：

**并行流程**：
```
应用拆分审批通过
  ↓
为每个应用投递 MQ 消息
  ↓
MQ 消费者异步创建子任务
  ↓
子任务并行下发 code-agent
  ↓
工作目录隔离避免冲突
```

**冲突解决**（两个机制）：

1. **工作目录隔离**
   - 每个子任务创建独立工作目录
   - /workspace/task-1/、/workspace/task-2/
   - 各自独立克隆代码，互不干扰

2. **MQ 异步解耦**
   - 避免阻塞主流程
   - 支持失败重试
   - 单个失败不影响其他

**效果**：
- 4个应用并行开发
- 开发时间 = 最慢的那个（不是总和）
- 效率提升4倍

**最终合并**：
- CR 阶段人工处理冲突
- 权衡：开发效率 > 合并成本

## 4. 需求审核标准

### Q4：需求边界要达到什么标准才能开发？

**回答**：

我们主要看三个点：

**1. 界面状态要全面**（前端）
- 正常态、加载态、空态、错误态、无权限态
- 不能只写正常流程

**2. 待确认点要清零**
- 需求模糊的地方必须在规划阶段解决
- Claude 会标记为待确认点
- 必须解决才能进入开发

**3. 测试要能覆盖**
- 需求必须能通过测试验证
- 不能是主观标准

**不同端的差异**：

**前端**：关注用户体验，5种界面状态

**后端**：关注性能和稳定性
- 线程模型必须明确
- 内存与性能约束
- 错误处理与容错

**客户端**：关注兼容性和环境约束
- Gradle 离线构建
- Mock 数据管理
- 真机能力边界

## 5. Hook机制

### Q5：Claude 如何判断需求合格？发现问题怎么处理？

**回答**：

我们有**两层 Gate Hook 机制**：

**第一层：ProposalFilesGateHook**（文件完整性检查）
```
检查4个产物文件是否齐全：
- design.md
- test_design.md
- tasks.md
- test-manifest.json

缺文件 → block → Claude 重试（最多3次）
```

**第二层：PrdAuditGateHook**（内容审核检查）
```
Claude 审核需求，生成 audit_report.json

Hook 读取报告，三种处理：

1. PASS（通过）
   - 无 P0 问题 → 进入下一阶段

2. RETRY（重试）
   - 格式问题、一致性问题
   - Claude 自己修正（最多3次）

3. ESCALATE（退回）
   - 存在 P0 问题
   - 退回产品修订（最多5次）
```

**P0 判断标准**（写在提示词中）：
- 边界态缺失（空态、错误态）
- 待确认点未清零
- 测试设计不完整

**核心约定**：
- verdict=BLOCKED ↔ 存在 P0 问题（强绑定）
- status=UNDEFINED 的能力必须有对应 P0 issue

---

### Q6：Hook 如何记录重试次数？5次后怎么处理？

**回答**：

**状态持久化**：
- 存储在本地文件：`prd_audit_escalate_hash.json`
- 不是数据库，避免分布式同步问题
- 记录的是**文件哈希**，不是简单计数器

**判断逻辑**：
```python
if 当前 audit_report 的哈希 == 上次保存的哈希:
    # 相同内容已退回过，避免无限循环
    return PASS  # 放行，进入下一阶段
else:
    # 内容变了，允许再次审核
    save_hash(task_id, current_hash)
    return ESCALATE  # 退回产品
```

**设计优势**：
1. 避免无限循环（产品改需求 → Claude 退回 → 重复）
2. 允许真正改进（哈希变了就可以继续审核）
3. 不需要中心化计数器

**实际行为**：
- 理论上可以无限次重试
- 只要每次 audit_report 都不同
- `max_escalation=5` 是预留参数，实际通过哈希去重防止循环

### Q7：提示词要求的文件和Hook检查是否匹配？

**回答**：

我们检查过，发现了不匹配的问题：

**前端**：✅ 完全匹配
```
提示词要求：design.md, test_design.md, tasks.md, test-manifest.json
Hook 检查：design.md, test_design.md, tasks.md, test-manifest.json
```

**后端**：⚠️ 不匹配
```

```

**客户端**：⚠️ 不够明确
```

```

**修复建议**：
1. 统一各端要求（推荐）- 让所有端都生成4个文件
2. Hook 根据类型动态检查 - 前端4个，后端2个

## 7. 子Agent机制

### Q8：系统支持子Agent吗？如何设计的？

**回答**：

**支持子Agent**，有两种模式：

1. **前台 subagent**（串行持有）
   - 主 Agent 创建子 Agent
   - 等待子 Agent 完成后再继续

2. **Detached subagent**（后台执行）
   - 主 Agent 创建后台子 Agent
   - 不等待完成，异步执行

**使用规范**：
```
客户端打包流程明确规定：
"禁止创建 detached subagent，禁止后台轮询未 join 就进入下一阶段"

原因：打包流程必须确保每一步都成功完成才能进入下一步
```

**设计权衡**：

从技术上讲，Claude SDK 支持工具调用和并行执行，不一定需要平台层管理。

但平台层控制的价值在于：
1. **可观测性** - 前端能看到子任务进度
2. **成本控制** - 防止无限并行，Token 消耗失控
3. **状态管理** - 某些场景必须串行执行

**最佳实践**：
- 默认不限制，让 Claude 自由发挥
- 只在需要平台可观测性或成本控制的场景，才使用平台层的子 Agent 机制
- 根据场景选择（灵活性 vs 可控性的权衡）

**回答**：

```java

    100,   // 核心线程
    300,   // 最大线程
    队列: 500
)

理论并发：300 个任务同时处理 + 500 个排队 = 800 总容量

```

```
  - 测试覆盖率：96%
```

**成本分析**：
```
平均每任务消耗：600万 tokens

单任务成本估算：
- 按 Claude Opus 定价（$15/M input, $75/M output）
- 假设 Input:Output = 3:1
- 成本约 $170-190/任务

总成本：
239 任务 × $180 = 约 $43,000
```

**监控能力**：
```
系统有完整的统计功能：
- Token 使用统计（input/output/cache）
- 任务完成情况统计
- 代码行数统计
- 成本监控（实时/每日/总成本）
```

**优化空间**：
