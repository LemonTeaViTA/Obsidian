# code-agent 上报机制与流式推送

> 记录时间：2026-07-09
> 目标：搞清 code-agent 如何向 ai24 上报信息(任务状态/对话内容/审批项),是主动推还是被动轮询,长连接还是短连接,以及 hook 在其中的真实作用。
> 关联：[启动与任务流程-理解校对与澄清](../00-导航/启动与任务流程-理解校对与澄清.md)、ai24 侧 stage5(回调闭环)

---

## 🎯 核心结论

code-agent 向 ai24 上报信息全部是**主动推送(短连接 HTTP POST)**,ai24 从不轮询。
有**三条独立的上报链路**,各司其职,千万别混。

```
【三条上报链路】
① 机器健康心跳       → /api/agentMachine/heartbeat          (定时,机器级)
② 任务状态更新       → /api/task/notify/taskStatus          (任务推进时,任务级)
③ 任务内容/对话上报  → /api/task/report/content             (流式,实时,内容级)
              └─ 特殊:创建审批项(某阶段完成后)
```

---

## 一、三条上报链路详解(各自触发时机、传什么)

### ① 机器健康心跳:告诉 ai24 "我这台机器在线且当前负载"

**文件**：machine_status_manager.py
**触发**：定时(每隔 N 秒,后台线程)
**目标 API**：`POST /api/agentMachine/heartbeat`

```python
# machine_status_manager.py:169
def _heartbeat_worker(self):
    while self._running:
        current_tasks = self.get_current_tasks()  # 当前任务列表
        self.report_machine_status(tasks=current_tasks)
        time.sleep(HEARTBEAT_INTERVAL)   # 间隔sleep
```

**上报内容**:
```json
{
  "ip": "本机IP",
  "hostname": "主机名",
  "tasks": ["t-001", "t-002"],  // 当前在跑的任务ID列表
  "claude_process_count": 3
}
```

**用途**：给 ai24 的**任务路由/负载均衡**用——ai24 发新任务前,要知道哪台机器在线、哪台机器负载低。

**配套**：还有个 `report_task_machine(task_id)`(line:136)上报"任务 t-xxx 在我这台机器",让 ai24 下次 query 能直连这台。

---

### ② 任务状态更新:告诉 ai24 "任务现在处于哪个阶段"

**文件**：external_api_proxy.py
**触发**：任务推进到新阶段时(初始化完成/开始开发/CR/完成...)
**目标 API**：`POST /api/task/notify/taskStatus`

```python
# external_api_proxy.py:239
url = f"{base_url}/api/task/notify/taskStatus"
payload = {
    "taskId": task_id,
    "status": status,       # 状态码:0/100/215/220/310/500/999...
    "consumeTime": ...,
    "reportContent": report_content  # 可选,状态变化时的说明文本
}
```

**状态码枚举(ai24 侧 TaskStatus.java)**:
```
0    INIT               初始化中(刚建任务)
100  INITIALIZED        初始化完成(code-agent拉完代码建好项目)
110  REQUIREMENT_ANALYSIS  需求分析
210  TECHNICAL_ANALYSIS    技术方案
215  DOMAIN_DIVIDE         领域划分  ← 你关心的
220  APP_SPLIT             应用拆分  ← 你关心的
310  CODING                开发中
320  CODE_REVIEW           CR中
410  UNIT_TEST             单测
420  INTEGRATION_TEST      集成测试
500  COMPLETED             完成(终态)
999  TERMINATED            已终止(终态:失败/中断)
```

**触发时机示例**:
- perform 初始化完 → 上报 status=100
- 进入领域拆分 → 上报 status=215
- 应用拆分完成 → 上报 status=220
- 任务全部完成 → 上报 status=500

**用途**：更新 ai24 的 `task_info.status` 字段 + WebSocket 推给前端更新进度条。

---

### ③ 任务内容/对话上报:告诉 ai24 "Claude 说了啥/做了啥"(流式推送)

**文件**：external_api_proxy.py、claude_agent_sdk_wrapper.py
**触发**：Claude 每次有输出、执行日志、产物报告时,**实时**
**目标 API**：`POST /api/task/report/content`

```python
# external_api_proxy.py:293
url = f"{base_url}/api/task/report/content"
payload = {
    "taskId": task_id,
    "recordId": record_id,     # 这条对话记录的ID
    "content": content,        # Claude 的回复内容
    "reportType": report_type, # 报告类型(对话/日志/文档)
    "reportContent": report_content  # 格式化的展示内容(markdown)
}
```

**关键机制:流式 → 短连接 POST 流**

Claude 输出是**流式的**(一个字一个字蹦),code-agent 处理方式(claude_agent_sdk_wrapper.py:2135):

```python
# StreamHandler:Claude 每输出一段就立刻 POST
def on_text_delta(text_delta):
    content += text_delta
    ManagementApiTool.notify_task(..., report_content=content)  # 立刻POST给ai24
```

**不是长连接,是"准实时的短连接流"**:
- Claude 说一句 → code-agent POST 一次 → ai24 收到 → WebSocket 推前端 → 前端看到 AI 在打字
- 每次 POST 完就断开,下次有新内容再 POST

**没有轮询**:ai24 完全被动等 code-agent POST,从不主动去 code-agent 拉。

**大量示例**(main.py 里到处都是):
```python
report_content=f"✅ 初始化完成\n\n项目已准备就绪"     # 初始化完成时POST
report_content=f"⏳ 正在分析需求..."               # 开始分析时POST
report_content=f"📋 领域拆分报告\n\n{domain_list}" # 拆分完成时POST
```

### 特殊情况:创建审批项(属于第③条链路的变种)

**领域拆分/应用拆分完成后,code-agent 还要创建审批项**——这本质也是"上报内容",只是内容类型是"审批项"而不是"对话"。

**推测 API**(我没找到确切调用点,但从 ai24 侧 ApprovalItemDO 反推):
```
POST /api/approval/item  (或类似路径)
payload = {
    "taskId": task_id,
    "eventType": "DOMAIN_DIVIDE" / "APP_SPLIT",
    "confirmItem": "订单域",
    "confirmContent": "{领域拆分详细报告JSON}",  ← 产物!
    "itemOwner": "领域名",
    "confirmer": "zhangsan,lisi",  # 审批人列表
}
```

**关键**:最近一次提交 `14adad0ed 创建审批项必须携带产物` 就是强化这个——审批项必须带 `confirmContent`(产物报告),不能空建。

## 二、三条链路对比表(千万别混)

| | ① 机器健康心跳 | ② 任务状态更新 | ③ 任务内容上报 |
|---|---|---|---|
| **上报啥** | 机器在线+负载(IP/tasks/进程数) | 任务处于哪个阶段(status码) | Claude对话/日志/产物 |
| **触发** | 定时(每N秒,后台线程) | 任务推进到新阶段时 | Claude每次有输出,实时 |
| **目标API** | /agentMachine/heartbeat | /task/notify/taskStatus | /task/report/content |
| **级别** | 机器级 | 任务级 | 内容级(最细粒度) |
| **用途** | 路由/负载均衡 | 更新task_info.status + 进度条 | 填task_record表 + 前端实时显示 |
| **频率** | 低频(N秒1次) | 中频(十几次/任务) | 高频(流式,可能几百次) |

**常见误解纠正**:
- ❌ 心跳上报任务进度 → ✅ 心跳只报机器健康,任务进度是第②条
- ❌ ai24 轮询 code-agent → ✅ 全是 code-agent 主动 POST,ai24 被动等
- ❌ 长连接推送 → ✅ 短连接,每次POST完就断,下次再POST

## 三、⚠️ hook 的真实作用(不是触发上报!)

**关键认知纠正**:hook **不负责上报**,上报是 code-agent **主流程代码主动调 API**。

### hook 是什么?

hook 是 **Claude SDK 层的拦截器**,拦截 Claude 的输出/工具调用,做校验/转换/触发额外动作:

```python
# hook 的典型职责(hooks/*.py):
- 拦截 Claude 输出 → 校验产物文件是否齐全(proposal_files_gate)
- 拦截工具调用 → 注入 git commit author(git_commit_author_hook)
- 判断是否停止任务 → 检查任务是否完成(task_completion_gate)
```

### 上报是主流程干的,不是 hook

```python
# 主流程(main.py / fetch_task_metadata等)
async def some_stage_complete():
    # ... code-agent 干完领域拆分
    
    # 主动调 API 上报状态
    ManagementApiTool.notify_task(task_id, status=215)
    
    # 主动调 API 上报内容
    ManagementApiTool.notify_task(task_id, report_content=f"领域拆分完成\n\n{report}")
    
    # 主动调 API 创建审批项(推测,我没找到确切位置但机制如此)
    create_approval_item(task_id, event_type="DOMAIN_DIVIDE", content=...)
```

**hook 只是拦截器,主流程才是调度者。** 把 hook 想成"高速路上的检查站"——它能拦车检查、决定放行还是扣下,但"车往哪开、开到哪报告位置"是司机(主流程)决定的,不是检查站发起的。

### hook vs 上报的层次关系

```
Claude SDK 层    ← hook 在这层拦截
    ↓
code-agent 应用层 ← 主流程在这层调 API 上报
    ↓
HTTP API         ← 上报目标(ai24)
```

**层次错位**:hook 是 SDK 层,上报是应用层,两者不在一个抽象层次。hook 可以**影响**流程(如拦住不让继续),间接影响"什么时候上报",但不是"hook 触发上报"。

## 四、流式推送的完整链路(实时看到 AI 打字的原理)

```
Claude API(流式输出)
    ↓ 一段一段返回
code-agent StreamHandler
    ↓ 每收到一段立刻 POST
ai24 /api/task/report/content
    ↓ 收到后写 task_record + 推 WebSocket
前端 WebSocket 监听
    ↓ 收到消息更新 UI
用户浏览器界面 ← 看到 AI 实时打字
```

**关键点**:
1. **Claude → code-agent**:流式(SSE/streaming)
2. **code-agent → ai24**:短连接 HTTP POST(准实时转换)
3. **ai24 → 前端**:WebSocket 长连接推送

整条链路是**流式 → 短连接流 → 长连接推**的组合,前端才能实时看到。

## 五、实际例子:领域拆分完整上报流程

```
① code-agent 执行领域拆分任务
   ↓ Claude 分析、调 MCP 工具、生成报告(过程中不断调第③条链路上报对话)
   
② 拆分完成,主流程代码:
   ManagementApiTool.notify_task(status=215, report_content="✅ 领域拆分完成")  ← 第②+③条
   
③ 创建审批项(推测代码):
   POST /api/approval/item
   {
     eventType: "DOMAIN_DIVIDE",
     confirmContent: "{订单域: [...], 用户域: [...]}"  ← 产物报告!
     confirmer: "zhangsan,lisi"
   }
   
④ ai24 收到审批项 → 写 approval_item 表(status=PENDING) → 企微通知审批人
   
⑤ 审批人在 ai24 前端审批 → 全过则创建应用拆分任务 / 驳回则 queryTask 打回
```

**关键**:第③步创建审批项,不是 hook 触发,是主流程"拆分完成后"主动调 API。
