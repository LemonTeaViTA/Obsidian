# 知识库同步机制详解

> code-agent 如何管理和同步三套 GitLab 知识库仓库，并通过动态分支配置保证不同环境使用正确的分支。

---

## 一、为什么需要知识库同步？

Claude 在执行任务时，需要读取知识库中的背景文档、规范说明和示例数据。这些内容存在 GitLab 仓库里，必须先同步到本地，Claude 才能通过文件工具读取它们。

---

## 二、三套知识库

当前维护三个独立的仓库，分别存储不同类型的知识内容：

| 仓库 | 本地目录 | 用途 |
|------|---------|------|
| `knowledge` | `/home/www/logs/knowledge` | 主知识库（通用背景文档/规范） |
| `knowledge-service` | `/home/www/logs/knowledge-service` | 服务知识库（各子服务相关知识） |
| `app-knowledge-v2` | `/home/www/logs/app-knowledge-v2` | 前端应用知识库（Flutter/App 相关） |

三套仓库：
- URL / 本地目录 / 分支配置各自独立
- 同步逻辑相同，但分支名从配置中心分别读取

---

## 三、同步逻辑

核心文件：`knowledge_repo_scheduler.py`

### 3.1 单次同步流程

```
检查本地目录是否存在
    ↓
不存在 → git clone（先 clone 再 checkout 目标分支）
已存在 → git fetch
         ↓
     git ls-remote 检查远程分支是否存在
         ├─ 分支存在 → git checkout <分支> → git pull
         └─ 分支不存在 → 跳过，打日志（避免 checkout 报错中断流程）
```

### 3.2 动态分支配置

分支名不是硬编码，而是从 Vitamin 配置中心动态拉取：

```python
def _get_branch_from_config(self, config_key: str, default: str) -> str:
    """
    从 Vitamin 配置中心获取分支名。
    接口：GET http://vitamin.{env}.vdian.net/node/query
    参数：groupId=ai24, serviceId=code-agent, nodeKey=<config_key>
    失败时回退到 default（通常是 'main'）
    """
```

配置 key 对应关系：

| 仓库 | 配置 Key | 默认分支 |
|------|---------|---------|
| knowledge | `KNOWLEDGE_REPO_BRANCH` | `main` |
| knowledge-service | `KNOWLEDGE_SERVICE_REPO_BRANCH` | `main` |
| app-knowledge-v2 | `APP_KNOWLEDGE_V2_REPO_BRANCH` | `main` |

好处：不同部署环境（daily/pre/prod）可以通过配置中心切换到不同分支，无需改代码。

## 四、触发时机

### 4.1 当前真正生效的方式：任务触发

```
触发路径1：每次任务提交（/task/perform）
    ↓
main.py TaskPerformResource.post()
    ↓
同步 knowledge 仓库
同步 knowledge-service 仓库
同步 app-knowledge-v2 仓库（三个都同步）
    ↓
继续执行任务初始化流程
```

当前主分支可以确认的主动同步点是 `/task/perform`。每次收到任务时，Code Agent 都会依次尝试同步三套知识库；同步过程出现异常会记录日志，不会阻断后续任务初始化。

### 4.2 已实现但当前没有启动的方式：定时调度器

`KnowledgeRepoScheduler` 保留了每 3600 秒执行一次的定时同步能力，而且它的 `_run_pull()` 同样会同步三套仓库：

```
KnowledgeRepoScheduler._run_pull()
    ├── pull knowledge
    ├── pull knowledge-service
    └── pull app-knowledge-v2
```

但当前 `main.py` 只创建了 `KnowledgeRepoScheduler` 实例，没有调用它的 `start()`。因此，定时同步代码目前不会运行，不能把它当作已经生效的第二条同步路径。

| 触发方式 | 同步仓库 | 当前状态 |
|---------|---------|---------|
| `/task/perform` | knowledge + knowledge-service + app-knowledge-v2 | 已生效，每次任务触发 |
| `KnowledgeRepoScheduler` | knowledge + knowledge-service + app-knowledge-v2 | 代码已实现，但未启动 |

## 五、与服务启动流程的关系

当前启动流程只启动了磁盘清理调度器，没有启动知识库调度器：

```python
# main.py 当前实际代码
_disk_cleanup_scheduler.start()

# 知识库同步已改为在 TaskPerformResource 中按需执行
# _knowledge_repo_scheduler.start() 没有被调用
```

如果以后重新调用 `_knowledge_repo_scheduler.start()`，调度器会先检查三套仓库是否需要 clone，然后设置定时器；到达同步时间后，后台线程会 pull 三套仓库并安排下一次执行。

## 六、目录结构和知识组织方式

### 6.1 执行机器上的三套仓库

```
/home/www/logs/
├── knowledge/         ← 主知识库（本地 clone）
│   ├── ...
├── knowledge-service/ ← 服务知识库（本地 clone）
│   └── ...
└── app-knowledge-v2/  ← 前端应用知识库（本地 clone）
    └── ...
```

这三个目录是 Claude 在执行任务时可以读取知识内容的来源。

### 6.2 `knowledge` 主知识库内部结构

2026-07-20 更新后，`knowledge` 不再只有 Markdown 文档，还增加了 Backstage Catalog 和 TechDocs：

```
knowledge/
├── shared/                  ← 领域路由索引、通用规则和提示词
├── prd-review/              ← PRD 审核规则
├── domains/                 ← 领域和应用级 Markdown 业务知识
├── catalog-info.yaml        ← Backstage Catalog 总入口
└── catalog/
    ├── domains.yaml         ← Domain（业务领域）
    ├── systems.yaml         ← System（领域下的系统）
    ├── components/*.yaml    ← Component 和 API
    ├── resources.yaml       ← MQ、数据库等 Resource
    └── domains-techdocs/    ← 60 个领域的 TechDocs
```

当前 Catalog 组织关系是：

```
Domain → System → Component → API / Resource
```

截至 2026-07-20，Catalog 中包含 60 个 Domain、60 个 System、525 个 Component、616 个 API 和 1669 个 Resource，并为 60 个领域准备了 TechDocs。

### 6.3 Catalog、TechDocs 和 Agent 查知识的区别

| 内容 | 主要作用 | Agent 当前怎么使用 |
|------|---------|-------------------|
| `shared/`、`prd-review/`、`domains/` | 存放通用规则、审核规则和领域知识 | 可以直接搜索和读取 |
| `catalog/*.yaml` | 给 Backstage 描述领域、系统、应用、API 和资源之间的关系 | 没有证据表明它是 Agent 的主要检索入口 |
| `domains-techdocs/` | 在 Backstage 页面展示领域文档 | 主要用于展示 |

这里要特别区分“同步”和“检索”：Code Agent 的同步逻辑只负责把 Git 仓库更新到本地。当前没有看到向量数据库、Embedding 或 RAG 召回流程；Agent 仍然根据提示词和任务上下文，自行使用文件搜索、目录索引和文件读取工具寻找知识。Catalog 是结构化治理目录，不等于 RAG 索引。

## 七、关键点总结

1. **三套仓库**：`knowledge`、`knowledge-service`、`app-knowledge-v2`，目录/URL/分支各自独立
2. **动态分支**：从 Vitamin 配置中心拉取，失败回退 `main`，多环境友好
3. **当前按需同步**：真正生效的入口是 `/task/perform`，每次任务同步三套仓库
4. **定时能力未启用**：调度器代码可以同步三套仓库，但 `main.py` 当前没有调用 `start()`
5. **checkout 前检查分支存在性**：避免分支不存在时报错中断
6. **不是 RAG**：仓库同步后由 Agent 使用文件工具查找内容，Catalog 和 TechDocs 主要服务于结构化治理和页面展示
