# 知识库同步流程改进记录

> 记录学习 Code Agent 知识库同步流程时发现的风险和可改进点。本文只记录现状与建议，不代表已经发生线上故障，也不代表改进已经实现。

## 一、当前实现

收到 `/task/perform` 请求后，Code Agent 会在项目初始化之前依次尝试同步三套知识库：

1. `knowledge`
2. `knowledge-service`
3. `app-knowledge-v2`

同步过程放在一个 `try/except` 中。如果出现异常，Code Agent 会记录 warning 日志，然后继续项目初始化，不会因为知识库同步失败而直接终止任务。

当前还存在以下事实：

- 没有看到同步失败后的自动重试机制。
- `KnowledgeRepoScheduler` 虽然实现了每小时同步能力，但 `main.py` 当前没有调用 `start()`，所以定时同步没有运行。
- 没有在任务开始前明确检查本地知识库是否存在、是否完整、是否过旧。
- 没有把三套仓库各自的同步结果作为明确状态传给后续 Agent。

## 二、存在的风险

### 2.1 本地有旧知识库

如果本地仓库已经存在，但本次 `pull` 失败，Agent 通常还可以读取旧内容。任务能够继续，但可能根据过期知识做出判断。

### 2.2 本地完全没有知识库

如果执行机器第一次运行，`clone` 又失败了，本地就没有可用知识。当前任务仍可能继续初始化，但 Agent 会缺少业务背景、审核规则或应用资料。

### 2.3 一套仓库异常可能影响后续同步

三套仓库的调用位于同一个外层 `try` 中。如果某个同步函数抛出未在函数内部处理的异常，程序会直接进入外层 `except`，后面的仓库可能没有机会继续同步。

### 2.4 后续流程不知道知识是否可用

当前主要通过日志记录同步结果。后续 Agent 不一定知道自己读到的是最新知识、旧知识，还是当前根本没有知识库，因此也无法在最终结论中主动提示这项风险。

## 三、为什么当前仍然选择继续任务

当前策略更偏向“任务可用性优先”：

- GitLab 或网络临时异常不应该阻断所有开发任务。
- 如果本地已有仓库，旧版本知识仍可能比完全没有知识更有价值。
- 有些任务主要依赖业务代码，不一定强依赖知识库。

这个选择可以理解，但还缺少对“旧知识”和“无知识”两种情况的区分。

## 四、建议的改进流程

```text
开始同步某套知识库
        ↓
第一次 clone / pull
        ↓
      是否成功？
      ├── 是 → 记录分支、commit、同步时间
      └── 否 → 间隔后重试 2～3 次
                    ↓
                仍然失败？
                ├── 本地有有效旧仓库
                │      → 使用旧版本
                │      → 标记“知识可能过期”
                └── 本地没有有效仓库
                       → 标记“知识不可用”
                       → 根据任务类型决定继续或中止
```

建议按优先级处理：

1. **增加重试**：同步失败后重试 2～3 次，并设置短暂的递增等待时间。
2. **分别隔离三套仓库**：每套仓库使用独立的异常处理，避免一套异常影响另外两套。
3. **检查本地可用性**：区分“同步失败但有旧版本”和“本地完全没有知识库”。
4. **记录明确状态**：至少记录仓库名、目标分支、当前 commit、同步时间和同步结果。
5. **把状态交给 Agent**：让后续 Agent 知道知识是最新、过期还是不可用，并在必要时提示用户。
6. **按任务类型决定是否继续**：普通代码任务可以降级执行；强依赖业务知识或审核规则的任务应考虑中止或请求人工处理。
7. **评估启用定时同步**：定时同步可以提前刷新本地缓存，但不能替代任务触发时的重试和可用性检查。

## 五、建议的最低验收标准

- GitLab 临时失败时，系统会自动重试，而不是第一次失败就放弃。
- 一套仓库同步失败时，另外两套仍会继续同步。
- 本地没有知识库时，任务状态或日志中能明确看到“知识不可用”。
- 使用旧知识继续任务时，能够记录实际使用的分支和 commit。
- 强依赖知识库的任务不会在完全无知识的情况下静默继续。
- 后续排查时可以回答：当时同步了哪套仓库、使用哪个版本、失败在哪里、Agent 是否知道这次失败。

## 六、当前结论

这不是“同步一定会失败”的代码问题，而是同步失败后的保障不够完整。当前实现保证了 GitLab 异常不会轻易阻断任务，但还需要补上重试、状态检查、降级标记和任务级处理策略，才能同时兼顾任务可用性与知识可靠性。
