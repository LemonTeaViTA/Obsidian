## 一、启动流程 10 步（main.py:3799 起，真实顺序，完整版）

```
code-agent 服务启动
启动入口: main.py __main__
    ↓
0. 解析命令行参数、加载环境配置
   setup_runtime_environment()
    ↓

   signal.signal(signal.SIGTERM, handle_shutdown_signal)
   signal.signal(signal.SIGINT, handle_shutdown_signal)
   作用: 优雅关闭(Ctrl+C 或 kill 时清理资源)
    ↓

   作用: 配置对象存储,上传会话文件/PRD文档
    ↓
3. 初始化 Langfuse
   init_langfuse()
   作用: 大模型调用追踪/可观测平台
    ↓
4. 恢复 .claude 目录
   - 恢复 .claude 目录和 .claude.json
   - 同步 skills/agents/settings.json 到用户目录
   作用: 把 Claude SDK 配置文件复制到位
    ↓
5. 创建 ClaudeAgentSDKService 单例
   create_claude_service(enable_path_security=True)
   - 装配 MCP 服务器(AI24/MemMachine/Figma/MasterGo...)
   - 注册系统强制 Hook(path_security/git_commit_author)
    ↓
6. 创建 MetaContainer 单例  ← "数据层初始化"
   get_meta_container()
   作用: 任务元数据管理器(云端存储模式)
    ↓

   TaskRecoveryManager.recover_interrupted_tasks()
   作用: 检查中断任务,自动恢复
    ↓
8. 启动机器状态心跳服务  ← 重要!三条上报链路之一
   machine_status_manager.start_heartbeat()
   作用: 定时上报 ip/tasks 给 ai24,给路由/负载均衡用
    ↓
9. 启动磁盘清理调度器
   _disk_cleanup_scheduler.start()
   作用: 定时清理超 30 天的项目目录
    ↓

   app.run(host='0.0.0.0', port=8080)

   - /task/interrupt → 中断任务
   - /status.ok → 健康检查
```

**关键点**:
- 第5步:ClaudeAgentSDKService 是核心,装配 MCP + 注册系统 Hook
- 第6步:MetaContainer 就是"数据层初始化"
- 第8步:心跳服务最容易被忽略,但它是三条上报链路之一,没它 ai24 不知道这台机器在线

## 二、三个启动疑问的答案

### 疑问1：「数据层初始化」是啥？—— get_meta_container()

初始化 **MetaContainer(任务元信息容器)**。meta_container.py:332 注释：

```
"所有操作直接读写云端API，不使用本地文件和内存缓存"
"MetaContainer 初始化完成（云端存储模式）"
```

- 「数据层」= 任务元数据(git地址/模型/模板/TDD开关等)的读写层，**云端存储模式**。
- 初始化它 = 把「元数据读写通道」准备好。详见 [../02-数据层/MetaContainer深度解析]。

### 疑问2：Flask API 是为了和 ai24 通信吗？—— 是 ✅

`app.run(0.0.0.0:8080)` 启动的 HTTP 服务器，专门接 ai24 打来的请求：
`/task/perform`、`/task/query`、`/task/interrupt` 等。它是 code-agent 的「耳朵」。

### 疑问3：心跳服务干啥？上报什么？—— 机器健康+负载，不是任务进度 ⚠️

machine_status_manager.py，上报到 `api/agentMachine/heartbeat`，内容：

```
ip / hostname / tasks(当前任务数) / claude进程数
```

**心跳 = "这台机器还活着 + 现在多忙"，不是任务进度。**

**为什么要心跳？** 给 ai24 的「任务路由/负载均衡」用！ai24 发任务前要 `isMachineOnline(ip)`、
挑负载低的机器——全靠这个心跳知道哪台在线、哪台忙。

### ⚠️ 三条上报链路千万别混

```
心跳    code-agent →(每隔N秒)→ ai24  "我在线,当前3个任务"        → 路由/负载均衡
任务映射 code-agent → ai24  "任务t-xxx在我这台"(task/{id}/machine) → query直连用
任务进度 code-agent → ai24  "t-xxx状态到100"(notify/taskStatus)   → 更新task_info表(另一条!)
```

- 心跳 = 机器健康
- 映射 = 任务在哪台机器
- 进度 = 任务状态（这条才是"上传任务信息"）

## 三、任务处理流程疑问

### 疑问4：「元数据保存到 ai24 和云服务就是表格对吧」—— 一半对 ⚠️

- **存到 ai24 那份**：✅ 是数据库表（task_info / task_record）。
- **存到云服务那份**：❌ **不是表，是对象存储 OSS/COS(文件)**。task_data_api.py：
  ```
  PRD_OSS_URL      # PRD文档的OSS存储URL
  SESSION_OSS_URL  # ClaudeCode会话文件的OSS存储URL
  ```
  云服务存的是**文件**：PRD 文档、会话记录文件。

**为什么分两处？** 结构化、要查询的(状态/创建人)进**数据库表**；大块文件(PRD/会话)进**对象存储**。
任务换机器时能从 OSS 拉回会话文件恢复。详见 [../02-数据层/云存储系统详解]。

> 一句话：**ai24 存"账本"(表)，云服务存"文件"(对象存储)。**

## 四、⭐ hook 两个来源 —— 元数据hook vs ai24下发hook

这是最容易混的点。code-agent 的 hook 有**两个来源、两种生效范围**：

### 来源A：元数据 hook（perform 初始化时定，长期生效）

perform 时 ai24 下发**开关**，存进 MetaContainer（main.py:303）：

```python
enable_tdd = data.get('enableTdd', False)   # perform时读,存进元数据
```

特点：初始化时决定，存进元数据，**整个任务生命周期都可能生效**（如 TDD hook）。

### 来源B：ai24 下发 hook（query 时定，仅本次生效）

query 时 ai24 在请求 body 带 `hooks` 列表（main.py:457）：

```python
raw_hooks = data.get('hooks')                  # 如 ["proposal_files_gate"]
resolved_hooks = hook_registry.resolve(...)     # 白名单校验后装配
```

hook_registry.py 注释：
```
"仅本次生效：每次 query 都会重建 ClaudeAgentOptions 并重新装配 hooks"
"白名单优先：AI24 只能下发本表已登记的 hook 名，未登记的静默跳过并告警"
```

### 两者区别一表看清

| | 来源A：元数据 hook | 来源B：ai24下发 hook |
|---|---|---|
| 何时决定 | perform 初始化时 | 每次 query 时 |
| 存哪 | MetaContainer(持久) | 请求 body 的 hooks 字段(临时) |
| 生效范围 | 任务生命周期(跨多轮) | **仅本次 query** |
| 例子 | enableTdd、enableDocumentAutoUpload | proposal_files_gate、task_completion_gate、prd_audit_gate、app_split_gate |
| 校验 | 开关布尔值 | 白名单(hook_registry 已登记的才认) |

### 谁选 ai24 下发的 hook？—— Java 侧 resolveQueryHooks

在 **ai24(Java)** 的 `TaskCreateOrchestrator.resolveQueryHooks(command, workflowNo)`，
按「命令 + 工作流」决定这次下发哪些：

```
/openspec:proposal + TDD工作流  → proposal_files_gate
/openspec:apply(所有工作流)     → task_completion_gate
PRD审核工作流                   → prd_audit_gate
应用拆分工作流                   → app_split_gate
```

完整链路：**ai24 按"命令+工作流"算出 hook 名 → 放进 query 请求 → code-agent 白名单校验后装配进这一次会话。**

### 为什么两种设计？

- **元数据 hook** = 任务的「固有属性」(它就是个 TDD 任务)，一次定终身 → 放元数据。
- **ai24下发 hook** = 任务的「阶段性需求」(这次是 proposal 阶段要校验产物)，每阶段不同 → 每次 query 临时下发，用完即弃。

> 一个是「体质」，一个是「这次吃什么药」。详见 [../05-扩展机制/Hook系统详解]。
