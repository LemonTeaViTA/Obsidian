## 🔥 难点1：多 Agent 并发执行时的资源冲突

### 问题描述

```
场景：
  应用拆分后创建4个子任务并行开发
  4个 code-agent 同时执行
  
冲突点：
  1. Git 冲突：多个任务修改同一个共享文件
  2. 端口冲突：多个任务启动测试服务占用同一端口
  3. 数据库冲突：多个任务使用同一个测试数据库
```

### 解决方案

**方案1：工作目录隔离**
```python
# code-agent 为每个任务创建独立工作目录
def task_perform(task_id):
    workspace = PathManager.ensure_task_dir_exists(task_id)
    # /workspace/task-1/order-system/
    # /workspace/task-2/payment-system/
    
    # 独立克隆代码
    git.clone(repo_url, workspace)
    
    # 在独立目录执行
    execute_in_workspace(task_id, workspace)
```

**方案2：动态资源分配**
```python
# 动态端口分配
def allocate_port(task_id):
    base_port = 8000
    task_hash = hash(task_id) % 1000
    return base_port + task_hash  # 8000-9000

# 动态数据库
def allocate_database(task_id):
    return f"test_db_{task_id}"
```

**方案3：CR 阶段合并冲突**
```
开发阶段：各自独立开发，不管冲突
CR 阶段：人工检查冲突，合并代码
```

### 效果
- ✅ 避免了 Git 冲突
- ✅ 避免了资源竞争
- ✅ 开发效率提升4倍

### 可改进
- 添加资源池管理（端口池、数据库池）
- 自动检测冲突并提前告警

## 🔥 难点2：审批拒绝后的重试机制

### 问题描述

```
场景：
  领域划分审批被拒绝
  - 原因："领域边界不清晰，订单创建和查询应该分离"
  
问题：
  - 如何让 AI 根据反馈重新分析？
  - 如何防止无限重试？
  - 如何记录重试历史？
```

### 解决方案

**方案1：/task/query 反馈机制**
```java
// DomainDivideApprovalStrategy.onSomeRejected()
public void onSomeRejected(String taskId, List<ApprovalItemDO> rejectedItems) {
    // 1. 收集拒绝原因
    StringBuilder feedback = new StringBuilder();
    feedback.append("审批被拒绝，需要重新分析。\n\n");
    
    for (ApprovalItemDO item : rejectedItems) {
        feedback.append(String.format(
            "【%s】被拒绝\n拒绝原因：%s\n\n",
            item.getConfirmItem(),
            item.getRejectReason()
        ));
    }
    
    // 2. 调用 code-agent
    codeAgentService.query(taskId, feedback.toString());
}
```

**方案2：重试次数限制**
```java
// 检查重试次数
TaskInfoDO task = taskInfoManager.getById(taskId);
Integer retryCount = task.getRetryCount() != null ? task.getRetryCount() : 0;

final int MAX_RETRY = 3;
if (retryCount >= MAX_RETRY) {
    // 标记失败，人工介入
    taskInfoManager.updateStatus(taskId, TaskStatus.FAILED);
    notifyHumanIntervention(taskId);
    return;
}

// 增加重试次数
taskInfoManager.incrementRetryCount(taskId);
```

**方案3：保留历史审批项**
```sql
-- 旧的审批项（已拒绝，不删除）
id    | confirm_item | confirm_status | gmt_create
10001 | 订单域       | REJECTED       | 2026-07-22 10:30

-- 新的审批项（重新上报）
10002 | 订单写入域   | PENDING        | 2026-07-22 11:00
10003 | 订单查询域   | PENDING        | 2026-07-22 11:00
```

### 效果
- ✅ AI 能根据反馈调整
- ✅ 避免无限循环
- ✅ 历史记录可追溯

### 可改进
- 添加反馈质量评分（判断反馈是否清晰）
- 智能决策重试策略（简单问题重试，复杂问题人工）

## 🔥 难点3：测试文件锁定后发现问题

### 问题描述

```
场景：
  TDD 开发中，测试已经写完并锁定
  后来发现测试逻辑有问题
  
问题：
  - TddTestLockHook 已锁定，无法修改
  - 强行绕过锁会破坏 TDD 流程
  - 只能任务失败重来？
```

### 解决方案

**当前方案：依赖 CR 发现**
```
流程：
  1. TDD 开发完成
  2. CR 阶段发现测试问题
  3. 开发者在代码仓库直接修改
  4. 重新运行测试
```

**缺点**：
- ❌ 测试问题延后到 CR 才发现
- ❌ 如果 AI 继续基于错误测试开发，返工成本高

**改进方案1：人工解锁接口**
```python
# code-agent 提供��锁接口
@app.post("/task/unlock_test")
def unlock_test(request: UnlockTestRequest):
    task_id = request.task_id
    test_file = request.test_file
    reason = request.reason
    approver = request.approver
    
    # 1. 记录解锁操作
    log_unlock_operation(task_id, test_file, reason, approver)
    
    # 2. 修改 manifest（回退到 PENDING）
    manifest = load_manifest(task_id)
    for case in manifest["cases"]:
        if case["test_file"] == test_file:
            case["state"] = "PENDING"
            case["unlock_reason"] = reason
    
    save_manifest(task_id, manifest)
    
    # 3. 通知 Claude 重新编写
    send_message_to_claude(task_id, f"测试文件 {test_file} 已解锁，请重新编写")
```

**改进方案2：测试审查阶段**
```
工作流改进：
  Proposal（设计测试） 
    ↓
  Test Review（审查测试设计）← 新增
    ↓
  Apply（TDD 开发）
    ↓
  Build（构建验证）
```

### 效果
- ⏳ 当前依赖 CR，可用但不完美
- ✅ 改进方案可以提前发现问题

### 实际权衡
```
是否实现解锁接口？

考虑因素：
  1. 测试写错的频率不高（5%以内）
  2. CR 能发现大部分问题
  3. 解锁接口增加复杂度
  
决策：暂不实现，后续根据实际情况评估
```

### 示例回答：多 Agent 冲突

```
面试官：你遇到的最大技术难点是什么？

我：最大的难点是多 Agent 并发执行时的资源冲突问题。

【问题】
我们的编排任务会同时创建4个子任务并行开发，4个 code-agent 
同时执行。一开始遇到多个任务修改同一个文件，导致 Git 冲突。

【原因】
因为所有任务共用一个工作目录 /workspace/project/，
当任务A和任务B都要修改 common/ErrorCode.java 添加错误码时，
后提交的会覆盖先提交的。

【方案】
我采用了工作目录隔离的方案。每个任务创建独立的工作目录，
比如 /workspace/task-1/、/workspace/task-2/，各自独立克隆代码。
这样各自开发互不干扰。在 CR 阶段，人工合并可能的冲突。

同时还做了动态资源分配，端口号用 task_id 的哈希值计算，
数据库名加上 task_id 后缀，避免端口和数据库冲突。

【效果】
实施后，4个任务可以完全并行，开发时间从串行的160分钟
优化到40分钟，效率提升4倍。

【反思】
目前的方案是事后合并冲突。如果能在开发前就识别出会修改
同一文件的任务，提前协调或串行，会更好。这是可以优化的点。
```
