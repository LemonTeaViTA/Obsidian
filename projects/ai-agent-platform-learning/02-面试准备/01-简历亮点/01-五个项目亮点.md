## 💎 亮点1：可配置的工作流引擎

### 简历描述
```
设计并实现了基于数据库配置的工作流引擎，支持灵活的流程定义。
通过 spec_workflow 三层表结构（workflow-stage-convention），
实现了无需修改代码即可新增或调整业务流程，提升系统扩展性。
```

### 技术关键词
- Spring Boot + MyBatis
- 数据库驱动配置
- 策略模式
- 三层表结构设计

### 面试可讲
```
Q：为什么要做成可配置的？
A：不同需求类型需要不同流程。硬编码的话，每增加一种流程就要改代码、
   发版。通过数据库配置，产品可以在后台配置新流程，开发无需介入。

Q：如何保证配置的正确性？
A：1. 配置界面有校验
   2. 工作流有版本管理
   3. 白名单机制，新流程先小范围试用
```

## 💎 亮点2：编排任务 FAN_OUT 并行机制

### 简历描述
```
负责编排任务的 FAN_OUT 并行开发机制，通过 MQ 解耦实现多应用并行构建。
使用工作目录隔离技术避免 Git 冲突，将4个应用的串行开发时间从160分钟
优化到40分钟，开发效率提升4倍。
```

### 技术关键词
- RocketMQ 消息队列
- 多线程并发
- 工作目录隔离
- 状态聚合

### 面试可讲
```
Q：如何解决并发冲突问题？
A：每个子任务独立的工作目录和 Git 仓库。
   /workspace/task-1/、/workspace/task-2/ 各自独立，
   互不干扰。CR 阶段人工合并冲突。

Q：如果 MQ 消息丢失怎么办？
A：1. 持久化到数据库记录
   2. 补偿定时任务扫描 PENDING 超时的
   3. 重新投递或直接创建

Q：如何聚合子任务状态？
A：定时任务每3秒检查一次，子任务全部完成（status=500）后，
   更新父任务状态。
```

## 💎 亮点3：TDD Hook 强制测试机制

### 简历描述
```
实现了基于 Hook 机制的 TDD 强制执行系统，通过 TddTestLockHook 锁定
已编写的测试文件，TddStopGateHook 拦截未完成测试的提交，确保代码质量
和测试覆盖率，通过 manifest.json 追踪测试用例状态（PENDING/RED/GREEN）。
```

### 技术关键词
- Hook 机制
- TDD（测试驱动开发）
- 文件锁定
- 状态机（PENDING/RED/GREEN）

### 面试可讲
```
Q：为什么需要强制 TDD？
A：AI 可能会跳过测试或先写实现。通过 Hook 强制流程，
   保证先写测试、再写实现，提高代码质量。

Q：如何实现测试文件锁定？
A：manifest.json 记录每个测试用例的状态。
   当 state != PENDING 时（测试已写出），
   Hook 拦截对该文件的修改操作，返回错误。

Q：如果测试写错了怎么办？
A：当前依赖 CR 阶段人工发现。
   可优化：添加人工解锁接口，记录解锁原因和审批人。
```

## 💎 亮点4：MCP 工具集成生态

### 简历描述
```
设计并实现了基于 MCP（Model Context Protocol）的工具集成框架，
通过 JSON-RPC 协议统一接入企业内部系统（DEP、GitLab、VOS 等），
使 AI Agent 能够调用企业工具，支持可扩展的工具生态。
```

### 技术关键词
- MCP（Model Context Protocol）
- JSON-RPC
- SSE（Server-Sent Events）
- 工具注册与调用

### 面试可讲
```
Q：MCP 是什么？
A：Model Context Protocol，一种标准化的 AI 工具调用协议。
   类似于 API 网关，统一了 AI 调用工具的方式。

Q：如何集成一个新工具？
A：1. 实现 MCP Server（暴露 JSON-RPC 接口）
   2. 在 code-agent 配置文件中注册
   3. AI 通过工具名调用，code-agent 转发请求

Q：工具调用失败怎么处理？
A：1. 重试机制（最多3次）
   2. 错误信息返回给 AI，AI 可以换方案
   3. 超时保护（30秒）
```

## 💎 亮点5：跨系统实时状态同步

### 简历描述
```
实现了基于 WebSocket + Redis Pub/Sub 的实时状态推送系统，
解决了多实例部署下的状态同步问题。通过 Redis 订阅发布机制，
实现任务状态变更的实时推送，用户无需刷新即可看到最新进度。
```

### 技术关键词
- WebSocket
- Redis Pub/Sub
- 多实例部署
- 实时推送

### 面试可讲
```
Q：为什么用 Redis Pub/Sub？
A：ai24 部署多实例，任务可能在实例A更新，但用户连接在实例B。
   通过 Redis 广播，所有实例都能收到状态变更，推送给连接的用户。

Q：WebSocket 断线怎么办？
A：1. 前端自动重连机制
   2. 重连后发送最后收到的消息ID
   3. 后端推送中间遗漏的消息

Q：性能如何优化？
A：1. 只推送变更字段，不推送全量
   2. 批量推送（100ms 内的变更合并）
   3. 按任务ID订阅，不是全局广播
```
