## 📋 基础问题（5个）

### Q1：项目的整体架构是什么？

**回答要点**：
```
三个系统协作：

1. 前端（ai-program-factory）
   - React + TypeScript
   - 任务创建、进度展示、审批交互

2. 后端（ai24）
   - Spring Boot + MyBatis + Redis + MQ
   - 任务管理、工作流配置、审批流程

3. Agent执行侧（code-agent）
   - Python + Flask + Claude SDK
   - 接收任务、执行、上报

通信方式：
- HTTP REST API（同步调用）
- WebSocket（实时推送）
- MQ（异步解耦）
```

---

### Q2：为什么选择这个技术栈？

**回答要点**：
```
后端选 Spring Boot：
- 团队熟悉，生态成熟
- MyBatis 灵活的 SQL 控制
- Redis 高性能缓存和 Pub/Sub

Agent 选 Python：
- Claude SDK 是 Python
- AI 生态主要是 Python
- Flask 轻量快速

前端选 React：
- 组件化开发
- 生态丰富
- React Query 状态管理方便
```

---

### Q3：数据库表如何设计的？

**回答要点**：
```
核心表：

1. task_info（任务信息）
   - task_id（主键）
   - status（状态：0初始化、100执行中、500完成、999失败）
   - workflow_no（关联工作流）
   - current_stage（当前阶段）

2. spec_workflow（工作流配置）
   - workflow_no（工作流编号）
   - workflow_name（名称）

3. spec_stage（阶段配置）
   - workflow_no（关联工作流）
   - stage_no（阶段编号）
   - stage_order（执行顺序）

4. approval_item（审批事项）
   - task_id（关联任务）
   - confirmer（审批人，逗号分隔支持多人）
   - actual_confirmer（实际审批人）
   - confirm_status（0待审、1通过、2拒绝）

5. sub_task_info（子任务）
   - parent_task_id（父任务ID）
   - sub_task_id（子任务ID）

设计亮点：
- workflow 三层表结构支持灵活配置
- approval_item 的 confirmer 支持多人审批
- extend 字段用 JSON 存储扩展信息
```

---

### Q4：前后端如何通信？

**回答要点**：
```
1. HTTP REST API（同步）
   - 前端 → ai24：创建任务、查询状态、审批
   - ai24 → code-agent：下发任务、查询进度

2. WebSocket（实时推送）
   - ai24 → 前端：任务状态变更实时推送
   - Redis Pub/Sub 解决多实例同步

3. MQ（异步解耦）
   - 应用拆分 → 子任务创建
   - 避免阻塞，支持重试

4. 回调（状态上报）
   - code-agent → ai24：执行完成后回调上报
```

### Q7：编排任务如何并行的？

**回答要点**：
```
FAN_OUT 机制：

1. 应用拆分审批通过
   ↓
2. 为每个应用投递 MQ 消息
   ↓
3. MQ 消费者创建子任务
   ↓
4. 子任务并行下发 code-agent
   ↓
5. 工作目录隔离避免冲突
   ↓
6. 定时聚合子任务状态

关键点：
- MQ 解耦，异步处理
- 工作目录隔离
- 状态聚合机制
```

**追问：如果 MQ 消息丢失怎么办？**
```
1. 持久化到数据库（sub_task_creation_log）
2. 补偿定时任务扫描 PENDING 超时的
3. 重新投递或直接创建
4. 告警通知人工检查
```

### Q8：Agent 如何调用工具的？

**回答要点**：
```
MCP（Model Context Protocol）机制：

1. 工具注册
   - 配置文件定义 MCP Server 列表
   - code-agent 启动时连接

2. 工具调用
   - Claude 决定调用哪个工具
   - code-agent 通过 JSON-RPC 转发
   - MCP Server 执行并返回结果

3. 结果返回
   - 工具执行结果返回给 Claude
   - Claude 继续执行

支持的工具：
- ai24-mcp：查询任务信息
- dep-mcp：查询需求文档
- ui-test-mcp：UI 自动化测试
```

---

### Q9：审批拒绝如何重试的？

**回答要点**：
```
重试机制：

1. 拒绝触发
   - 审批人点击拒绝，填写原因
   - 触发策略的 onSomeRejected()

2. 反馈 AI
   - 调用 /task/query 接口
   - 传递拒绝原因
   - AI 根据反馈重新分析

3. 重试限制
   - 检查 retry_count
   - 最多重试 3 次
   - 超过转人工处理

4. 历史保留
   - 旧审批项不删除（REJECTED）
   - 新审批项重新创建（PENDING）
   - 可追溯变更历史
```

### Q10：测试锁定机制原理？

**回答要点**：
```
TDD Hook 机制：

1. manifest.json 记录测试状态
   {
     "cases": [
       {"test_file": "Test.java", "state": "PENDING"},
       {"test_file": "Test.java", "state": "RED"}
     ]
   }

2. TddTestLockHook 拦截修改
   - 检查该文件的 case state
   - 如果 state != PENDING（已写出）
   - 拒绝修改操作

3. TddStopGateHook 拦截结束
   - 检查是否还有 PENDING 或 RED
   - 如果有，拒绝 Stop
   - 连续 3 次自检通过才放行

目的：
- 强制先写测试、再写实现
- 保证测试覆盖率
```

### Q11：如何保证实时性？

**回答要点**：
```
WebSocket + Redis Pub/Sub：

1. 问题
   - ai24 多实例部署
   - 任务在实例A更新
   - 用户连接在实例B

2. 方案
   - 实例A 状态变更 → Redis Publish
   - 所有实例 Subscribe → 收到消息
   - 实例B 通过 WebSocket 推送给前端

3. 优化
   - 只推送变更字段
   - 批量推送（100ms 合并）
   - 按任务ID订阅（不是全局）

4. 容错
   - 前端自动重连
   - 重连后补发遗漏消息
```

### Q12：如何解决 Git 冲突？

**回答要点**：
```
工作目录隔离：

1. 开发阶段
   - 每个子任务独立工作目录
   - /workspace/task-1/project/
   - /workspace/task-2/project/
   - 独立克隆，互不干扰

2. CR 阶段
   - 人工检查冲突
   - 手动合并代码
   - 解决冲突后提交

优缺点：
- 优点：开发阶段无冲突
- 缺点：CR 阶段合并成本
- 权衡：开发效率 > 合并成本
```

### Q13：状态机如何设计的？

**回答要点**：
```
任务状态流转：

0（初始化）
  ↓ 下发 code-agent
100（执行中）
  ↓ 执行完成
200（待审批）
  ↓ 审批通过
300（推进下一阶段）
  ↓ 所有阶段完成
500（完成）

失败分支：
  ↓ 执行失败/超时
999（失败）

状态更新：
- code-agent 上报 → ai24 更新
- WebSocket 推送 → 前端展示
- 状态变更记录到 task_record
```

```
监控指标：

1. 任务维度

告警：
- 任务失败 → 钉钉告警
- 系统异常 → 短信告警

工具：
- Prometheus + Grafana
- Skywalking（APM）
- Langfuse（AI 调用追踪）
```

### Q15：性能瓶颈在哪里？

**回答要点**：
```
当前瓶颈：

1. Claude API 调用
   - 单次调用 10-30秒
   - 占总时长 80%
   - 无法优化（外部 API）

2. 审批等待
   - 人工审批 5-30分钟
   - 可以优化：增加审批人、设置超时

3. MQ 消费速度
   - 子任务创建略有延迟
   - 可优化：增加消费者

已优化点：
- 数据库索引优化
- Redis 缓存热点数据
- 并行执行代替串行
```

### Q17：如果重新设计会怎么做？

**回答要点**：
```
可以改进的地方：

1. 测试解锁接口
   - 当前依赖 CR 发现问题
   - 改进：添加人工解锁机制

2. 事件驱动的状态聚合
   - 当前定时轮询（3秒）
   - 改进：子任务完成发 MQ，立即聚合

3. 自动冲突检测
   - 当前事后人工合并
   - 改进：开发前识别会修改同一文件的任务

4. 智能重试策略
   - 当前固定3次
   - 改进：根据错误类型决定是否重试

但要说明：
- 这些不是缺陷，是权衡
- 当前方案满足业务需求
- 改进需要评估投入产出比
```
